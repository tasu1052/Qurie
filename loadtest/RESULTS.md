# 부하 테스트 결과 기록

측정 규칙: 같은 서버·같은 데이터·같은 명령으로 3회 실행, **중앙값**을 기록한다.
첫 1회는 워밍업(JIT·커넥션 풀 채우기)으로 버린다. 개선은 한 번에 하나씩 적용한다.

목표 규모(반 1개, 30명)에서 채팅은 병목이 아니다 — 개선 대상에서 제외.
알려진 구조적 한계는 지연이 아니라 인메모리 SimpleBroker 의 단일 인스턴스 제약(수평 확장 불가)이다.

### 한계 탐색 (인원·빈도를 올려가며, 로컬 60초씩)

| 구성 | 팬아웃 수신량 (60초) | latency p95 | max | 에러 |
|---|---|---|---|---|
| 30명 × 2초 간격 (목표 규모) | 26,140 | 40.5ms | 55ms | 0 |
| 30명 × 0.5초 간격 | 107,130 | 27ms | 35ms | 0 |

목표 부하의 약 45배(초당 2만 건 팬아웃)에서도 p95 가 수십 ms 로 유지 — 로컬 기준 한계점(knee)에
도달하지 못했다. 인메모리 브로커라 네트워크 왕복이 없는 조건임을 감안해도, 채팅 경로 자체는
충분한 여유가 있다. 100명 × 0.5초에서 STOMP 에러 1건(입장 직후 메시지 전송 타이밍 추정)과
단발성 스파이크(max 434ms)만 관찰됨.

## 시나리오 02 — 동시 편집 저장 (미측정)

실시간 공동 편집 동기화는 프론트 Yjs(collab-server) 담당이라 백엔드 측정 대상이 아니다.
백엔드 몫은 스냅샷 저장(`PUT /files/content`)인데, 저장 1회마다 프로젝트 전체 파일 본문을
읽어 versionHash 를 재계산하는 구조라 **파일 수백 개짜리 프로젝트**에서만 의미 있는 수치가 나온다.
현재 시드(파일 30개)로는 변별력이 없어 측정을 보류했다 — 대형 레포 임포트 후 측정할 것.
스크립트는 준비되어 있다: `loadtest/02-edit.js` (SAME_FILE=1 로 lost update 재현 모드 포함).

## 시나리오 04 — 리포트 (측정·개선 완료, 2026-08-18)

시연(학생 5명)에서 일괄 발급 오류가 재현된 뒤 측정했다. 진단했던 병목 두 개가 그대로 원인이었다:
- 일괄 발급(`POST /reports/all`)이 학생 수 × AI 동기 호출의 **순차 루프** — 30명이면 요청 하나가
  90초를 넘겨 CloudFront(오리진 응답 30초)가 먼저 504 를 끊는다. 백엔드는 계속 돌고 있으므로
  강사가 재클릭하면 두 번째 발급이 겹친다.
- 발급 동시 요청 시 delete→insert 레이스 — 집계와 저장 사이 AI 호출(수 초)이 창을 벌려,
  겹친 요청 둘 다 insert 로 가서 (session_id, ordinary_user_id) 유니크 제약 위반 500 + AI 중복 과금.

측정 조건: 로컬, AI 서버는 **지연 3초 고정 Node 목 서버**(LLM 변동성 제거, 콜 단위 동시 처리 수 로깅).
같은 시드·같은 명령으로 개선 전/후 각 1회 — 지연이 고정이라 회차 변동이 거의 없다.

| 지표 | 개선 전 | 개선 후 |
|---|---|---|
| 일괄 발급 HTTP 응답 (5명) | 16.7s (완료까지 대기) | **0.17s** (202 접수) |
| 일괄 발급 HTTP 응답 (30명) | **93s** → 게이트웨이 한계(30s) 초과 | **0.11s** (202 접수) |
| 전원 발급 완료 (30명) | 93s | **16.6s (−82%)** |
| 동시 단건 발급 10발: 5xx | 4건 | **0건** (1건 201 + 9건 409) |
| 동시 단건 발급 10발: AI 호출 | 10회 (같은 리포트에 10배 과금) | **1회** |
| AI 서버 동시 처리 (목 서버 로그) | 최대 1 (순차) | 최대 6 (병렬, 풀 설계값) |

적용 (브랜치 `fix/kts/report-bulk-async`): ① 일괄 발급 202 즉시 응답 + `reportBulkExecutor` 백그라운드
처리 + 완료 앱 알림 ② 학생별 발급을 `reportAiExecutor`(동시 6)로 병렬화 — 6 인 근거는 병목이 LLM 왕복,
HikariCP 기본 풀 10, GMS rate limit ③ delete→insert 를 같은 행 update(upsert)로 교체 + (세션, 학생)
단위 진행 중 가드로 겹친 발급을 409 거절.

남은 것: EC2 실서버 + 실제 LLM 재측정(GMS 지연 변동 포함), 다중 인스턴스로 가면 인메모리 가드를 DB 락으로 교체.

## EC2 측정 (운영 환경: nginx TLS + t계열 인스턴스 + 컨테이너 MySQL)

| 지표 | EC2 before (3회 중앙값) | EC2 after (3회 중앙값) | 변화 | 로컬 참고 (before→after) |
|---|---|---|---|---|
| GET /questions p95 (ms) | 590.4 | **518.8** | **−12%** | 201.5 → 138.8 (−31%) |
| GET /questions avg (ms) | 365.4 | **307.1** | **−16%** | 127.3 → 74.9 (−41%) |
| POST /progress p95 (ms) | 221.2 | 199.8 | −10% | 61.8 → 63.3 |
| 채팅 브로드캐스트 p95 (ms) — **대조군** | 79.1 | 105.0 | +33% | 40.5 (코드 변경 없음) |

- before 회차별 p95: 472.9 / 590.4 / 676.1 · after 회차별: 587.9 / 518.8 / 514.8 (전 회차 실패 0)
- **첫 after 측정(ec2-after-quiz-*)은 폐기** — 배포 직후 JVM 콜드 + 직후 다른 MR 재배포가 겹쳐
  워밍업 부족 상태였다(avg 475→377→325 로 급강하 중). 워밍업 3연발 후 재측정한 것이 위 값(after2).
- **대조군 해석**: 코드가 안 바뀐 채팅이 before 세션보다 33% 느리게 측정됐다 — after 측정 시점의
  서버 환경(공유 t계열 인스턴스)이 before 시점보다 느렸다는 뜻이고, 따라서 −12~16% 는 **실제 개선의
  하한선**으로 보는 것이 타당하다.
- EC2 개선 폭이 로컬(−31%)보다 작은 이유: 이 배포는 MySQL 이 **같은 호스트의 컨테이너**라 쿼리
  왕복이 수백 µs 수준이다. N+1 제거의 이득은 왕복 지연에 비례하므로, DB 를 분리(RDS 등)하는 순간
  이 개선의 가치가 커진다. 현재 EC2 응답시간의 지배 요인은 인스턴스 CPU + TLS 다.

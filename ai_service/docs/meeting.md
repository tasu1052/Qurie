# Qurie 팀 회의 안건 — AI 파트 설계 공유

> 작성: 준형 (AI 담당)
> 목적: AI 파이프라인 설계 확정 사항 공유 + 파트 간 인터페이스 합의 + 팀 결정 필요 사항 처리

---

## 0. 회의 목표 (3가지)

1. **공유**: AI 퀴즈 생성이 어떻게 동작하는지 팀 전체가 이해
2. **합의**: AI 서버 ↔ 백엔드 인터페이스, DB 스키마 변경점 확정
3. **결정**: 팀이 함께 정해야 할 열린 질문 처리

소요 예상: 40~50분

---

## 1. [공유] AI 퀴즈 생성 방식 — 5분 설명

핵심 한 문장:
> "LLM이 만든 문제를 그대로 쓰지 않는다. 출제·풀이·판정 3역할이 검증한 문항만 사용자에게 나가고, 이미 만든 문항은 재사용해 비용을 줄인다."

**구조**: Generator(출제) → Solver(정답 가리고 풀기) → Judge(품질 채점) → 통과분만 사용
- 왜 3역할? LLM이 자기 문제를 검수하면 같은 실수를 반복함. 정답 가리고 독립적으로 풀려야 모호성이 드러남.
- 왜 계열 다른 모델? 같은 회사 모델은 실패 패턴이 같아 교차 검증이 안 됨. (생성=A사, 풀이·판정=B사)

**모델 선택**: A/B 실측으로 결정 중. 현재 claude-sonnet 계열이 가성비 우위. (감이 아니라 데이터로 정함)

**비용 관리**: 크레딧이 토큰 비례라 실측 로깅 필수. 배치 생성 + 코드 참조 + 시맨틱 캐시로 절감.

> 상세 근거는 `quiz_design_final.md` 참고 (12개 결정 + 예상질문 대비)

## 2. [합의] DB 스키마 변경점 — 백엔드와 확정

`quiz_schema.dbml` 기준. 기존 ERD에서 바뀐 것:

### 신규 테이블
- **code_snapshot** ⭐ — 코드 원본을 어디 저장할지가 기존 스키마에 없었음. 특정 시점 코드를 파일별로 얼려 보관. quiz가 이걸 참조.
- **quiz_set** — "퀴즈 생성 버튼 1회 = 출제 회차". 사용자 입력(문항수/유형/난이도 비율/자유 프롬프트)과 비동기 생성 상태(PENDING→READY) 저장.
- **quiz_choice** — 객관식 보기. (기존엔 answer 한 컬럼뿐이라 객관식 불가능했음)
- **quiz_llm_log** — LLM 호출 토큰 실측 로그 (비용 관리용, 선택이지만 권장)

### 기존 테이블 수정
- **quiz**: 코드를 복제하지 않고 `file_path + line_start/end`로 스냅샷 참조. `tested_concept`(개념 태그), 파이프라인 산출물(status/judge_score/gen_model) 추가.
- **quiz_progress**: `chosen_choice_id`(고른 보기 = 오개념 분석), `status`(ATTEMPTED/SKIPPED/TIMEOUT)로 통합, `(quiz_id, user_id)` unique로 재응시 제한. 단답형 채점 상태(grading_status) 추가. + 기존 `ordinary_user_id → group.id` 오타 수정 필요.
- **report**: 타입 수정(bigint→decimal/json), `concept_stats` 추가 ⭐, `quiz_set_id` 추가.

### 백엔드에 특별히 요청할 것
- **report에 `concept_stats`(개념별 정답률) 꼭 넣기** — AI가 붙인 tested_concept 태그가 여기서 살아남. 없으면 "취약 개념 진단"이라는 차별점이 죽음.
- **재응시 제한은 DB unique 제약으로** — 앱 로직으로 막으면 동시 요청에서 뚫림.
- **quiz_set.status가 READY 되기 전엔 문항 조회 차단** — 생성 중인 문항 노출 방지.

## 3. [합의] AI 서버 ↔ 백엔드 인터페이스

**아키텍처 제안**: AI는 FastAPI 별도 서버, Spring Boot가 HTTP로 호출.
- 이유: LangGraph·트레이싱 도구가 Python 우선 + AI 담당 작업 영역 분리 + 배포 독립

**역할 분담**:
- AI 서버(FastAPI): 받은 코드 AST 분석(전처리) → 퀴즈 생성/검증 → 결과 반환. 코드는 저장 안 하고 참조만.
- 백엔드(Spring): quiz_set/quiz 저장, 출제 정책(모드별 선택), 응답 채점 집계.

**작업 경계 명확화**:
- AST 분석(import·참조 감지)은 LLM이 아니라 코드가 하는 전처리 단계 → 언어별 파서가 Python에 있으니 AI 서버 담당.
- 코드 원본은 백엔드가 요청에 실어 보내는 방식 제안(방식 C) → AI 서버가 DB 직접 접근 안 해도 됨(결합도·보안 유리).

**제안하는 요청 형태** (`POST /quizzes/generate`):
```json
{
  "quiz_set_id": 42,
  "language": "javascript",
  "target": { "file_path": "solution.js", "line_start": 3, "line_end": 10 },
  "files": {
    "solution.js": "파일 전체 코드...",
    "utils.js": "참조 가능성 있는 파일..."
  },
  "config": {
    "count": 5,
    "types": ["MULTIPLE_CHOICE"],
    "ratio": { "easy": 30, "normal": 50, "hard": 20 },
    "user_prompt": "cleanup 위주로"
  }
}
```
- AI 서버가 받은 코드를 넓게(드래그 범위보다 넓게, 프로젝트 전체보다 좁게) 읽고, AST로 필요한 것만 골라 생성.
- `files`에 무엇을 얼마나 담을지 = 멀티파일 지원 범위(Q2)와 직결. MVP는 드래그된 파일 하나, 크로스파일은 확장.

**확인 필요**:
- `files` 범위: MVP에서 드래그된 파일만 보낼지, 프로젝트 여러 파일을 보낼지.
- 중복 검사(임베딩 비교)를 AI 서버가 하려면 기존 문항 임베딩을 봐야 함 → ① 백엔드가 요청에 실어 보냄 vs ② AI 서버에 읽기 전용 DB 접근 허용. 어느 쪽?
- 생성이 비동기(수십 초)라 콜백/폴링 방식 합의 필요.

## 4. [결정] 팀이 함께 정해야 할 열린 질문

### Q1. 코드 원본을 어디 저장하나 ⭐ (인프라·백엔드)
- A: DB에 저장 (code_snapshot.content = longtext)
- B: Git 연동, 커밋 해시만 저장 (기획서 "Git 연동 미확정"과 연결)
- → 인프라 담당 의견 필요. 지금 스키마는 A 기준.

### Q2. 한 세션에서 파일 하나만 다루나, 여러 파일인가
- 여러 파일이면 → file_path 필요, import된 함수가 다른 파일에 있는 문제 대응 필요
- 하나면 → 단순해짐
- → 스크린샷 UI는 멀티파일(solution.js, test_cases.json...). 범위 결정 필요.

### Q3. MVP 문제 유형 범위
- 제안: 객관식 + 빈칸 먼저. 단답형은 AI 채점(의미 판단)이 또 하나의 과제라 2차.
- 지원 언어: Python + Java 1차 (AST 분석이 언어별로 달라서)

### Q4. 두 출제 모드 확정
- ASSESSMENT(평가): 전원 동일 문제, 리포트 반영, 재응시 제한, 난이도 비율 통제
- PRACTICE(학습): 개인화(취약 개념), 반복 가능, 점수 미반영
- → 개인화는 AI가 아니라 개념 태그 기반 DB 쿼리로 구현. 우선순위 합의.

### Q5. report의 quiz_rating이 무슨 의미인가
- 사용자 실력 점수? 리포트 만족도? 문항 평점?
- → 의미 확정 필요.

## 5. [공유] 확장 로드맵 (지금 안 하지만 방향 공유)

MVP 이후, 필요성 확인되면 도입:
- 계산형 문제 파라미터화 (값만 바꿔 LLM 없이 재생성)
- 프로젝트 전체 코드 검색 (진짜 Agentic RAG — 온보딩 시나리오)
- 라이브러리 문서 조건부 검색 / 공식문서 근거 인용
- 난이도 자동 보정 (Elo/IRT)

→ "RAG 왜 안 쓰냐"는 질문 대비: 지금은 검색이 필요없는 구조(코드가 손에 있음). 낯선 라이브러리 다룰 때 조건부로 도입 예정.

## 부록: 회의 중 나올 만한 질문 대비 (준형 참고용)

- **"RAG 안 써요?"** → 검색이 필요한 문제가 아님. 코드가 이미 있음. 저희 문제는 생성물 품질 보증이라 Evaluator-Optimizer 루프를 씀. 낯선 라이브러리는 조건부 검색으로 확장 예정.
- **"에이전트 몇 개?"** → 개수가 본질이 아님. 생성자·검증자 분리 + 검증이 게이트 + 피드백 루프가 핵심.
- **"비용 괜찮아요?"** → 배치 생성, 코드 참조(줄번호만), 정답 비교는 코드로(0콜), 시맨틱 캐시 재사용, 개발 중 mock 모드. 토큰 실측 관리.
- **"품질 어떻게 보장?"** → 독립 풀이자+심사자 통과분만 사용. 계열 다른 모델로 교차 검증. 탈락 문항은 프롬프트 개선에 활용.
- **"왜 코드를 문항에 안 넣고 줄번호만?"** → 토큰 절약 + 코드 변형 방지 + 원본을 프론트가 잘라 보여줌.

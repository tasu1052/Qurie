# Qurie 퀴즈 생성 설계 — 최종 정리 (설명용)

> 팀원·심사위원에게 "왜 이렇게 설계했는가"를 설명하기 위한 문서.
> 각 결정마다 [무엇을] + [왜] + [한 줄 방어 멘트]를 붙였다.

---

## 0. 한 장 요약

퀴즈를 단일 LLM 호출로 뚝딱 만들지 않는다.
**생성 → 블라인드 풀이 → 판정**의 3역할 루프로 품질을 보증하고,
같은 문제를 반복 생성하지 않도록 **시맨틱 캐시**로 비용을 줄이며,
두 가지 **출제 모드(평가/학습)**로 나눠 운영한다.

핵심 문장:
> "저희는 LLM이 만든 문제를 그대로 쓰지 않습니다.
> 독립된 풀이자와 심사자가 검증한 문항만 사용자에게 나가고,
> 이미 만든 문항은 재사용해 비용을 줄입니다."

---

## 1. 왜 파인튜닝이 아니라 API + 파이프라인인가

**무엇을**: HuggingFace 모델 파인튜닝 대신, GMS API를 호출하는 파이프라인으로 구현.

**왜**:
- "코드를 읽고 퀴즈를 만든다"는 추론 능력 문제. 오픈 7B~14B를 파인튜닝해도 프론티어 모델의 코드 이해력을 못 따라감.
- 파인튜닝하려면 고품질 "코드→퀴즈" 쌍 수천 개가 필요한데, 그 데이터를 만드는 것 자체가 프로젝트보다 큰 일.
- 퀴즈 품질을 결정하는 건 모델 선택 10%, 파이프라인·프롬프트 설계 90%.

**방어 멘트**:
> "품질 병목은 모델이 아니라 설계라고 판단했습니다. 파인튜닝은 데이터가 쌓인 뒤 비용 절감용으로 미뤄둔 카드입니다."

---

## 2. 왜 단일 프롬프트가 아니라 3역할 루프인가 (핵심)

**무엇을**: Generator(출제) → Solver(블라인드 풀이) → Judge(판정)의 역할 분리 + 불합격 시 재생성 루프.
패턴 이름: Self-Refine / Evaluator-Optimizer / LLM-as-a-Judge.

**왜**:
- LLM에게 "문제 만들고 스스로 검수해"라고 하면 자기 오류를 관대하게 통과시킴.
- 그래서 **정답을 가린 채 독립적으로 풀게 하는 Solver**가 핵심. 출제자가 놓친 정답 모호성이 여기서 드러남.
- Solver가 출제 정답과 다른 답을 고르면 → 정답이 모호하다는 증거 → 자동 불합격.
- Judge는 "정답이 유일한가 / 오답이 그럴듯한가"라는 품질을 따로 검증.
- 불합격 사유(critique)를 다음 생성에 넣어 같은 실수를 반복하지 않게 함.

**Solver와 Judge의 역할 차이 (자주 받는 질문)**:
- Solver: "답이 흔들리지 않고 유지되는가" (안정성)
- Judge: "정답이 논란 없이 하나인가" (유일성)
- 둘은 다른 걸 보므로 둘 다 필요. Solver만 쓰면 "애매한데 우연히 정답과 같은 번호를 찍은" 불량 문항이 통과됨.

**방어 멘트**:
> "출제자가 자기 문제를 검수하면 같은 착각을 반복합니다. 그래서 정답을 가리고 독립적으로 풀게 한 뒤, 심사자가 정답 유일성까지 확인합니다."

---

## 3. 왜 서로 다른 회사 모델을 섞는가

**무엇을**: Generator는 한 계열(예: OpenAI 또는 Claude sonnet), Solver·Judge는 다른 계열(예: Claude haiku).

**왜**:
- 같은 회사 모델은 학습 데이터·아키텍처가 비슷해 실패 패턴도 비슷함.
- GPT로 출제하고 GPT로 풀면 GPT가 착각하는 지점을 둘 다 똑같이 착각 → 검증이 헛돎.
- 계열을 섞으면 실패 지점이 겹치지 않아 진짜 독립적인 검증자가 됨.

**방어 멘트**:
> "검증자가 출제자와 같은 계열이면 같은 실수를 공유합니다. 교차 검증을 위해 계열을 다르게 뒀습니다."

---

## 4. 왜 모델을 실험으로 골랐는가 (감이 아니라 측정)

**무엇을**: 대표 코드 몇 개로 모델별 통과율·크레딧·문항당 비용을 실측해서 선택.

**왜**:
- "제일 좋은 모델이 답"이 아님. pro급(540크레딧)은 12배 비싼데 이 태스크엔 과함.
- Generator를 너무 올리면 Solver가 못 푸는 문제가 나와 정답인데도 탈락 → 재시도 급증.
- 통과율이 비슷하면 싼 모델, 확실히 차이 나면 좋은 모델. 판단 기준은 "합격 문항 1개당 크레딧".

**방어 멘트**:
> "모델 선택을 감이 아니라 A/B 실측으로 정했습니다. 통과율 대비 비용이 가장 효율적인 조합을 골랐습니다."

---

## 5. 왜 코드를 문항에 넣지 않고 줄 번호로 참조하는가

**무엇을**: 문항에 코드를 복제하지 않고 `file_path` + `line_start/end`만 저장. 화면엔 원본을 잘라 표시.

**왜**:
- 코드를 문항마다 출력하면 출력 토큰(=크레딧)이 크게 늘어남. 줄 번호 2개만 출력하면 훨씬 쌈.
- LLM이 코드를 베껴 쓰다 오타·변형을 내면 정답이 틀려질 수 있음. 원본을 그대로 쓰면 원천 차단.
- 동시 편집으로 코드가 바뀌므로, 스냅샷(code_version) + 줄 번호로 "그 시점 그 줄"을 고정해야 해설이 성립.

**방어 멘트**:
> "코드를 복제하면 토큰 낭비 + 변형 위험이 있어, 원본의 줄 범위만 참조하도록 했습니다."

---

## 5.5. 왜 드래그한 코드 범위를 그대로 믿지 않고 import를 먼저 분석하는가

**무엇을**: 사용자가 드래그한 줄 범위를 그대로 출제에 쓰지 않고, 먼저 AST로 그 범위의 외부 의존성(import·정의 안 된 이름)을 분석한다.

**왜 (구체적 사례)**:
- 사용자가 3~10줄을 드래그했는데, 그 안에 `from utils import factorial` 처럼 **다른 파일에서 온 함수**만 있고 정의는 범위 밖에 있을 수 있음.
- 이 상태로 "이 코드의 출력은?"을 출제하면, AI가 `factorial`이 뭔지 몰라 상상해서 **틀린 문제(할루시네이션)**를 냄.
- 드래그 범위는 "코드의 자기완결적 단위"가 아닐 수 있다는 게 핵심. 실제 멀티파일 프로젝트에선 반드시 발생.

**어떻게 (MVP 방침)**:
1. **AST로 import·외부 참조 감지** (LLM 없이, 크레딧 0) — 최소한 "이 범위에 외부 의존성이 있다"는 것만이라도 알아야 모르고 출제하지 않음.
2. **같은 파일 내에서 정의를 찾을 수 있으면** → 드래그 범위를 자동 확장해 정의까지 컨텍스트에 포함.
3. **다른 파일/외부 라이브러리면** → MVP에선 그 부분을 피해 출제하거나, 해당 함수의 동작을 묻지 않는 문제만 출제.
4. **프로젝트 전체를 검색해 정의를 가져오는 것**은 2차 (= Agentic RAG, 아래 로드맵). 대형 코드베이스/온보딩 시나리오와 연결됨.

**AST란**: 코드를 글자가 아니라 문법 구조(트리)로 분해한 것. "이 이름이 함수 호출인지, 이 범위에 정의가 있는지"를 정확히 판단할 수 있어 LLM 없이 의존성을 뽑아냄. 언어마다 파서가 달라 1차 지원 언어(Python·Java)에 맞춰 구성.

**방어 멘트**:
> "드래그한 텍스트를 그대로 출제하면 외부 의존성 때문에 틀린 문제가 나올 수 있습니다. 그래서 먼저 import를 분석해 코드 범위가 자기완결적인지 확인합니다."

## 6. 왜 시맨틱 캐시로 비용을 줄이는가

**무엇을**: 검증 통과한 문항을 임베딩과 함께 저장(문항 은행). 새 요청이 오면 먼저 유사한 기존 문항을 검색해 재사용.
전문 용어: Semantic Cache(의미 기반 캐시).

**왜**:
- 매 요청마다 생성하면 토큰이 계속 나감. "생성"을 "검색"으로 대체하면 검색은 크레딧이 안 듦.
- 서비스가 굴러갈수록 은행이 차서 재사용률이 오르고 문항당 비용이 떨어짐.

**유사도 3구간 분기**:
- 매우 높음(같은 코드) → 그대로 재사용 (LLM 0콜)
- 중간 → 재검증 (아래 7번)
- 낮음/없음 → 새로 생성

**방어 멘트**:
> "생성형 AI 서비스의 비용 문제를 시맨틱 캐시로 풉니다. 이미 만든 문항을 의미 기반으로 찾아 재사용합니다."

---

## 7. 왜 캐시를 "수정"이 아니라 "재검증"으로 재사용하는가

**무엇을**: 유사하지만 코드가 살짝 다른 캐시 히트 시, 문제를 고치지 않고 **Solver로 다시 풀려 + Judge로 재확인**. 통과하면 재사용, 실패하면 새로 생성.

**왜**:
- "수정"은 기존 문제 전체를 입력에 넣고 다시 써야 해서 입력·출력이 커짐 → 새로 생성과 비용이 비슷.
- "재검증"은 문제를 안 고치고 Solver가 정답 번호 하나만 출력 → 훨씬 쌈.
- 대부분 코드가 살짝 달라도(변수명 등) 문제는 여전히 성립하므로 재검증만으로 충분한 경우가 많음.

**비용 순서**:
재사용(0) < 재검증(Solver+Judge, 생성 스킵) < 수정 ≈ 새 생성

**방어 멘트**:
> "고치는 게 만드는 것보다 쌀 것 같지만, 기존 문제를 입력에 넣어야 해서 실제론 비슷합니다. 그래서 고치지 않고 다시 풀려서 여전히 유효한지만 확인합니다."

---

## 8. 왜 캐시 매칭에 "코드 유사도"까지 보는가 (중요한 함정)

**무엇을**: 캐시를 뒤질 때 개념 유사도뿐 아니라 실제 코드 유사도도 함께 판단.

**왜 (구체적 사례)**:
- 캐시: "이 재귀 함수에 4를 넣으면?" / 새 사용자 코드: 반복문으로 구현
- 답(24)은 같아서 Solver 재검증도 통과해버리지만, 지문이 "재귀 함수"라고 코드 구조를 특정 → 반복문 코드엔 안 맞음.
- 개념만 보면 이 사고를 못 막음. 코드 유사도까지 봐야 "구조가 다르면 재사용 안 함"이 성립.

**문제 유형별 캐시 정책**:
- MICRO(코드 밀착): 사실상 같은 코드일 때만 재사용 → 주로 같은 프로젝트 내 재출제에서 히트
- CONCEPTUAL(개념 확장): 개념만 맞으면 사용자 간 공유 가능 → 캐시 이득이 큼

**방어 멘트**:
> "개념이 같아도 코드 구조가 다르면 재사용하면 안 됩니다. 그래서 캐시 매칭에 코드 유사도를 함께 넣었습니다."

---

## 9. 왜 두 가지 출제 모드로 나누는가

**무엇을**:
- ASSESSMENT(평가): 참여자 전원 동일 문제, 공식 리포트 반영, 재응시 제한, 시스템이 난이도 비율 통제
- PRACTICE(학습): 학생별 개인화, 취약 개념 중심, 반복 가능, 공식 점수 미반영

**왜**:
- 두 모드는 "출제 정책"만 다를 뿐 생성 파이프라인은 동일 → 파이프라인은 그대로 두고 정책만 얹음.
- 개인화(취약 영역)는 LLM이 아니라 DB 쿼리로 함: 개념 태그별 정답률을 집계해 약한 개념 문항을 우선 출제.
- 캐시는 주로 PRACTICE에 사용. ASSESSMENT는 문제 유출/공정성 때문에 fresh 생성 위주.

**방어 멘트**:
> "평가와 학습은 목적이 달라 출제 정책을 분리했습니다. 개인화는 AI가 아니라 개념 태그 기반 통계로 구현해 비용 없이 동작합니다."

---

## 10. 왜 비동기 생성인가

**무엇을**: 생성 요청 시 즉시 "접수" 응답을 주고, 실제 생성은 백그라운드에서. 상태(PENDING→GENERATING→READY)를 폴링.

**왜**:
- Self-Refine 루프는 재시도까지 하면 문항당 수십 초 걸림. 사용자를 로딩 화면에 묶어둘 수 없음.
- 리뷰 세션 진행 중 백그라운드로 미리 생성 → 리뷰 종료 시점에 퀴즈 시작하면 지연이 UX에 안 보임.

**방어 멘트**:
> "생성이 수십 초 걸려서, 접수만 즉시 응답하고 백그라운드로 만들어 리뷰가 끝날 때 바로 풀 수 있게 했습니다."

---

## 11. 왜 개념 태그(tested_concept)를 붙이는가

**무엇을**: 문항마다 검증 개념 태그(예: "useEffect cleanup")를 저장.

**왜**:
- 사용자별로 어느 개념을 틀렸는지 집계 가능 → PRACTICE의 취약 개념 집중 출제의 근거.
- 세션 리포트에 "이 팀은 X 개념이 약함" 같은 개념별 통계가 거의 공짜로 생김.
- 이게 없으면 "10문제 중 6개 맞음" 수준의 뭉뚱그린 점수밖에 못 줌.

**방어 멘트**:
> "개념 태그 덕분에 '무엇을 모르는지'를 짚어줄 수 있습니다. 약점만 골라 반복 학습하는 게 저희 서비스의 차별점입니다."

---

## 12. 왜 실패·비용을 기록하는가

**무엇을**: 탈락 문항(reject_reason), 생성 모델(gen_model), LLM 호출 토큰 로그(quiz_llm_log)를 저장.

**왜**:
- 탈락 사유가 쌓이면 어떤 유형이 자꾸 실패하는지 보이고 → 프롬프트 개선 근거가 됨.
- 크레딧이 토큰 비례라 실측 로그가 없으면 비용 예측·최적화가 불가능(초기 추정과 실측이 10배 차이 난 경험).
- gen_model 기록으로 "어느 모델 문항의 정답률이 높나" 사후 비교 가능.

**방어 멘트**:
> "실패와 비용을 데이터로 남겨 파이프라인을 개선합니다. 문항당 크레딧을 얼마나 줄였는지 정량으로 보여줄 수 있습니다."

## 13. 확장 로드맵 (MVP 이후, 측정 후 도입)

지금 넣지 않지만 필요성이 확인되면 붙일 것들. "측정 없이 최적화하지 말라" 원칙에 따라, 해당 패턴이 실제로 반복되는지 데이터로 확인한 뒤 도입한다.

- **계산형 문제 파라미터화** — 입력값만 바꾸면 답이 바뀌는 계산형 문항(예: `fib(4)` → `fib(6)`)을 "템플릿 + 계산기 + 오답 규칙"으로 저장. 이후 값 변경은 코드가 계산하므로 LLM 없이 무한 재생성(크레딧 0). 단, 처음 생성이 더 비싸고 계산형 문제에만 적용되므로, 반복 출제가 잦다고 확인된 뒤 도입.
- **프로젝트 전체 코드 검색 (Agentic RAG)** — 드래그 범위 밖(다른 파일)의 함수 정의를 프로젝트에서 검색해 컨텍스트에 추가. 멀티파일 프로젝트·대형 코드베이스·신입 온보딩 시나리오에서 필요. 이때가 진짜 Retrieval이 생기는 시점.
- **라이브러리 문서 조건부 검색** — 낯설거나 빠르게 바뀌는 라이브러리(LangChain 등)를 감지하면 공식문서를 검색해 근거로 첨부. 표준 라이브러리엔 불필요하므로 "필요할 때만" 검색.
- **공식문서 근거 인용** — 퀴즈 해설에 언어 공식문서 출처를 링크로 제공. 초보 학습자 신뢰도·할루시네이션 방어의 차별점.
- **난이도 자동 보정(Elo/IRT)** — 실사용 정답 데이터로 문항 난이도를 자가 보정. LLM이 붙인 difficulty의 부정확성을 데이터로 교정.

## 부록 A. 전체 흐름 한눈에

```
[요청] 문항 수·유형·난이도 비율·자유 프롬프트 입력 (quiz_set 생성, status=PENDING)
   ↓  (비동기)
[캐시 조회] 요청 임베딩 → 유사 문항 검색 (개념 + 코드 유사도)
   ├─ 매우 유사 & 같은 코드 → 재사용 (LLM 0콜)
   ├─ 중간 유사 → 재검증(Solver 풀이 + Judge 확인) → 통과 시 재사용
   └─ 낮음/없음 → 생성 파이프라인
                    Generator(출제) → Solver(블라인드 풀이)
                    → 정답 일치? (코드로 비교, 0콜)
                       ├─ 불일치 → 탈락 or 재생성(critique 반영)
                       └─ 일치 → Judge(품질 채점) → 통과분만 은행 적립
   ↓
[출제] ASSESSMENT(고정 세트) / PRACTICE(취약 개념 우선)
   ↓
[응답 기록] 고른 답·정답 여부·소요시간 저장 → 리포트·개인화 재료
```

## 부록 B. 예상 질문 대비

- **"RAG 왜 안 썼어요?"**
  → 검색이 필요한 문제가 아니었음(코드가 이미 손에 있음). 저희 문제는 생성물 품질 보증이라 Evaluator-Optimizer를 씀. 단, 낯선 라이브러리는 문서를 조건부 검색하는 Agentic RAG로 확장 예정.

- **"에이전트가 몇 개예요?"**
  → 개수가 본질이 아님. 핵심은 생성자와 검증자가 분리돼 있고, 검증이 게이트 역할을 하며, 피드백이 루프를 돈다는 것.

- **"비용 많이 들지 않아요?"**
  → 배치 생성, 코드 참조, 정답 일치는 코드로 비교(0콜), 시맨틱 캐시로 재사용, 개발 중엔 mock 모드. 토큰을 실측해 관리함.

- **"품질 어떻게 보장해요?"**
  → 독립 풀이자와 심사자를 통과한 문항만 나감. 계열이 다른 모델로 교차 검증. 탈락 문항은 프롬프트 개선에 활용.

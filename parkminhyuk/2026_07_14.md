# Day 2 — Spring Boot 프로젝트 구조

## 1. 학습 목표

Qurie 백엔드 프로젝트의 기본 구조를 구성하고, Spring Boot에서 요청이 처리되는 흐름을 학습했다.

이번 학습의 주요 목표는 다음과 같다.

* `Controller → Service → Repository` 계층의 역할을 이해한다.
* Entity와 Request/Response DTO를 분리한다.
* 생성자 기반 의존성 주입 방식을 이해한다.
* 기능 중심으로 패키지 구조를 구성한다.
* REST API의 HTTP 메서드와 상태 코드를 구분한다.
* 방 생성, 조회, 수정, 삭제 API를 구현한다.
* Swagger를 통해 방 CRUD API를 테스트한다.
* Controller에서 Entity를 직접 반환하지 않는다.

---

## 2. Spring Boot 프로젝트 구성

Spring Boot는 `spring-boot-starter-web` 의존성을 통해 Spring MVC 기반 웹 애플리케이션을 구성할 수 있다.

`spring-boot-starter-web`에는 일반적으로 다음 기능이 포함된다.

* Spring MVC
* 내장 Tomcat 서버
* JSON 직렬화 및 역직렬화
* HTTP 요청 및 응답 처리
* REST API 구현 기능
* Bean Validation 연동

프로젝트에서 사용할 주요 의존성은 다음과 같다.

```gradle
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
    implementation 'org.springframework.boot:spring-boot-starter-data-jpa'
    implementation 'org.springframework.boot:spring-boot-starter-validation'

    implementation 'org.springdoc:springdoc-openapi-starter-webmvc-ui:2.8.9'

    runtimeOnly 'com.mysql:mysql-connector-j'

    compileOnly 'org.projectlombok:lombok'
    annotationProcessor 'org.projectlombok:lombok'

    testImplementation 'org.springframework.boot:spring-boot-starter-test'
}
```

각 의존성의 역할은 다음과 같다.

| 의존성                              | 역할                       |
| -------------------------------- | ------------------------ |
| `spring-boot-starter-web`        | REST API 및 Spring MVC 구성 |
| `spring-boot-starter-data-jpa`   | JPA 기반 데이터베이스 접근         |
| `spring-boot-starter-validation` | 요청 데이터 검증                |
| `springdoc-openapi`              | Swagger API 문서 생성        |
| `mysql-connector-j`              | MySQL 연결                 |
| `lombok`                         | 반복적인 Java 코드 감소          |
| `spring-boot-starter-test`       | 테스트 환경 구성                |

## 3. 요청 처리 흐름

Spring Boot에서 일반적인 요청 처리 흐름은 다음과 같다.

```text
클라이언트
    ↓ HTTP 요청
Controller
    ↓
Service
    ↓
Repository
    ↓
Database
```

응답은 반대 방향으로 전달된다.

```text
Database
    ↓
Repository
    ↓
Service
    ↓
Controller
    ↓ HTTP 응답
클라이언트
```

예를 들어 방 생성 요청은 다음과 같이 처리된다.

```text
POST /api/rooms
        ↓
RoomController.createRoom()
        ↓
RoomService.createRoom()
        ↓
RoomRepository.save()
        ↓
방 생성 결과 반환
```

# 4. Controller, Service, Repository의 역할

## 4.1 Controller

Controller는 클라이언트의 HTTP 요청을 받는 계층이다.

주요 책임은 다음과 같다.

* URL과 HTTP 메서드 매핑
* 요청 데이터 수신
* 요청 데이터 검증
* 인증된 사용자 정보 전달
* Service 호출
* HTTP 응답과 상태 코드 반환

Controller에는 핵심 비즈니스 로직을 작성하지 않는 것이 좋다.

```java
@RestController
@RequestMapping("/api/rooms")
@RequiredArgsConstructor
public class RoomController {

    private final RoomService roomService;

    @PostMapping
    public ResponseEntity<RoomResponse> createRoom(
            @Valid @RequestBody CreateRoomRequest request
    ) {
        RoomResponse response = roomService.createRoom(request);

        return ResponseEntity
                .status(HttpStatus.CREATED)
                .body(response);
    }
}
```

Controller는 방을 어떻게 저장하는지 직접 알 필요가 없다.

```java
roomRepository.save(room);
```

이와 같은 코드는 Controller가 아니라 Service에서 처리한다.

---

## 4.2 Service

Service는 애플리케이션의 핵심 비즈니스 로직을 수행한다.

주요 책임은 다음과 같다.

* 도메인 규칙 검증
* Entity 생성 및 변경
* Repository 호출
* 여러 Repository 작업 조합
* 트랜잭션 관리
* 권한 검증
* Entity를 Response DTO로 변환

```java
@Service
@RequiredArgsConstructor
@Transactional(readOnly = true)
public class RoomService {

    private final RoomRepository roomRepository;

    @Transactional
    public RoomResponse createRoom(CreateRoomRequest request) {
        Room room = Room.create(
                request.name(),
                request.description()
        );

        Room savedRoom = roomRepository.save(room);

        return RoomResponse.from(savedRoom);
    }
}
```

데이터를 변경하는 메서드에는 `@Transactional`을 사용한다.

```java
@Transactional
public RoomResponse createRoom(CreateRoomRequest request) {
    // 데이터 생성
}
```

단순 조회 메서드는 클래스에 선언된 `readOnly = true` 설정을 사용한다.

```java
public RoomResponse getRoom(Long roomId) {
    // 데이터 조회
}
```

---

## 4.3 Repository

Repository는 데이터베이스와 통신하는 계층이다.

주요 책임은 다음과 같다.

* Entity 저장
* Entity 조회
* Entity 삭제
* 조건에 맞는 데이터 검색
* 데이터 존재 여부 확인

Spring Data JPA를 사용하면 기본적인 CRUD 메서드를 직접 구현하지 않아도 된다.

```java
public interface RoomRepository
        extends JpaRepository<Room, Long> {
}
```

`JpaRepository`에서 제공하는 대표적인 메서드는 다음과 같다.

| 메서드              | 설명           |
| ---------------- | ------------ |
| `save(entity)`   | Entity 저장    |
| `findById(id)`   | ID로 조회       |
| `findAll()`      | 전체 조회        |
| `existsById(id)` | 데이터 존재 여부 확인 |
| `delete(entity)` | Entity 삭제    |
| `deleteById(id)` | ID를 기준으로 삭제  |

필요한 경우 메서드 이름을 이용해 조회 쿼리를 생성할 수 있다.

```java
List<Room> findAllByCreatedById(Long userId);
```

```java
boolean existsByInviteCode(String inviteCode);
```

# 5. 계층별 책임 분리

각 계층은 자신의 역할에 맞는 코드만 가져야 한다.

| 계층           | 주요 책임            |
| ------------ | ---------------- |
| Controller   | HTTP 요청과 응답 처리   |
| Service      | 비즈니스 로직과 트랜잭션 처리 |
| Repository   | 데이터베이스 접근        |
| Entity       | 데이터와 도메인 상태 관리   |
| Request DTO  | 클라이언트 요청 데이터 전달  |
| Response DTO | 클라이언트 응답 데이터 전달  |

잘못된 구조의 예시는 다음과 같다.

```java
@PostMapping
public Room createRoom(
        @RequestBody Room room
) {
    return roomRepository.save(room);
}
```

이 구조에는 다음과 같은 문제가 있다.

* Controller가 Repository를 직접 호출한다.
* 요청 데이터로 Entity를 직접 사용한다.
* Entity를 API 응답으로 직접 반환한다.
* 비즈니스 로직을 추가하기 어렵다.
* 데이터베이스 구조가 API에 노출된다.
* 생성 가능한 필드를 클라이언트가 임의로 전달할 수 있다.

개선된 구조는 다음과 같다.

```java
@PostMapping
public ResponseEntity<RoomResponse> createRoom(
        @Valid @RequestBody CreateRoomRequest request
) {
    RoomResponse response = roomService.createRoom(request);

    return ResponseEntity
            .status(HttpStatus.CREATED)
            .body(response);
}
```

# 6. Entity와 DTO 분리

## 6.1 Room Entity

Room Entity는 데이터베이스의 방 정보를 표현한다.

```java
@Entity
@Table(name = "rooms")
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class Room {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 50)
    private String name;

    @Column(length = 500)
    private String description;

    @Column(nullable = false, unique = true)
    private String inviteCode;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false)
    private RoomStatus status;

    private LocalDateTime createdAt;

    private LocalDateTime updatedAt;

    private Room(
            String name,
            String description,
            String inviteCode
    ) {
        this.name = name;
        this.description = description;
        this.inviteCode = inviteCode;
        this.status = RoomStatus.ACTIVE;
        this.createdAt = LocalDateTime.now();
        this.updatedAt = LocalDateTime.now();
    }

    public static Room create(
            String name,
            String description,
            String inviteCode
    ) {
        return new Room(name, description, inviteCode);
    }

    public void update(
            String name,
            String description
    ) {
        this.name = name;
        this.description = description;
        this.updatedAt = LocalDateTime.now();
    }

    public void close() {
        this.status = RoomStatus.CLOSED;
        this.updatedAt = LocalDateTime.now();
    }
}
```

Entity의 생성자를 외부에 직접 공개하지 않고 정적 팩토리 메서드를 사용할 수 있다.

```java
Room room = Room.create(
        request.name(),
        request.description(),
        inviteCode
);
```

Entity의 상태는 Setter를 통해 무분별하게 변경하지 않고, 의미가 드러나는 메서드로 변경한다.

```java
room.update(name, description);
room.close();
```

다음과 같은 Setter 사용은 피하는 것이 좋다.

```java
room.setName(name);
room.setDescription(description);
room.setStatus(RoomStatus.CLOSED);
```

---

## 6.2 RoomStatus

방의 상태는 Enum으로 관리한다.

```java
public enum RoomStatus {
    ACTIVE,
    CLOSED
}
```

문자열 대신 Enum을 사용하면 정해진 값만 사용할 수 있다.

JPA에는 문자열 형태로 저장하도록 설정한다.

```java
@Enumerated(EnumType.STRING)
private RoomStatus status;
```

`EnumType.ORDINAL`을 사용하면 데이터베이스에 숫자로 저장된다.

```text
ACTIVE → 0
CLOSED → 1
```

Enum 순서가 변경되면 기존 데이터의 의미가 달라질 수 있으므로 `EnumType.STRING`을 사용하는 것이 안전하다.

---

## 6.3 방 생성 Request DTO

```java
public record CreateRoomRequest(

        @NotBlank(message = "방 이름은 필수입니다.")
        @Size(max = 50, message = "방 이름은 50자 이하여야 합니다.")
        String name,

        @Size(max = 500, message = "방 설명은 500자 이하여야 합니다.")
        String description
) {
}
```

Request DTO는 클라이언트로부터 필요한 값만 받는다.

클라이언트가 다음 값을 직접 지정하게 하면 안 된다.

* 방 ID
* 초대 코드
* 방 상태
* 생성 일시
* 수정 일시
* OWNER 사용자 ID

이러한 값은 서버에서 생성하거나 인증 정보로 결정해야 한다.

---

## 6.4 방 수정 Request DTO

```java
public record UpdateRoomRequest(

        @NotBlank(message = "방 이름은 필수입니다.")
        @Size(max = 50, message = "방 이름은 50자 이하여야 합니다.")
        String name,

        @Size(max = 500, message = "방 설명은 500자 이하여야 합니다.")
        String description
) {
}
```

수정 API에서 모든 값을 필수로 받을 경우 `PUT`에 가까운 방식이 된다.

이번 API에서는 `PATCH`를 사용하지만, MVP에서는 이름과 설명을 한 번에 전달하는 방식으로 단순하게 구현할 수 있다.

추후 부분 수정이 필요하면 각 필드를 선택적으로 받을 수 있다.

## 6.5 Room Response DTO

```java
public record RoomResponse(
        Long roomId,
        String name,
        String description,
        String inviteCode,
        RoomStatus status,
        LocalDateTime createdAt,
        LocalDateTime updatedAt
) {

    public static RoomResponse from(Room room) {
        return new RoomResponse(
                room.getId(),
                room.getName(),
                room.getDescription(),
                room.getInviteCode(),
                room.getStatus(),
                room.getCreatedAt(),
                room.getUpdatedAt()
        );
    }
}
```

Entity를 직접 반환하지 않고 Response DTO로 변환한다.

```java
return RoomResponse.from(room);
```

이를 통해 API에 노출할 필드를 직접 통제할 수 있다.

# 7. Entity를 직접 반환하면 안 되는 이유

Controller에서 Entity를 그대로 반환할 경우 다음 문제가 발생할 수 있다.

## 7.1 데이터베이스 구조 노출

Entity 필드가 그대로 JSON으로 변환된다.

```java
@GetMapping("/{roomId}")
public Room getRoom(@PathVariable Long roomId) {
    return roomRepository.findById(roomId).orElseThrow();
}
```

Entity에 내부 관리용 필드가 추가되면 해당 값도 API에 노출될 수 있다.

---

## 7.2 불필요하거나 민감한 정보 노출

다음과 같은 값이 의도하지 않게 노출될 수 있다.

* 비밀번호 해시
* 삭제 여부
* 내부 상태값
* AI 정답 정보
* 운영용 로그 정보
* 사용자 권한 정보

---

## 7.3 순환 참조 발생

양방향 연관관계를 그대로 JSON으로 변환하면 순환 참조가 발생할 수 있다.

```text
Room
 → RoomMember
   → Room
     → RoomMember
       → Room
```

이로 인해 무한 반복이나 JSON 직렬화 오류가 발생할 수 있다.

---

## 7.4 지연 로딩 문제

JPA Entity를 Controller에서 직렬화할 때 지연 로딩된 연관관계가 추가로 조회될 수 있다.

이로 인해 다음 문제가 발생할 수 있다.

* 예상하지 못한 SQL 실행
* N+1 문제
* 트랜잭션 종료 후 지연 로딩 오류
* 과도한 데이터 응답

---

## 7.5 API와 데이터베이스의 강한 결합

Entity 필드명이 변경되면 API 응답 형식도 같이 변경될 수 있다.

Response DTO를 사용하면 데이터베이스 구조와 API 응답 구조를 독립적으로 관리할 수 있다.

# 8. 의존성 주입

의존성 주입은 객체가 필요한 의존 객체를 직접 생성하지 않고 외부에서 전달받는 방식이다.

다음 코드는 Service가 Repository를 직접 생성하는 잘못된 예시이다.

```java
public class RoomService {

    private final RoomRepository roomRepository
            = new RoomRepository();
}
```

Spring에서는 Repository 객체를 Bean으로 등록하고 Service에 주입한다.

```java
@Service
@RequiredArgsConstructor
public class RoomService {

    private final RoomRepository roomRepository;
}
```

`@RequiredArgsConstructor`는 `final` 필드에 대한 생성자를 자동으로 생성한다.

실제로는 다음 코드와 같은 역할을 한다.

```java
@Service
public class RoomService {

    private final RoomRepository roomRepository;

    public RoomService(RoomRepository roomRepository) {
        this.roomRepository = roomRepository;
    }
}
```

---

## 8.1 생성자 주입을 사용하는 이유

생성자 주입의 장점은 다음과 같다.

* 의존성을 명확하게 확인할 수 있다.
* 객체 생성 시 필요한 의존성이 반드시 전달된다.
* `final` 필드를 사용할 수 있다.
* 테스트에서 가짜 객체를 전달하기 쉽다.
* 순환 의존성을 빠르게 발견할 수 있다.
* 필드 주입보다 Spring Framework에 대한 의존이 적다.

다음과 같은 필드 주입은 피하는 것이 좋다.

```java
@Autowired
private RoomRepository roomRepository;
```

생성자 주입 방식은 다음과 같다.

```java
private final RoomRepository roomRepository;

public RoomService(RoomRepository roomRepository) {
    this.roomRepository = roomRepository;
}
```

Lombok을 사용할 경우 다음과 같이 작성한다.

```java
@RequiredArgsConstructor
public class RoomService {

    private final RoomRepository roomRepository;
}
```

# 9. 패키지 구조

Qurie 백엔드는 기능 중심 패키지 구조를 사용한다.

```text
m.qurie
├─ auth
├─ user
├─ room
├─ document
├─ quiz
├─ ai
├─ report
├─ websocket
└─ global
   ├─ config
   ├─ exception
   ├─ response
   └─ security
```

기능 중심 패키지 구조는 비즈니스 기능별로 관련 코드를 한곳에 모은다.

예를 들어 `room` 패키지는 다음과 같이 구성할 수 있다.

```text
room
├─ controller
│  └─ RoomController.java
├─ service
│  └─ RoomService.java
├─ repository
│  └─ RoomRepository.java
├─ entity
│  ├─ Room.java
│  └─ RoomStatus.java
└─ dto
   ├─ request
   │  ├─ CreateRoomRequest.java
   │  └─ UpdateRoomRequest.java
   └─ response
      ├─ RoomResponse.java
      └─ RoomListResponse.java
```

전체 구조는 다음과 같이 구성할 수 있다.

```text
m.qurie
├─ QurieApplication.java
│
├─ auth
│  ├─ controller
│  ├─ service
│  └─ dto
│
├─ user
│  ├─ controller
│  ├─ service
│  ├─ repository
│  ├─ entity
│  └─ dto
│
├─ room
│  ├─ controller
│  ├─ service
│  ├─ repository
│  ├─ entity
│  └─ dto
│
├─ document
│  ├─ controller
│  ├─ service
│  ├─ repository
│  ├─ entity
│  └─ dto
```

## 9.1 기능 중심 패키지의 장점

기능 중심 패키지의 장점은 다음과 같다.

* 하나의 기능과 관련된 코드를 빠르게 찾을 수 있다.
* 기능별 책임이 명확하다.
* 프로젝트 규모가 커져도 관리하기 쉽다.
* 기능 단위 수정과 삭제가 쉽다.
* 팀원이 기능별로 작업을 나누기 쉽다.

다음과 같이 모든 계층을 최상위로 분리하는 구조도 가능하다.


Qurie는 `room`, `document`, `quiz`, `ai` 등 도메인이 명확하므로 기능 중심 패키지 구조가 적절하다.

# 11. REST API 설계

방 CRUD API는 다음과 같이 구성한다.

```http
POST   /api/rooms
GET    /api/rooms
GET    /api/rooms/{roomId}
PATCH  /api/rooms/{roomId}
DELETE /api/rooms/{roomId}
```

각 HTTP 메서드의 의미는 다음과 같다.

| HTTP 메서드 | 의미         |
| -------- | ---------- |
| `POST`   | 새로운 리소스 생성 |
| `GET`    | 리소스 조회     |
| `PUT`    | 리소스 전체 교체  |
| `PATCH`  | 리소스 일부 수정  |
| `DELETE` | 리소스 삭제     |

REST API의 URL에는 행위보다 리소스를 표현하는 것이 좋다.

좋은 예시는 다음과 같다.

```http
POST /api/rooms
PATCH /api/rooms/1
DELETE /api/rooms/1
```

다음과 같이 URL에 행위를 포함하는 방식은 가급적 피한다.

```http
POST /api/createRoom
POST /api/updateRoom
POST /api/deleteRoom
```

HTTP 메서드 자체가 행위를 나타내므로 URL은 `rooms`라는 리소스를 중심으로 구성한다.

# 12. HTTP 상태 코드

REST API에서는 처리 결과에 맞는 HTTP 상태 코드를 반환해야 한다.

## 12.1 성공 상태 코드

| 상태 코드 | 이름         | 사용 상황          |
| ----- | ---------- | -------------- |
| `200` | OK         | 조회 및 수정 성공     |
| `201` | Created    | 새로운 리소스 생성 성공  |
| `204` | No Content | 응답 본문 없이 삭제 성공 |

방 CRUD에서는 다음과 같이 사용할 수 있다.

```text
POST   /api/rooms          → 201 Created
GET    /api/rooms          → 200 OK
GET    /api/rooms/{id}     → 200 OK
PATCH  /api/rooms/{id}     → 200 OK
DELETE /api/rooms/{id}     → 204 No Content
```

---

## 12.2 클라이언트 오류 상태 코드

| 상태 코드 | 이름           | 사용 상황       |
| ----- | ------------ | ----------- |
| `400` | Bad Request  | 요청 값 검증 실패  |
| `401` | Unauthorized | 인증되지 않은 사용자 |
| `403` | Forbidden    | 권한이 없는 사용자  |
| `404` | Not Found    | 존재하지 않는 리소스 |
| `409` | Conflict     | 중복 또는 상태 충돌 |

예시는 다음과 같다.

```text
방 이름이 비어 있음
→ 400 Bad Request
```

```text
로그인하지 않고 방 생성 요청
→ 401 Unauthorized
```

```text
MEMBER가 방 정보를 수정
→ 403 Forbidden
```

```text
존재하지 않는 roomId 조회
→ 404 Not Found
```

```text
이미 참여한 방에 다시 참여
→ 409 Conflict
```

---

## 12.3 서버 오류 상태 코드

| 상태 코드 | 이름                    | 사용 상황              |
| ----- | --------------------- | ------------------ |
| `500` | Internal Server Error | 처리되지 않은 서버 오류      |
| `502` | Bad Gateway           | 외부 AI API 응답 오류    |
| `503` | Service Unavailable   | 외부 서비스 또는 서버 사용 불가 |

예상 가능한 비즈니스 오류는 `500`으로 처리하지 않고 적절한 상태 코드로 반환해야 한다.

```java

```

다만 새로운 Entity를 생성할 때는 `save()`가 필요하다.

## 13.5 방 삭제

실제 데이터를 삭제하지 않고 방 상태를 `CLOSED`로 변경하는 방식을 사용할 수 있다.

### API

```http
DELETE /api/rooms/{roomId}
```

### Controller

```java
@DeleteMapping("/{roomId}")

        @PathVariable Long roomId
) {
    roomService.closeRoom(roomId);

    return ResponseEntity.noContent().build();
}
```

### Service

```java
@Transactional
public void closeRoom(Long roomId) {
    Room room = findRoom(roomId);

    room.close();
}
```

방을 실제로 삭제하지 않는 이유는 다음과 같다.

* 코드 문서 이력을 보존할 수 있다.
* 퀴즈 응시 결과를 유지할 수 있다.
* 실수로 삭제된 방을 복구할 수 있다.
* 감사 및 운영 기록을 유지할 수 있다.

초기 구현에서는 API 이름은 `DELETE`를 사용하지만 내부적으로는 소프트 삭제를 수행한다.

# 15. RoomService 전체 예시

```java
@Service
@RequiredArgsConstructor
@Transactional(readOnly = true)
public class RoomService {

    private final RoomRepository roomRepository;
    private final InviteCodeGenerator inviteCodeGenerator;

    @Transactional
    public RoomResponse createRoom(
            CreateRoomRequest request
    ) {
        String inviteCode =
                inviteCodeGenerator.generate();

        Room room = Room.create(
                request.name(),
                request.description(),
                inviteCode
        );

        Room savedRoom = roomRepository.save(room);

        return RoomResponse.from(savedRoom);
    }

    public List<RoomResponse> getRooms() {
        return roomRepository.findAll()
                .stream()
                .map(RoomResponse::from)
                .toList();
    }

    public RoomResponse getRoom(Long roomId) {
        Room room = findRoom(roomId);

        return RoomResponse.from(room);
    }

    @Transactional
    public RoomResponse updateRoom(
            Long roomId,
            UpdateRoomRequest request
    ) {
        Room room = findRoom(roomId);

        room.update(
                request.name(),
                request.description()
        );

        return RoomResponse.from(room);
    }

    @Transactional
    public void closeRoom(Long roomId) {
        Room room = findRoom(roomId);

        room.close();
    }

    private Room findRoom(Long roomId) {
        return roomRepository.findById(roomId)
                .orElseThrow(() ->
                        new RoomNotFoundException(roomId)
                );
    }
}
```

* 방 이름과 설명이 정상적으로 변경되는지 확인
* 수정 시간이 갱신되는지 확인
* 존재하지 않는 방 수정 시 `404`가 반환되는지 확인
* 잘못된 요청 값에 `400`이 반환되는지 확인

---

## 19.5 방 삭제

```http
DELETE /api/rooms/{roomId}
```

확인할 내용은 다음과 같다.

* 상태 코드가 `204 No Content`인지 확인
* 응답 본문이 없는지 확인
* 데이터가 실제 삭제되는 대신 `CLOSED` 상태로 변경되는지 확인
* 존재하지 않는 방 삭제 시 `404`가 반환되는지 확인

# 20. API 응답 형식

프로젝트 전체에서 일관된 응답 형식을 사용하려면 공통 응답 객체를 사용할 수 있다.

```java
public record ApiResponse<T>(
        boolean success,
        T data
) {

    public static <T> ApiResponse<T> success(T data) {
        return new ApiResponse<>(true, data);
    }
}
```

응답은 다음과 같이 반환된다.

```json
{
  "success": true,
  "data": {
    "roomId": 1,
    "name": "Qurie Backend Study",
    "status": "ACTIVE"
  }
}
```

Controller에서는 다음과 같이 사용할 수 있다.

```java
@PostMapping
public ResponseEntity<ApiResponse<RoomResponse>>
createRoom(
        @Valid @RequestBody CreateRoomRequest request
) {
    RoomResponse response =
            roomService.createRoom(request);

    return ResponseEntity
            .status(HttpStatus.CREATED)
            .body(ApiResponse.success(response));
}
```

다만 초기 MVP에서는 불필요하게 구조를 복잡하게 만들지 않기 위해 Response DTO를 직접 반환하고, 이후 팀의 API 응답 규칙에 따라 공통 응답 객체를 도입할 수 있다.

# 21. 구현하면서 중요하다고 느낀 점

## 21.1 Controller는 요청과 응답에 집중해야 한다

Controller에서 데이터 조회, Entity 생성, 권한 검증 등의 비즈니스 로직을 직접 수행하면 코드가 복잡해진다.

Controller는 다음 역할만 수행하도록 구성해야 한다.

```text
요청 수신
→ 요청 검증
→ Service 호출
→ HTTP 응답 반환
```

---

## 21.2 Service가 비즈니스 규칙의 중심이다

방 생성, 수정, 종료와 같은 규칙은 Service에서 관리해야 한다.

추후 OWNER 권한 검증이 추가되면 다음과 같이 처리할 수 있다.

```java
@Transactional
public RoomResponse updateRoom(
        Long roomId,
        Long currentUserId,
        UpdateRoomRequest request
) {
    validateOwner(roomId, currentUserId);

    Room room = findRoom(roomId);

    room.update(
            request.name(),
            request.description()
    );

    return RoomResponse.from(room);
}
```

---

## 21.3 Entity와 API 모델은 분리해야 한다

Entity는 데이터베이스와 도메인 모델을 위한 객체이고, DTO는 외부 요청과 응답을 위한 객체이다.

두 객체를 분리하면 다음 장점이 있다.

* 요청 가능한 필드를 통제할 수 있다.
* 응답에 노출되는 필드를 통제할 수 있다.
* Entity의 연관관계가 API에 영향을 주지 않는다.
* API 명세 변경과 데이터베이스 변경을 분리할 수 있다.

---

## 21.4 의존성은 직접 생성하지 않는다

Spring이 관리하는 객체를 `new`로 직접 생성하면 의존성 주입과 Bean 관리의 장점을 활용할 수 없다.

```java
RoomService roomService = new RoomService();
```

Controller에서는 생성자 주입으로 Service를 전달받아야 한다.

```java
@RequiredArgsConstructor
public class RoomController {

    private final RoomService roomService;
}
```

---

## 21.5 데이터 변경에는 트랜잭션이 필요하다

방 생성, 수정, 종료는 데이터베이스 상태를 변경하므로 `@Transactional`이 필요하다.

```java
@Transactional
public RoomResponse createRoom(...) {
}
```

조회 전용 작업에는 다음 설정을 사용할 수 있다.

```java
@Transactional(readOnly = true)
public class RoomService {
}
```

---

## 21.6 HTTP 상태 코드는 처리 결과를 표현한다

모든 성공 응답에 `200 OK`만 사용하는 것이 아니라 작업 결과에 맞는 상태 코드를 사용해야 한다.

```text
생성 성공 → 201
조회 성공 → 200
수정 성공 → 200
삭제 성공 → 204
잘못된 요청 → 400
인증 실패 → 401
권한 부족 → 403
리소스 없음 → 404
상태 충돌 → 409
```

# 22. 추가로 결정해야 할 사항

다음 내용은 이후 인증과 권한 기능을 구현하면서 결정해야 한다.

* 방 목록에서 현재 사용자가 참여한 방만 조회할 것인가

* 방 이름의 중복을 허용할 것인가

* 초대 코드의 유효기간을 설정할 것인가

* 목록 조회에 페이지네이션을 적용할 것인가
* 공통 API 응답 객체를 사용할 것인가
* 생성일과 수정일을 직접 관리할 것인가
* JPA Auditing을 사용할 것인가

# 23. 이후 개선 방향

## 23.1 BaseTimeEntity 도입

생성일과 수정일을 공통 Entity로 분리할 수 있다.

```java
@Getter
@MappedSuperclass
@EntityListeners(AuditingEntityListener.class)
public abstract class BaseTimeEntity {

    @CreatedDate
    @Column(updatable = false)
    private LocalDateTime createdAt;

    @LastModifiedDate
    private LocalDateTime updatedAt;
}
```

Room Entity는 다음과 같이 상속받는다.

```java
@Entity
public class Room extends BaseTimeEntity {
}
```

JPA Auditing을 활성화한다.

```java
@EnableJpaAuditing
@SpringBootApplication
public class QurieApplication {

    public static void main(String[] args) {
        SpringApplication.run(
                QurieApplication.class,
                args
        );
    }
}
```

---

## 23.2 인증 사용자 적용

현재는 사용자 인증 기능이 없으므로 방 생성자를 임시 처리할 수 있다.

인증 기능이 추가되면 다음 데이터가 자동으로 설정되어야 한다.

```text
현재 로그인 사용자
→ Room 생성자
→ RoomMember OWNER
```

방 생성은 하나의 트랜잭션 안에서 다음 두 작업을 수행해야 한다.

```text
Room 저장
    ↓
RoomMember를 OWNER 역할로 저장
```

---

## 23.3 페이지네이션 적용

방이 많아지면 모든 방을 한 번에 조회하면 안 된다.

```http
GET /api/rooms?page=0&size=20
```

Spring Data의 `Pageable`을 사용할 수 있다.

```java
@GetMapping
public Page<RoomResponse> getRooms(
        Pageable pageable
) {
    return roomService.getRooms(pageable);
}
```

# 24. 오늘 학습한 내용 요약

오늘은 Qurie 백엔드의 Spring Boot 프로젝트 구조를 설계하고 방 CRUD API를 구현하는 흐름을 학습했다.

주요 학습 내용은 다음과 같다.

1. HTTP 요청은 Controller, Service, Repository 순서로 처리된다.
2. Controller는 요청과 응답을 처리하고 비즈니스 로직은 Service에 작성한다.
3. Repository는 데이터베이스 접근을 담당한다.
4. Entity는 데이터베이스와 도메인 상태를 표현한다.
5. Request DTO는 클라이언트 요청 값을 전달한다.
6. Response DTO는 클라이언트에 필요한 값만 반환한다.
7. Entity를 Controller에서 직접 반환하면 내부 정보 노출과 순환 참조 문제가 발생할 수 있다.
8. 의존성은 생성자 주입 방식을 사용하는 것이 적절하다.
9. Qurie 프로젝트는 기능 중심 패키지 구조를 사용한다.
10. 공통 설정, 예외, 응답, 보안 코드는 `global` 패키지에서 관리한다.
11. REST API는 URL에 리소스를 표현하고 HTTP 메서드로 행위를 구분한다.
12. 작업 결과에 맞는 HTTP 상태 코드를 반환해야 한다.
13. 데이터 변경 메서드는 트랜잭션 안에서 실행해야 한다.
14. Swagger를 통해 API 명세를 확인하고 직접 요청을 테스트할 수 있다.
15. 방 삭제는 데이터 보존을 위해 `CLOSED` 상태로 변경하는 소프트 삭제 방식을 사용할 수 있다.

# 트러블슈팅 — 세션 리포트 일괄 발급 (동기 순차 처리 → 비동기 병렬 전환)

> 자기소개서·면접용 STAR 정리. 측정 원본은 `loadtest/RESULTS.md` 시나리오 04, 코드는 `fix/kts/report-bulk-async` 브랜치.

---

## 요약 (자소서 붙여넣기용, 4문장)

개발 단계에서 1~2명으로 테스트할 때는 정상이던 세션 리포트 일괄 발급이, 시연에서 학생 5명이 참여하자 오류가 발생했습니다. 부하 테스트로 재현해 보니 원인은 두 가지였습니다 — 학생 수만큼 AI 호출을 요청 안에서 순차로 기다리는 동기 구조가 게이트웨이 타임아웃(30초)을 넘겼고, 오류를 본 사용자가 재클릭하면 아직 실행 중인 발급과 겹치면서 delete→insert 방식의 저장 로직이 유니크 제약 위반(500)과 AI 중복 과금을 일으켰습니다. 이를 202 즉시 응답의 비동기 접수 구조로 바꾸고 학생별 AI 호출을 전용 스레드풀로 병렬화(동시 6)했으며, 저장을 upsert로 바꾸고 진행 중 가드를 두어 중복 요청을 409로 거절하게 했습니다. 그 결과 동일 조건 재측정에서 30명 기준 응답 시간이 93초에서 0.1초로, 전원 발급 완료가 93초에서 16.6초로 줄었고, 동시 요청 10발에서 500 오류 4건·중복 AI 호출 10회가 모두 0건·1회가 되었습니다.

---

## S — Situation (상황)

- AI 퀴즈 기반 실시간 코딩 교육 플랫폼 **Qurie**에서, 강사가 세션 종료 후 학생 전원의 학습 리포트를 일괄 발급하는 기능을 담당했다.
- 리포트마다 정량 지표는 서버가 DB에서 집계하고, 정성 코멘트(총평·강점·보완점)는 **학생 1명당 LLM 1회 호출**로 생성한다.
- **개발 중 1~2명 테스트에서는 아무 문제가 없었다.** 그런데 시연에서 학생 5명이 참여한 세션의 리포트를 발급하자 화면에 오류가 떴고, 당황한 상태로 재클릭하자 이번에는 서버 500 오류까지 발생했다.

## T — Task (과제)

- 시연에서만 재현되는 원인을 규명하고, 서비스 목표 규모인 **한 반 30명**에서도 안정적으로 동작하도록 개선해야 했다.
- "고쳤다"가 아니라 **같은 조건의 측정으로 개선을 수치 검증**하는 것까지를 목표로 잡았다 (이전 N+1 개선 때 확립한 팀 측정 규칙).

## A — Action (행동)

**1. 결정적으로 재현했다.**
- LLM 응답 시간이 회차마다 달라 측정이 오염되는 것을 막기 위해, **지연 3초 고정 + 동시 처리 수를 로그로 남기는 목(mock) AI 서버**를 만들어 원인 변수를 통제했다.
- k6로 두 시나리오를 스크립트화했다 — ① 일괄 발급 소요 시간(bulk), ② 같은 학생 동시 발급 10발(race).

**2. 원인을 두 층으로 규명했다.**
- **1차 — 동기 + 순차 구조**: 일괄 발급이 `for` 루프에서 학생마다 AI 호출을 끝날 때까지 기다렸다. 측정 결과 5명 16.7초, 30명 93초. 배포 경로의 CloudFront는 오리진 응답을 30초까지만 기다리므로, **서버는 정상 동작 중인데 사용자에게는 504가 먼저 도착**했다. 1~2명(3~7초)에서는 절대 드러나지 않는 구조였다.
- **2차 — 재클릭 레이스**: 오류를 본 강사가 재클릭하면 아직 실행 중인 첫 발급과 겹친다. 재발급 로직이 delete→insert 방식인데 집계와 저장 사이에 AI 호출(수 초)이 끼어 있어, 겹친 두 요청이 모두 "지울 것 없음 → insert" 경로를 타면서 **(session_id, ordinary_user_id) 유니크 제약 위반으로 500**이 났다. 측정으로 확인하니 동시 10발에서 500이 4건, 같은 리포트에 AI 호출이 10번(과금 10배) 나갔다.

**3. 세 가지를 고쳤다.**
- **비동기 접수**: 일괄 발급을 202 즉시 응답으로 바꾸고, 실제 발급은 전용 스레드풀에서 백그라운드로 처리. 완료는 앱 알림으로 강사에게 전달 — 게이트웨이 타임아웃 문제가 구조적으로 사라진다.
- **병렬화**: 학생별 발급을 `CompletableFuture`로 병렬 처리하되 **동시 6으로 제한** — 병목이 LLM 왕복이라 그 이상은 이득이 없고, DB 커넥션 풀(기본 10)과 LLM 게이트웨이 rate limit을 함께 보호해야 하기 때문이다.
- **레이스 제거**: delete→insert를 같은 행을 덮어쓰는 update(upsert)로 교체하고, (세션, 학생) 단위 진행 중 가드를 두어 겹친 요청을 500이 아닌 **409(이미 진행 중)** 로 명확히 거절.

**4. 같은 조건으로 재측정해 검증했다.** 단위 테스트도 새 계약(202 접수·upsert)에 맞춰 갱신했다.

## R — Result (결과)

| 지표 | 개선 전 | 개선 후 |
|---|---|---|
| 일괄 발급 HTTP 응답 (30명) | 93초 → **게이트웨이 504** | **0.1초** (202 접수) |
| 전원 발급 완료 (30명) | 93초 | **16.6초 (−82%)** |
| 전원 발급 완료 (5명) | 16.7초 | 4.4초 |
| 동시 발급 10발 — 서버 오류 | 500 × 4건 | **0건** (1건 성공 + 9건 409) |
| 동시 발급 10발 — AI 호출 | 10회 (중복 과금) | **1회** |
| AI 동시 처리 (목 서버 로그) | 최대 1 (순차) | 최대 6 (설계값과 일치) |

- 시연을 재현한 5명 조건은 물론, 목표 규모 30명에서도 사용자는 0.1초 안에 접수 확인을 받고, 리포트는 백그라운드에서 순차 대비 6배 빠르게 완성된다.
- 중복 요청이 500이 아닌 409로 떨어지므로 프론트가 "이미 발급 중" 안내를 보여줄 수 있게 됐고, LLM 중복 과금이 사라졌다.

## 배운 점

1. **"1명에서 되는 것"과 "N명에서 되는 것"은 다른 기능이다.** 처리 시간이 인원수에 비례하는 구조는 게이트웨이 타임아웃이라는 외부 한계와 만나는 순간 갑자기 무너진다. 부하 조건을 바꿔가며 테스트해야 이런 구조적 결함이 보인다.
2. **오류는 연쇄로 온다.** 1차 오류(타임아웃)가 사용자 행동(재클릭)을 유발하고, 그 행동이 2차 오류(레이스)를 깨운다. 첫 오류만 고치면 두 번째가 남는다 — 사용자 행동까지 포함해 시나리오를 재현해야 한다.
3. **측정 변수를 통제하면 인과가 명확해진다.** LLM 지연을 3초로 고정한 목 서버 덕분에 "구조 변경의 효과"만 분리해 측정할 수 있었고, 동시 처리 수 로그(1→6)가 병렬화의 직접 증거가 됐다.
4. **병렬화는 "몇 개까지"가 설계다.** 스레드를 무한정 늘리는 게 아니라 병목(LLM)·커넥션 풀·외부 rate limit을 근거로 동시 6을 정했다 — 숫자에 근거가 있어야 면접에서도 방어된다.

## 부록 — 재측정 명령 (검증 재현용)

```bash
# 개선 후 일괄 발급 (202 접수 + 완료 폴링)
k6 run -e BASE_URL=http://localhost:8080 -e SESSION_ID=6 -e INSTRUCTOR_EMAIL=teacher@test.com -e EXPECTED_REPORTS=30 loadtest/04-report.js

# 동시 발급 레이스 (기대: 1건 201 + 9건 409, 5xx 0건)
k6 run -e BASE_URL=http://localhost:8080 -e SESSION_ID=6 -e INSTRUCTOR_EMAIL=teacher@test.com -e MODE=race -e STUDENT_ID=36 -e RACE_VUS=10 loadtest/04-report.js
```

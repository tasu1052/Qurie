# HTTP와 브라우저 동작 원리 정리

## 1. HTTP란?

**HTTP(Hypertext Transfer Protocol)**는 클라이언트와 서버가 웹상에서 데이터를 주고받기 위해 사용하는 애플리케이션 계층 프로토콜이다.

웹 브라우저가 HTML 문서, 이미지, 동영상, JSON 데이터 등을 서버에 요청하고 응답받을 때 주로 사용된다.

```text
클라이언트 요청 → 서버
클라이언트 ← 서버 응답
```

예를 들어 브라우저가 서버에 사용자 목록을 요청하면 다음과 같은 형태로 통신한다.

```http
GET /users HTTP/1.1
Host: example.com
```

서버는 요청을 처리한 뒤 상태 코드, 헤더, 본문을 포함한 응답을 반환한다.

```http
HTTP/1.1 200 OK
Content-Type: application/json

[
  {
    "id": 1,
    "name": "Kim"
  }
]
```

---

## 2. HTTP의 작동 원리

HTTP는 기본적으로 **클라이언트-서버 구조**로 동작한다.

### 클라이언트

서버에 필요한 자원이나 작업을 요청하는 주체이다.

대표적인 클라이언트는 다음과 같다.

* 웹 브라우저
* 모바일 애플리케이션
* 프론트엔드 애플리케이션
* Postman
* 다른 서버 애플리케이션

### 서버

클라이언트의 요청을 받아 처리한 뒤 결과를 응답하는 주체이다.

예를 들어 다음과 같은 작업을 수행할 수 있다.

* HTML 문서 반환
* 데이터베이스 조회
* 회원가입 처리
* 파일 전송
* 인증 및 권한 검사

HTTP 통신의 기본 흐름은 다음과 같다.

```text
1. 클라이언트가 서버에 HTTP 요청을 보낸다.
2. 서버가 요청을 분석한다.
3. 서버가 필요한 작업을 수행한다.
4. 서버가 HTTP 응답을 반환한다.
5. 클라이언트가 응답을 처리한다.
```

---

## 3. HTTP 요청의 구조

HTTP 요청은 일반적으로 다음과 같이 구성된다.

```text
요청 라인
요청 헤더
빈 줄
요청 본문
```

예시:

```http
POST /users HTTP/1.1
Host: example.com
Content-Type: application/json
Authorization: Bearer token-value

{
  "name": "Kim",
  "email": "kim@example.com"
}
```

### 요청 라인

```http
POST /users HTTP/1.1
```

요청 라인에는 다음 정보가 포함된다.

* HTTP 메서드: `POST`
* 요청 경로: `/users`
* HTTP 버전: `HTTP/1.1`

### 요청 헤더

요청에 대한 부가 정보를 전달한다.

```http
Content-Type: application/json
Authorization: Bearer token-value
```

대표적인 요청 헤더는 다음과 같다.

| 헤더              | 역할                   |
| --------------- | -------------------- |
| `Host`          | 요청을 보내는 서버의 도메인      |
| `Content-Type`  | 요청 본문의 데이터 형식        |
| `Authorization` | 인증 정보                |
| `Cookie`        | 브라우저에 저장된 쿠키         |
| `Accept`        | 클라이언트가 받을 수 있는 응답 형식 |
| `User-Agent`    | 브라우저 및 클라이언트 정보      |

### 요청 본문

서버에 전달할 실제 데이터를 담는다.

주로 `POST`, `PUT`, `PATCH` 요청에서 사용된다.

```json
{
  "name": "Kim",
  "email": "kim@example.com"
}
```

## 4. HTTP 응답의 구조

HTTP 응답은 일반적으로 다음과 같이 구성된다.

```text
상태 라인
응답 헤더
빈 줄
응답 본문
```

예시:

```http
HTTP/1.1 200 OK
Content-Type: application/json
Set-Cookie: sessionId=abc123; HttpOnly

{
  "message": "요청이 성공했습니다."
}
```

### 상태 라인

```http
HTTP/1.1 200 OK
```

상태 라인에는 다음 정보가 포함된다.

* HTTP 버전
* 상태 코드
* 상태 메시지

### 응답 헤더

응답과 관련된 부가 정보를 전달한다.

| 헤더               | 역할            |
| ---------------- | ------------- |
| `Content-Type`   | 응답 본문의 데이터 형식 |
| `Content-Length` | 응답 본문의 크기     |
| `Set-Cookie`     | 브라우저에 저장할 쿠키  |
| `Cache-Control`  | 캐시 사용 정책      |
| `Location`       | 리다이렉션할 주소     |

### 응답 본문

클라이언트에게 전달하는 실제 데이터이다.

다음과 같은 데이터가 포함될 수 있다.

* HTML
* JSON
* 이미지
* 동영상
* 파일
* 오류 메시지

---

## 5. HTTP 메서드

HTTP 메서드는 클라이언트가 서버에 어떤 작업을 요청하는지 나타낸다.

| 메서드       | 주요 역할           | 예시           |
| --------- | --------------- | ------------ |
| `GET`     | 자원 조회           | 사용자 목록 조회    |
| `POST`    | 자원 생성 또는 작업 수행  | 회원가입         |
| `PUT`     | 자원 전체 수정 또는 교체  | 사용자 정보 전체 수정 |
| `PATCH`   | 자원 일부 수정        | 닉네임만 수정      |
| `DELETE`  | 자원 삭제           | 사용자 삭제       |
| `HEAD`    | 본문 없이 헤더만 조회    | 파일 정보 확인     |
| `OPTIONS` | 서버가 지원하는 메서드 확인 | CORS 사전 요청   |

---

### 5.1 GET

서버의 자원을 조회할 때 사용한다.

```http
GET /users/1
```

일반적으로 요청 본문을 사용하지 않고 URL이나 쿼리 파라미터로 조건을 전달한다.

```http
GET /users?page=1&size=10
```

---

### 5.2 POST

새로운 자원을 생성하거나 특정 작업을 실행할 때 사용한다.

```http
POST /users
```

```json
{
  "name": "Kim"
}
```

POST는 반드시 생성에만 사용되는 것은 아니다.

예를 들어 로그인, 결제, 검색 처리 등 서버의 특정 동작을 실행할 때도 사용할 수 있다.

---

### 5.3 PUT

자원의 전체 내용을 교체하거나 수정할 때 사용한다.

```http
PUT /users/1
```

```json
{
  "name": "Kim",
  "email": "new@example.com",
  "age": 26
}
```

일반적으로 해당 자원의 전체 필드를 전달하는 방식으로 사용한다.

---

### 5.4 PATCH

자원의 일부만 수정할 때 사용한다.

```http
PATCH /users/1
```

```json
{
  "nickname": "taesu"
}
```

---

### 5.5 DELETE

자원을 삭제할 때 사용한다.

```http
DELETE /users/1
```

---

## 6. HTTP 메서드의 속성

HTTP 메서드는 안전성, 멱등성, 캐시 가능성 등의 특징을 가진다.

### 6.1 안전성

요청을 수행해도 서버의 자원 상태가 변경되지 않는 성질이다.

대표적으로 `GET`, `HEAD`는 안전한 메서드이다.

```text
GET /users/1
```

단순 조회이므로 사용자 데이터가 변경되지 않는다.

---

### 6.2 멱등성

같은 요청을 여러 번 수행해도 최종 결과가 동일한 성질이다.

예를 들어 다음 요청을 여러 번 보내더라도 최종적으로 사용자는 삭제된 상태이다.

```http
DELETE /users/1
```

대표적인 멱등 메서드는 다음과 같다.

* GET
* PUT
* DELETE

POST는 일반적으로 멱등하지 않다.

예를 들어 같은 결제 요청을 여러 번 보내면 결제가 중복될 수 있다.

---

## 7. HTTP 상태 코드

HTTP 상태 코드는 서버가 요청을 어떻게 처리했는지 나타내는 세 자리 숫자이다.

---

### 7.1 1xx: 정보 응답

요청을 받았으며 처리가 계속 진행 중임을 의미한다.

| 상태 코드                     | 의미                    |
| ------------------------- | --------------------- |
| `100 Continue`            | 요청의 나머지 내용을 계속 전송해도 됨 |
| `101 Switching Protocols` | 다른 프로토콜로 전환           |

`101 Switching Protocols`는 WebSocket 연결을 시작할 때 사용될 수 있다.

---

### 7.2 2xx: 성공

서버가 요청을 정상적으로 처리했음을 의미한다.

| 상태 코드            | 의미                     |
| ---------------- | ---------------------- |
| `200 OK`         | 요청 성공                  |
| `201 Created`    | 새로운 자원 생성 성공           |
| `202 Accepted`   | 요청은 접수했지만 처리가 완료되지는 않음 |
| `204 No Content` | 요청은 성공했지만 응답 본문이 없음    |

예를 들어 회원가입에 성공하면 `201 Created`를 사용할 수 있다.

---

### 7.3 3xx: 리다이렉션

요청을 완료하려면 클라이언트가 추가 작업을 해야 함을 의미한다.

| 상태 코드                    | 의미                |
| ------------------------ | ----------------- |
| `301 Moved Permanently`  | 자원이 영구적으로 이동      |
| `302 Found`              | 자원이 임시로 다른 위치에 있음 |
| `304 Not Modified`       | 캐시된 자원을 그대로 사용 가능 |
| `307 Temporary Redirect` | 요청 메서드를 유지한 임시 이동 |
| `308 Permanent Redirect` | 요청 메서드를 유지한 영구 이동 |

예를 들어 HTTP 요청을 HTTPS로 변경할 때 리다이렉션을 사용할 수 있다.

---

### 7.4 4xx: 클라이언트 오류

클라이언트가 보낸 요청에 문제가 있음을 의미한다.

| 상태 코드                        | 의미               |
| ---------------------------- | ---------------- |
| `400 Bad Request`            | 요청 형식이나 값이 잘못됨   |
| `401 Unauthorized`           | 인증이 필요함          |
| `403 Forbidden`              | 인증은 되었지만 권한이 없음  |
| `404 Not Found`              | 요청한 자원을 찾을 수 없음  |
| `405 Method Not Allowed`     | 지원하지 않는 HTTP 메서드 |
| `409 Conflict`               | 요청이 현재 자원 상태와 충돌 |
| `415 Unsupported Media Type` | 지원하지 않는 데이터 형식   |
| `429 Too Many Requests`      | 너무 많은 요청을 보냄     |

`401 Unauthorized`라는 이름과 달리 실제로는 주로 **인증되지 않은 상태**를 의미한다.

`403 Forbidden`은 사용자가 누구인지는 확인되었지만 해당 자원에 접근할 권한이 없는 경우에 사용한다.

---

### 7.5 5xx: 서버 오류

클라이언트의 요청은 유효하지만 서버 내부 문제로 처리할 수 없음을 의미한다.

| 상태 코드                       | 의미                       |
| --------------------------- | ------------------------ |
| `500 Internal Server Error` | 서버 내부 오류                 |
| `502 Bad Gateway`           | 게이트웨이가 잘못된 응답을 받음        |
| `503 Service Unavailable`   | 서버가 일시적으로 요청을 처리할 수 없음   |
| `504 Gateway Timeout`       | 게이트웨이가 제한 시간 내 응답을 받지 못함 |

---

## 8. HTTP의 특징

### 8.1 클라이언트-서버 구조

클라이언트는 요청을 보내고 서버는 요청을 처리하여 응답한다.

클라이언트와 서버의 역할을 분리하면 각각 독립적으로 개발하고 확장하기 쉽다.

---

### 8.2 무상태성

**무상태성(Stateless)**은 서버가 이전 요청의 상태를 기본적으로 기억하지 않는다는 의미이다.

예를 들어 사용자가 다음 요청을 보냈다고 가정한다.

```text
1. 로그인 요청
2. 마이페이지 요청
```

HTTP 자체만으로는 서버가 두 요청을 동일한 사용자의 요청이라고 판단하지 못한다.

따라서 로그인 상태를 유지하려면 다음과 같은 추가 기술이 필요하다.

* 쿠키
* 세션
* 토큰
* JWT

무상태성의 장점은 다음과 같다.

* 서버가 클라이언트 상태를 반드시 보관할 필요가 없음
* 서버 확장이 쉬움
* 여러 서버가 요청을 나누어 처리하기 쉬움

다만 서버가 상태를 전혀 저장하지 않는다는 뜻은 아니다.

HTTP 프로토콜 자체가 이전 요청의 상태를 자동으로 기억하지 않는다는 의미이다.

---

### 8.3 비연결성

**비연결성(Connectionless)**은 요청과 응답이 끝난 뒤 연결을 계속 유지하지 않는 특성을 의미한다.

HTTP 초기 버전에서는 요청마다 TCP 연결을 생성하고 응답 후 연결을 종료하는 방식이 일반적이었다.

```text
TCP 연결
→ HTTP 요청
→ HTTP 응답
→ TCP 연결 종료
```

이 방식은 서버가 연결을 계속 유지하지 않아도 되어 리소스를 절약할 수 있다.

하지만 요청마다 TCP 연결을 새로 생성하면 다음과 같은 비용이 발생한다.

* TCP 3-way handshake
* 연결 종료 과정
* TLS handshake
* 네트워크 지연

---

## 9. HTTP Keep-Alive

**Keep-Alive**는 하나의 TCP 연결을 재사용하여 여러 HTTP 요청과 응답을 처리하는 방식이다.

```text
TCP 연결 생성
→ HTTP 요청 1
→ HTTP 응답 1
→ HTTP 요청 2
→ HTTP 응답 2
→ 일정 시간 후 연결 종료
```

이를 통해 다음과 같은 장점을 얻을 수 있다.

* TCP 연결 생성 비용 감소
* TLS 연결 비용 감소
* 응답 시간 단축
* 서버와 클라이언트의 네트워크 부담 감소

HTTP/1.1에서는 지속 연결이 기본적으로 사용된다.

다만 Keep-Alive를 사용하더라도 연결을 영구적으로 유지하는 것은 아니다.

서버 설정, 제한 시간, 요청 횟수 등에 따라 연결이 종료될 수 있다.

---

## 10. HTTP 버전별 특징

### 10.1 HTTP/1.0

* 기본적으로 요청마다 새로운 TCP 연결 사용
* 지속 연결이 기본이 아님
* 여러 요청을 처리할 때 연결 비용이 큼

---

### 10.2 HTTP/1.1

* Keep-Alive가 기본
* 하나의 TCP 연결을 재사용 가능
* 파이프라이닝 개념 지원
* 같은 연결에서 앞선 요청이 지연되면 뒤 요청도 지연될 수 있음

이러한 문제를 **Head-of-Line Blocking**이라고 한다.

---

### 10.3 HTTP/2

* 하나의 TCP 연결에서 여러 요청과 응답을 동시에 처리
* 멀티플렉싱 지원
* 헤더 압축
* 서버 푸시 기능 제공
* HTTP/1.1보다 네트워크 효율이 높음

다만 TCP 수준에서 패킷이 손실되면 같은 연결의 다른 스트림도 영향을 받을 수 있다.

---

### 10.4 HTTP/3

* TCP 대신 QUIC 프로토콜 사용
* QUIC은 UDP를 기반으로 동작
* 연결 설정 시간이 짧음
* 스트림 간 간섭 감소
* 네트워크 변경에 유연함

예를 들어 와이파이에서 모바일 네트워크로 변경되어도 연결을 유지하는 데 유리하다.

---

## 11. HTTPS

**HTTPS(HTTP Secure)**는 HTTP 통신에 TLS 암호화를 적용한 방식이다.

```text
HTTP + TLS = HTTPS
```

HTTPS는 다음과 같은 보안 기능을 제공한다.

### 기밀성

전송되는 데이터를 암호화하여 제3자가 내용을 확인하기 어렵게 한다.

### 무결성

통신 중 데이터가 변조되지 않았는지 확인할 수 있다.

### 인증

인증서를 통해 접속한 서버가 신뢰할 수 있는 서버인지 확인한다.

HTTPS를 사용하지 않으면 로그인 정보, 쿠키, 개인정보 등이 평문으로 노출될 수 있다.

---

# 쿠키, 세션, 웹 스토리지

## 12. 쿠키

### 12.1 쿠키란?

**쿠키(Cookie)**는 브라우저에 저장되는 작은 크기의 문자열 데이터이다.

일반적으로 `key=value` 형태로 저장된다.

```text
sessionId=abc123
```

서버는 HTTP 응답의 `Set-Cookie` 헤더를 통해 브라우저에 쿠키를 저장하도록 요청할 수 있다.

```http
Set-Cookie: sessionId=abc123
```

브라우저는 이후 같은 도메인에 요청을 보낼 때 조건에 맞는 쿠키를 자동으로 포함할 수 있다.

```http
Cookie: sessionId=abc123
```

---

### 12.2 쿠키의 사용 목적

쿠키는 다음과 같은 용도로 사용된다.

* 로그인 세션 ID 저장
* 사용자 설정 저장
* 장바구니 정보 저장
* 최근 본 상품 저장
* 사용자 행동 분석
* 자동 로그인

---

### 12.3 쿠키의 주요 속성

#### Expires와 Max-Age

쿠키의 만료 시간을 설정한다.

```http
Set-Cookie: theme=dark; Max-Age=3600
```

`Max-Age=3600`이면 1시간 뒤 만료된다.

만료 시간을 지정하지 않은 쿠키는 일반적으로 브라우저 세션 종료 시 삭제되는 세션 쿠키가 된다.

---

#### Domain

쿠키를 전송할 도메인을 지정한다.

```http
Set-Cookie: id=123; Domain=example.com
```

---

#### Path

쿠키가 전송될 URL 경로 범위를 지정한다.

```http
Set-Cookie: id=123; Path=/users
```

---

#### Secure

HTTPS 연결에서만 쿠키를 전송하도록 설정한다.

```http
Set-Cookie: sessionId=abc123; Secure
```

---

#### HttpOnly

JavaScript에서 쿠키에 접근하지 못하도록 제한한다.

```http
Set-Cookie: sessionId=abc123; HttpOnly
```

이를 통해 XSS 공격으로 세션 쿠키가 탈취될 위험을 줄일 수 있다.

다만 `HttpOnly`가 XSS 공격 자체를 방지하는 것은 아니다.

JavaScript가 해당 쿠키를 직접 읽지 못하게 하는 옵션이다.

---

#### SameSite

다른 사이트에서 요청을 보낼 때 쿠키를 전송할지 결정한다.

```http
Set-Cookie: sessionId=abc123; SameSite=Lax
```

주요 값은 다음과 같다.

| 값        | 의미                           |
| -------- | ---------------------------- |
| `Strict` | 다른 사이트에서 시작된 요청에는 거의 전송하지 않음 |
| `Lax`    | 일부 안전한 외부 이동 요청에는 전송         |
| `None`   | 다른 사이트 요청에도 전송 가능            |

`SameSite=None`을 사용할 때는 일반적으로 `Secure`도 함께 설정해야 한다.

SameSite 설정은 CSRF 공격 위험을 줄이는 데 도움이 된다.

---

### 12.4 쿠키의 장점

* 브라우저가 자동으로 요청에 포함
* 로그인 상태 유지에 활용 가능
* 사용자가 재방문했을 때 설정 복원 가능
* 서버가 세션 ID를 기준으로 사용자 식별 가능

---

### 12.5 쿠키의 단점

* 저장 용량이 작음
* 요청마다 전송되어 네트워크 트래픽이 증가할 수 있음
* 중요한 정보를 그대로 저장하면 보안 위험이 있음
* JavaScript 접근이 허용되면 XSS로 탈취될 수 있음
* 자동으로 요청에 포함되기 때문에 CSRF 공격 위험이 있음

쿠키 자체가 무조건 CSRF에 취약한 것이 아니라, 브라우저가 쿠키를 자동 전송하는 특성 때문에 CSRF 공격이 가능해질 수 있다.

이를 방지하기 위해 다음 방법을 사용할 수 있다.

* SameSite 설정
* CSRF 토큰
* Origin 및 Referer 검사
* 중요 요청에 대한 추가 인증

---

## 13. 세션

### 13.1 세션이란?

**세션(Session)**은 서버가 사용자의 상태나 정보를 저장하고 관리하는 방식이다.

사용자가 처음 서버에 접속하거나 로그인하면 서버는 고유한 세션 ID를 생성할 수 있다.

```text
sessionId = abc123
```

서버는 실제 사용자 정보를 서버의 메모리, 데이터베이스, Redis 등에 저장한다.

```text
abc123 → 사용자 ID 1, 로그인 상태, 권한 정보
```

세션 ID는 일반적으로 쿠키를 통해 클라이언트에게 전달된다.

```http
Set-Cookie: sessionId=abc123; HttpOnly; Secure
```

클라이언트는 이후 요청마다 해당 세션 ID를 서버에 전달한다.

```http
Cookie: sessionId=abc123
```

서버는 세션 ID를 통해 사용자를 식별한다.

---

### 13.2 세션 동작 과정

```text
1. 사용자가 로그인 요청을 보낸다.
2. 서버가 사용자 정보를 확인한다.
3. 서버가 세션을 생성한다.
4. 서버가 세션 ID를 브라우저에 쿠키로 전달한다.
5. 브라우저가 이후 요청마다 세션 ID를 전송한다.
6. 서버가 세션 ID를 조회하여 사용자를 식별한다.
```

---

### 13.3 세션의 장점

* 실제 사용자 정보가 서버에 저장됨
* 클라이언트에는 세션 ID만 전달 가능
* 서버에서 세션을 즉시 만료시킬 수 있음
* 사용자별 로그인 상태를 관리하기 쉬움

---

### 13.4 세션의 단점

* 사용자가 많아질수록 서버 저장 공간 사용량 증가
* 서버 메모리에 저장하면 서버 재시작 시 세션이 사라질 수 있음
* 여러 서버를 사용하는 환경에서는 세션 공유가 필요함
* 세션 저장소 장애 시 로그인 상태 유지가 어려울 수 있음

---

### 13.5 분산 서버와 세션

서버가 여러 대인 환경에서는 사용자의 요청이 서로 다른 서버로 전달될 수 있다.

```text
사용자 요청 1 → 서버 A
사용자 요청 2 → 서버 B
```

세션이 서버 A의 메모리에만 있다면 서버 B는 사용자를 식별하지 못할 수 있다.

이를 해결하는 방법은 다음과 같다.

#### Sticky Session

같은 사용자의 요청을 항상 같은 서버로 전달한다.

#### 세션 클러스터링

서버 간 세션 정보를 복제한다.

#### 외부 세션 저장소

Redis나 데이터베이스에 세션을 저장하여 여러 서버가 공유한다.

실무에서는 Redis를 세션 저장소로 사용하는 경우가 많다.

---

## 14. 쿠키와 세션의 관계

쿠키와 세션은 서로 완전히 대체되는 개념이 아니다.

세션 방식에서도 세션 ID를 전달하기 위해 쿠키를 사용하는 경우가 많다.

```text
쿠키
→ 클라이언트가 세션 ID를 저장

세션
→ 서버가 세션 ID에 해당하는 사용자 정보를 저장
```

예시:

```text
브라우저 쿠키:
sessionId=abc123

서버 세션 저장소:
abc123 → 사용자 김태수
```

---

## 15. 웹 스토리지

**웹 스토리지(Web Storage)**는 브라우저에서 데이터를 저장할 수 있도록 제공되는 클라이언트 저장 공간이다.

웹 스토리지에는 다음 두 종류가 있다.

* Local Storage
* Session Storage

쿠키와 달리 저장된 데이터가 HTTP 요청마다 서버에 자동으로 전송되지 않는다.

---

## 16. Local Storage

### 16.1 Local Storage란?

**Local Storage**는 사용자가 직접 삭제하거나 애플리케이션에서 삭제하지 않는 한 데이터를 계속 유지하는 저장소이다.

브라우저를 종료했다가 다시 실행해도 데이터가 남아 있다.

```javascript
localStorage.setItem("theme", "dark");
```

```javascript
const theme = localStorage.getItem("theme");
```

```javascript
localStorage.removeItem("theme");
```

---

### 16.2 Local Storage 사용 예시

* 사용자 테마
* 언어 설정
* 최근 검색어
* 임시 작성 내용
* 사용자 인터페이스 설정

민감한 개인정보나 중요한 인증 정보를 저장하는 것은 주의해야 한다.

---

## 17. Session Storage

### 17.1 Session Storage란?

**Session Storage**는 브라우저의 탭 단위로 데이터를 저장하는 공간이다.

해당 탭을 닫으면 데이터가 삭제된다.

```javascript
sessionStorage.setItem("currentStep", "2");
```

```javascript
const currentStep = sessionStorage.getItem("currentStep");
```

새로운 탭이나 창을 열면 기본적으로 별도의 Session Storage 영역이 만들어진다.

---

### 17.2 Session Storage 사용 예시

* 다단계 입력 화면의 현재 단계
* 탭에서만 필요한 임시 데이터
* 페이지 이동 중 유지할 임시 상태
* 결제나 회원가입 과정의 중간 데이터

---

## 18. 웹 스토리지의 특징

### 장점

* 쿠키보다 비교적 큰 데이터를 저장할 수 있음
* HTTP 요청마다 자동 전송되지 않음
* 불필요한 네트워크 트래픽을 줄일 수 있음
* JavaScript를 통해 쉽게 사용할 수 있음

### 단점

* JavaScript에서 접근 가능하므로 XSS 공격에 취약
* 문자열 형태로만 저장
* 객체 저장 시 직렬화가 필요
* 서버가 직접 저장된 값을 읽을 수 없음
* 사용자가 브라우저에서 값을 수정할 수 있음

---

### 객체 저장 예시

객체는 그대로 저장할 수 없으므로 JSON 문자열로 변환해야 한다.

```javascript
const user = {
  id: 1,
  name: "Kim",
};

localStorage.setItem("user", JSON.stringify(user));
```

가져올 때는 다시 객체로 변환한다.

```javascript
const savedUser = JSON.parse(localStorage.getItem("user"));
```

---

## 19. 웹 스토리지는 CSRF에 안전한가?

Local Storage와 Session Storage의 데이터는 HTTP 요청에 자동으로 포함되지 않는다.

따라서 쿠키 기반 인증보다 CSRF 공격에 직접 노출될 가능성은 낮다.

하지만 JavaScript에서 접근할 수 있으므로 XSS 공격에는 더 취약할 수 있다.

예를 들어 Local Storage에 액세스 토큰을 저장하면 XSS 공격자가 토큰을 읽어갈 수 있다.

따라서 단순히 다음과 같이 말하는 것은 정확하지 않다.

```text
웹 스토리지는 안전하다.
```

정확하게는 다음과 같이 이해해야 한다.

```text
웹 스토리지는 자동 전송되지 않아 CSRF 위험은 낮지만,
JavaScript로 접근할 수 있어 XSS 공격에 취약하다.
```

---

## 20. 쿠키, 세션, 웹 스토리지 비교

| 구분            | 쿠키                | 세션              | Local Storage | Session Storage |
| ------------- | ----------------- | --------------- | ------------- | --------------- |
| 저장 위치         | 클라이언트             | 서버              | 클라이언트         | 클라이언트           |
| 데이터 전송        | 요청마다 자동 전송 가능     | 세션 ID만 전송       | 자동 전송 안 됨     | 자동 전송 안 됨       |
| 데이터 유지        | 만료 설정에 따라 다름      | 서버 정책에 따라 다름    | 직접 삭제 전까지 유지  | 탭 종료 시 삭제       |
| 저장 크기         | 작음                | 서버 용량에 따라 다름    | 쿠키보다 큼        | 쿠키보다 큼          |
| JavaScript 접근 | 설정에 따라 가능         | 직접 접근 불가        | 가능            | 가능              |
| XSS 위험        | HttpOnly 미사용 시 위험 | 세션 ID 탈취 위험     | 높음            | 높음              |
| CSRF 위험       | 자동 전송 때문에 존재      | 쿠키 사용 시 존재      | 상대적으로 낮음      | 상대적으로 낮음        |
| 주요 용도         | 세션 ID, 사용자 설정     | 로그인 상태 및 사용자 정보 | 장기 설정         | 탭 단위 임시 정보      |

# 브라우저에 URL을 입력하면 발생하는 일

## 21. 전체 흐름

브라우저 주소창에 다음 URL을 입력했다고 가정한다.

```text
https://www.example.com/users
```

전체 과정은 다음과 같다.

```text
1. URL 분석
2. 캐시 및 서비스 워커 확인
3. DNS 조회
4. 서버와 네트워크 연결
5. TLS 연결
6. HTTP 요청 전송
7. 서버의 요청 처리
8. HTTP 응답 수신
9. 브라우저 렌더링
10. 추가 리소스 요청
```

---

## 22. URL 분석

브라우저는 입력된 URL을 여러 부분으로 나눈다.

```text
https://www.example.com:443/users?page=1#profile
```

| 부분                | 의미     |
| ----------------- | ------ |
| `https`           | 프로토콜   |
| `www.example.com` | 도메인    |
| `443`             | 포트     |
| `/users`          | 경로     |
| `page=1`          | 쿼리 문자열 |
| `profile`         | 프래그먼트  |

HTTPS의 기본 포트는 `443`, HTTP의 기본 포트는 `80`이다.

프래그먼트는 일반적으로 서버로 전송되지 않고 브라우저 내부에서 사용된다.

---

## 23. 브라우저 캐시 확인

브라우저는 서버에 요청하기 전에 기존에 저장된 캐시를 확인할 수 있다.

캐시된 데이터가 아직 유효하다면 네트워크 요청 없이 바로 사용할 수 있다.

또는 서버에 다음과 같은 조건부 요청을 보낼 수 있다.

```http
If-None-Match: "abc123"
```

서버가 자원이 변경되지 않았다고 판단하면 다음 상태 코드를 반환할 수 있다.

```http
304 Not Modified
```

브라우저는 기존에 저장된 캐시를 사용한다.

---

## 24. 서비스 워커 확인

웹 애플리케이션에 서비스 워커가 등록되어 있다면 서비스 워커가 요청을 가로챌 수 있다.

서비스 워커는 다음과 같은 작업을 수행할 수 있다.

* 캐시된 응답 반환
* 오프라인 페이지 제공
* 네트워크 요청 전달
* 백그라운드 동기화
* 푸시 알림 처리

서비스 워커가 응답을 처리하지 않으면 브라우저는 일반 네트워크 요청을 진행한다.

---

## 25. DNS 조회

브라우저는 도메인 이름을 서버의 IP 주소로 변환해야 한다.

```text
www.example.com
→ 203.0.113.10
```

이 과정을 **DNS 조회**라고 한다.

---

### 25.1 DNS 캐시 확인

DNS 조회는 일반적으로 여러 캐시를 확인한다.

```text
1. 브라우저 DNS 캐시
2. 운영체제 DNS 캐시
3. hosts 파일
4. 로컬 네트워크 또는 DNS 리졸버 캐시
```

과거에는 공유기나 ISP DNS 캐시라고 설명하는 경우가 많았지만, 실제 동작은 운영체제와 네트워크 설정에 따라 달라질 수 있다.

현대 환경에서는 사용자가 설정한 DNS 서버, 공용 DNS, 기업 DNS, DoH 서버 등을 사용할 수 있다.

---

### 25.2 DNS 리졸버의 조회 과정

캐시에 IP 주소가 없다면 DNS 리졸버가 다음 서버에 질의할 수 있다.

```text
루트 DNS 서버
→ 최상위 도메인 DNS 서버
→ 권한 있는 DNS 서버
```

예를 들어 `www.example.com`을 조회하면 다음과 같은 과정을 거친다.

```text
1. 루트 DNS 서버에 .com 서버 위치 질의
2. .com DNS 서버에 example.com 서버 위치 질의
3. example.com 권한 DNS 서버에 www.example.com IP 질의
4. IP 주소 반환
```

실제로 브라우저가 이 모든 서버에 직접 요청하는 것이 아니라, 보통 재귀 DNS 리졸버가 대신 수행한다.

---

## 26. 서버와 연결 생성

IP 주소를 확인한 뒤 브라우저는 서버와 연결을 생성한다.

연결 방식은 HTTP 버전에 따라 달라질 수 있다.

### HTTP/1.1과 HTTP/2

일반적으로 TCP 연결을 사용한다.

### HTTP/3

QUIC을 사용하며 UDP를 기반으로 동작한다.

---

## 27. TCP 3-way Handshake

TCP 연결은 일반적으로 3-way handshake를 통해 생성된다.

```text
클라이언트 → 서버: SYN
클라이언트 ← 서버: SYN + ACK
클라이언트 → 서버: ACK
```

### 1단계: SYN

클라이언트가 서버에 연결 요청을 보낸다.

### 2단계: SYN + ACK

서버가 연결 요청을 확인하고 응답한다.

### 3단계: ACK

클라이언트가 서버의 응답을 확인한다.

이후 TCP 연결이 수립된다.

---

## 28. TLS Handshake

URL이 HTTPS라면 TCP 연결 이후 TLS handshake를 수행한다.

TLS handshake에서는 다음 작업이 이루어진다.

* 서버 인증서 전달
* 인증서 유효성 확인
* 암호화 방식 협상
* 암호화 키 생성
* 안전한 통신 채널 생성

간단한 흐름은 다음과 같다.

```text
1. 클라이언트가 지원 가능한 암호화 정보를 전달
2. 서버가 인증서와 암호화 정보를 반환
3. 클라이언트가 인증서를 검증
4. 양쪽이 암호화 키를 생성
5. 암호화된 통신 시작
```

HTTP/3에서는 QUIC 내부에 TLS 기능이 통합되어 있다.

---

## 29. HTTP 요청 전송

연결이 완료되면 브라우저가 서버에 HTTP 요청을 보낸다.

```http
GET /users HTTP/1.1
Host: www.example.com
Accept: text/html
Cookie: sessionId=abc123
```

요청에는 다음 정보가 포함될 수 있다.

* HTTP 메서드
* 경로
* 요청 헤더
* 쿠키
* 인증 정보
* 요청 본문

---

## 30. 서버의 요청 처리

서버는 요청을 받은 뒤 다음과 같은 과정을 수행할 수 있다.

```text
1. 웹 서버 또는 리버스 프록시가 요청 수신
2. 애플리케이션 서버로 요청 전달
3. 라우팅할 Controller 또는 Handler 탐색
4. 인증 및 권한 검사
5. 비즈니스 로직 실행
6. 데이터베이스 조회 또는 수정
7. HTTP 응답 생성
```

예를 들어 Spring Boot에서는 다음과 같이 처리될 수 있다.

```text
Nginx
→ Spring Security Filter
→ DispatcherServlet
→ Controller
→ Service
→ Repository
→ Database
```

---

## 31. 서버 응답 수신

서버는 처리 결과를 HTTP 응답으로 반환한다.

```http
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1024

<!DOCTYPE html>
<html>
...
</html>
```

브라우저는 상태 코드와 헤더를 확인한 뒤 응답 본문을 처리한다.

---

## 32. 브라우저 렌더링

브라우저가 HTML을 수신하면 화면을 그리기 위한 과정을 시작한다.

이 과정을 **Critical Rendering Path**라고 한다.

전체 흐름은 다음과 같다.

```text
HTML 파싱
→ DOM 생성
→ CSS 파싱
→ CSSOM 생성
→ Render Tree 생성
→ Layout
→ Paint
→ Composite
```

---

## 33. DOM 생성

브라우저는 HTML 문서를 위에서 아래로 읽으면서 **DOM(Document Object Model)** 트리를 생성한다.

HTML:

```html
<body>
  <h1>Hello</h1>
  <p>Welcome</p>
</body>
```

DOM 구조:

```text
body
├── h1
│   └── Hello
└── p
    └── Welcome
```

---

## 34. CSSOM 생성

브라우저는 CSS를 분석하여 **CSSOM(CSS Object Model)**을 생성한다.

```css
h1 {
  color: red;
}
```

CSSOM에는 각 요소에 적용될 스타일 정보가 포함된다.

---

## 35. Render Tree 생성

브라우저는 DOM과 CSSOM을 결합하여 Render Tree를 만든다.

Render Tree에는 실제 화면에 표시될 요소만 포함된다.

예를 들어 다음 요소는 Render Tree에 포함되지 않는다.

```css
display: none;
```

---

## 36. Layout

Layout 단계에서는 각 요소의 크기와 위치를 계산한다.

예를 들어 다음 정보를 계산한다.

* 요소의 너비와 높이
* 화면에서의 위치
* 여백과 패딩
* 부모와 자식 요소의 배치

Layout은 Reflow라고도 부른다.

---

## 37. Paint

Paint 단계에서는 각 요소를 실제 픽셀로 그릴 준비를 한다.

다음과 같은 시각적 요소를 처리한다.

* 글자
* 색상
* 배경
* 테두리
* 그림자
* 이미지

---

## 38. Composite

브라우저는 여러 레이어를 적절한 순서로 합성하여 최종 화면을 표시한다.

CSS 애니메이션이나 `transform` 같은 속성은 별도 레이어에서 처리될 수 있다.

---

## 39. 추가 리소스 요청

HTML을 파싱하는 과정에서 브라우저는 추가 리소스를 발견할 수 있다.

```html
<link rel="stylesheet" href="/style.css">
<script src="/app.js"></script>
<img src="/logo.png">
```

브라우저는 다음 자원을 추가로 요청한다.

* CSS
* JavaScript
* 이미지
* 글꼴
* 동영상
* API 데이터

이러한 요청도 HTTP를 통해 이루어진다.

---

## 40. JavaScript 실행

브라우저는 JavaScript를 실행하여 다음 작업을 수행할 수 있다.

* DOM 수정
* 이벤트 등록
* API 요청
* 사용자 입력 처리
* 화면 변경
* 데이터 저장

일반적인 `<script>` 태그는 HTML 파싱을 중단시킬 수 있다.

```html
<script src="/app.js"></script>
```

이를 줄이기 위해 `defer` 또는 `async`를 사용할 수 있다.

### defer

```html
<script src="/app.js" defer></script>
```

* HTML 파싱과 병렬로 다운로드
* HTML 파싱이 완료된 뒤 실행
* 선언 순서대로 실행

### async

```html
<script src="/analytics.js" async></script>
```

* HTML 파싱과 병렬로 다운로드
* 다운로드가 완료되면 바로 실행
* 실행 순서가 보장되지 않음

---

## 41. TCP 연결 종료

TCP 연결을 종료할 때는 일반적으로 4-way handshake가 사용된다.

```text
클라이언트 → 서버: FIN
클라이언트 ← 서버: ACK
클라이언트 ← 서버: FIN
클라이언트 → 서버: ACK
```

### 1단계

한쪽이 연결 종료를 요청한다.

### 2단계

상대방이 종료 요청을 확인한다.

### 3단계

상대방도 전송을 마치고 연결 종료를 요청한다.

### 4단계

최종적으로 종료 요청을 확인한다.

다만 HTTP Keep-Alive를 사용하면 HTTP 요청 하나가 끝났다고 해서 TCP 연결이 즉시 종료되는 것은 아니다.

또한 HTTP/2나 HTTP/3에서는 하나의 연결을 여러 요청이 공유할 수 있다.

---

## 42. URL 입력 후 전체 흐름 요약

```text
1. 사용자가 브라우저에 URL 입력
2. 브라우저가 URL 분석
3. 브라우저 캐시와 서비스 워커 확인
4. DNS를 통해 도메인의 IP 주소 확인
5. 서버와 TCP 또는 QUIC 연결 생성
6. HTTPS인 경우 TLS 연결 수행
7. 브라우저가 HTTP 요청 전송
8. 서버가 요청 처리
9. 서버가 HTTP 응답 반환
10. 브라우저가 HTML 파싱
11. DOM과 CSSOM 생성
12. Render Tree 생성
13. Layout 수행
14. Paint 수행
15. Composite 수행
16. 화면 표시
17. CSS, JavaScript, 이미지 등 추가 리소스 요청
```

## 43. 핵심 정리

```text
HTTP
→ 클라이언트와 서버가 데이터를 주고받기 위한 프로토콜

HTTP 요청
→ 메서드, 경로, 헤더, 본문으로 구성

HTTP 응답
→ 상태 코드, 헤더, 본문으로 구성

Stateless
→ HTTP가 이전 요청 상태를 자동으로 기억하지 않음

Connectionless
→ 요청 처리 후 연결을 계속 유지하지 않는 특성

Keep-Alive
→ 하나의 TCP 연결을 여러 HTTP 요청에서 재사용

Cookie
→ 브라우저에 저장되고 요청에 자동 포함될 수 있는 작은 데이터

Session
→ 서버에 사용자 상태를 저장하고 세션 ID로 사용자를 식별

Local Storage
→ 브라우저 종료 후에도 유지되는 클라이언트 저장소

Session Storage
→ 탭을 닫을 때 삭제되는 클라이언트 저장소

DNS
→ 도메인 이름을 IP 주소로 변환

TCP 3-way Handshake
→ TCP 연결을 생성하는 과정

TLS Handshake
→ HTTPS 암호화 연결을 생성하는 과정

Critical Rendering Path
→ HTML과 CSS를 화면에 표시하는 전체 렌더링 과정
```

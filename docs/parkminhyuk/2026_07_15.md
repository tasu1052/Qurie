# Day 3 — JPA·MySQL·트랜잭션

## 1. 학습 목표

Qurie 프로젝트에 MySQL과 Spring Data JPA를 연결하고, 방 생성과 방 참여자 등록을 하나의 트랜잭션으로 처리하는 방법을 학습했다.

이번 학습의 주요 목표는 다음과 같다.

* `@Entity`, `@Id`, `@ManyToOne`의 역할을 이해한다.
* Entity 간 연관관계를 설정한다.
* 지연 로딩이 필요한 이유를 이해한다.
* 영속성 컨텍스트와 변경 감지 원리를 이해한다.
* Service 계층에 트랜잭션 경계를 설정한다.
* 방 생성 시 생성자를 `OWNER`로 자동 등록한다.
* 방 수정 및 삭제 시 소유자 권한을 확인한다.
* JPA Auditing으로 생성일과 수정일을 관리한다.
* N+1 문제가 발생하는 이유와 기본 해결 방법을 학습한다.
* 데이터베이스 인덱스의 기본 원리를 이해한다.

## 2. 방 생성 기능의 처리 흐름

방 생성은 단순히 `Room` 데이터만 저장하는 작업이 아니다.

방을 생성한 사용자는 해당 방의 `OWNER`로 자동 등록되어야 한다.

따라서 하나의 방 생성 기능에는 다음 두 개의 Repository 작업이 포함된다.

```text
사용자 조회
    ↓
Room 저장
    ↓
RoomMember를 OWNER 역할로 저장
    ↓
RoomResponse 반환
```

코드로 표현하면 다음과 같다.

```java
@Transactional
public RoomResponse createRoom(
        Long userId,
        CreateRoomRequest request
) {
    User user = userRepository.findById(userId)
            .orElseThrow(UserNotFoundException::new);

    Room room = roomRepository.save(
            Room.create(request.title())
    );

    roomMemberRepository.save(
            RoomMember.createOwner(room, user)
    );

    return RoomResponse.from(room);
}
```

`Room` 저장과 `RoomMember` 저장은 하나의 기능이므로 반드시 같은 트랜잭션 안에서 처리해야 한다.

## 3. JPA란 무엇인가

JPA는 Java 객체와 관계형 데이터베이스 테이블을 연결하기 위한 ORM 표준이다.

ORM은 객체와 관계형 데이터베이스 사이의 차이를 매핑해주는 기술이다.

```text
Java 객체                     관계형 데이터베이스

Room Entity        ↔          rooms 테이블
User Entity        ↔          users 테이블
RoomMember Entity  ↔          room_members 테이블
```

JPA를 사용하면 SQL을 직접 작성하지 않고도 Entity를 저장하고 조회할 수 있다.

```java
Room savedRoom = roomRepository.save(room);
```

위 코드는 내부적으로 다음과 유사한 SQL을 실행한다.

```sql
INSERT INTO rooms (
    title,
    status,
    created_at,
    updated_at
)
VALUES (?, ?, ?, ?);
```

Spring Data JPA는 JPA를 편리하게 사용할 수 있도록 Repository 기능을 제공한다.

```java
public interface RoomRepository
        extends JpaRepository<Room, Long> {
}
```

## 4. MySQL 연결 설정

Spring Boot에서 MySQL을 사용하려면 MySQL 드라이버와 JPA 의존성이 필요하다.

### 4.1 Gradle 의존성

```gradle
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-data-jpa'

    runtimeOnly 'com.mysql:mysql-connector-j'
}
```

---

### 4.2 `application.yml`

```yaml
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/qurie
    username: root
    password: ${DB_PASSWORD}
    driver-class-name: com.mysql.cj.jdbc.Driver

  jpa:
    hibernate:
      ddl-auto: update

    properties:
      hibernate:
        format_sql: true
        highlight_sql: true
        default_batch_fetch_size: 100

    open-in-view: false

logging:
  level:
    org.hibernate.SQL: debug
    org.hibernate.orm.jdbc.bind: trace
```

각 설정의 의미는 다음과 같다.

| 설정                         | 설명                             |
| -------------------------- | ------------------------------ |
| `datasource.url`           | 연결할 MySQL 주소와 데이터베이스           |
| `datasource.username`      | 데이터베이스 사용자 이름                  |
| `datasource.password`      | 데이터베이스 비밀번호                    |
| `ddl-auto`                 | Entity를 기준으로 테이블 구조를 관리하는 방식   |
| `format_sql`               | 실행되는 SQL을 보기 좋게 출력             |
| `default_batch_fetch_size` | 연관관계 조회 시 배치 크기 설정             |
| `open-in-view`             | Controller까지 영속성 컨텍스트를 유지할지 결정 |

비밀번호는 코드나 Git 저장소에 직접 작성하지 않고 환경 변수로 관리하는 것이 적절하다.

```yaml
password: ${DB_PASSWORD}
```

## 5. `ddl-auto` 설정

Hibernate의 `ddl-auto`는 Entity 변경 사항을 데이터베이스 스키마에 어떻게 반영할지 결정한다.

| 값             | 설명                       |
| ------------- | ------------------------ |
| `none`        | 스키마를 변경하지 않음             |
| `validate`    | Entity와 테이블 구조가 일치하는지 검증 |
| `update`      | 변경된 Entity 구조를 테이블에 반영   |
| `create`      | 실행 시 기존 테이블을 삭제하고 다시 생성  |
| `create-drop` | 실행 시 생성하고 종료 시 삭제        |

개발 초기에는 다음 설정을 사용할 수 있다.

```yaml
spring:
  jpa:
    hibernate:
      ddl-auto: update
```

하지만 운영 환경에서는 자동 스키마 변경이 위험하므로 일반적으로 다음과 같이 사용한다.

```yaml
spring:
  jpa:
    hibernate:
      ddl-auto: validate
```

운영 환경의 데이터베이스 변경은 Flyway나 Liquibase 같은 마이그레이션 도구로 관리하는 것이 안전하다.

# 6. `@Entity`

`@Entity`는 해당 클래스가 JPA에서 관리하는 Entity임을 나타낸다.

```java
@Entity
@Table(name = "rooms")
public class Room {
}
```

JPA Entity에는 기본적으로 다음 조건이 필요하다.

* `@Entity`가 선언되어야 한다.
* 기본 생성자가 있어야 한다.
* 식별자 필드가 있어야 한다.
* Entity 클래스는 `final`로 선언하지 않는 것이 일반적이다.

Lombok을 사용할 경우 기본 생성자는 다음과 같이 제한할 수 있다.

```java
@NoArgsConstructor(access = AccessLevel.PROTECTED)
```

외부에서 의미 없이 Entity를 생성하는 것을 막고 JPA만 기본 생성자를 사용할 수 있도록 한다.

---

## 6.1 Room Entity

```java
@Entity
@Table(name = "rooms")
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class Room extends BaseTimeEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 100)
    private String title;

    @Column(nullable = false, unique = true, length = 20)
    private String inviteCode;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 20)
    private RoomStatus status;

    private Room(
            String title,
            String inviteCode
    ) {
        this.title = title;
        this.inviteCode = inviteCode;
        this.status = RoomStatus.ACTIVE;
    }

    public static Room create(
            String title,
            String inviteCode
    ) {
        return new Room(title, inviteCode);
    }

    public void updateTitle(String title) {
        this.title = title;
    }

    public void close() {
        this.status = RoomStatus.CLOSED;
    }
}
```

# 7. `@Id`

`@Id`는 Entity의 기본 키를 나타낸다.

```java
@Id
private Long id;
```

데이터베이스가 기본 키를 자동 생성하도록 하려면 `@GeneratedValue`를 사용한다.

```java
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;
```

`GenerationType.IDENTITY`는 MySQL의 `AUTO_INCREMENT` 방식을 사용한다.

생성되는 테이블은 다음과 유사하다.

```sql
CREATE TABLE rooms (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    title VARCHAR(100) NOT NULL
);
```

Entity를 처음 생성할 때는 ID가 없다.

```java
Room room = Room.create(
        "Qurie Backend",
        "ABC123"
);

room.getId(); // null
```

Repository를 통해 저장하면 데이터베이스가 ID를 생성한다.

```java
Room savedRoom = roomRepository.save(room);

savedRoom.getId(); // 1
```

# 8. User Entity

```java
    @GeneratedValue(strategy = GenerationType.IDENTITY)

        nullable = false,

            String email,

        this.email = email;
        this.nickname = nickname;
    }

    public static User create(
            String email,

        return new User(email, nickname);
    }
}
```

# 9. RoomMember Entity

`RoomMember`는 `User`와 `Room`의 관계를 표현하는 Entity이다.

한 사용자는 여러 방에 참여할 수 있고, 하나의 방에는 여러 사용자가 참여할 수 있다.

```text
User N : M Room
```

관계형 데이터베이스에서는 다대다 관계를 중간 테이블로 분리한다.

```text
User 1 ─ N RoomMember N ─ 1 Room
```

`RoomMember`에는 단순한 연결 정보뿐만 아니라 사용자의 역할도 저장한다.

```text
room_id
user_id
role
joined_at
```

---

## 9.1 RoomRole

```java
public enum RoomRole {
    OWNER,
    MEMBER
}
```

---

## 9.2 RoomMember 구현

```java
@Entity
@Table(
    name = "room_members",
    uniqueConstraints = {
        @UniqueConstraint(
            name = "uk_room_member_room_user",
            columnNames = {"room_id", "user_id"}
        )
    }
)
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class RoomMember extends BaseCreatedEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(
        name = "room_id",
        nullable = false
    )
    private Room room;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(
        name = "user_id",
        nullable = false
    )
    private User user;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 20)
    private RoomRole role;

    private RoomMember(
            Room room,
            User user,
            RoomRole role
    ) {
        this.room = room;
        this.user = user;
        this.role = role;
    }

    public static RoomMember createOwner(
            Room room,
            User user
    ) {
        return new RoomMember(
                room,
                user,
                RoomRole.OWNER
        );
    }

    public static RoomMember createMember(
            Room room,
            User user
    ) {
        return new RoomMember(
                room,
                user,
                RoomRole.MEMBER
        );
    }

    public boolean isOwner() {
        return this.role == RoomRole.OWNER;
    }

    public boolean belongsTo(Long userId) {
        return this.user.getId().equals(userId);
    }
}
```

# 10. `@ManyToOne`

`@ManyToOne`은 여러 개의 현재 Entity가 하나의 다른 Entity를 참조하는 관계이다.

여러 `RoomMember`는 하나의 `Room`을 참조한다.

```java
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "room_id")
private Room room;
```

여러 `RoomMember`는 하나의 `User`를 참조한다.

```java
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "user_id")
private User user;
```

데이터베이스에서는 다음 외래 키로 표현된다.

```sql
room_members.room_id → rooms.id
room_members.user_id → users.id
```

`@JoinColumn`은 외래 키 컬럼명을 지정한다.

```java
@JoinColumn(name = "room_id")
```

---

## 10.1 연관관계의 주인

JPA 연관관계에서 외래 키를 관리하는 Entity를 연관관계의 주인이라고 한다.

현재 외래 키는 `room_members` 테이블에 존재한다.

```text
room_members.room_id
room_members.user_id
```

따라서 `RoomMember`가 연관관계의 주인이다.

```java
@ManyToOne
@JoinColumn(name = "room_id")
private Room room;
```

Day 3 단계에서는 `Room`에 `List<RoomMember>` 양방향 연관관계를 반드시 추가할 필요는 없다.

단방향 관계만으로도 다음 기능을 구현할 수 있다.

* 방의 OWNER 조회
* 사용자의 방 참여 여부 확인
* 방 생성자 등록
* 참여자 권한 확인

필요하지 않은 양방향 연관관계는 추가하지 않는 것이 구조를 단순하게 유지하는 데 도움이 된다.

# 11. 지연 로딩

지연 로딩은 연관된 Entity를 실제로 사용할 때 조회하는 방식이다.

```java
@ManyToOne(fetch = FetchType.LAZY)
private Room room;
```

`RoomMember`를 조회할 때 `Room`과 `User`를 즉시 조회하지 않고 프록시 객체를 넣어둔다.

```java
RoomMember roomMember =
        roomMemberRepository.findById(memberId)
                .orElseThrow();

Room room = roomMember.getRoom();
```

다음과 같이 실제 필드에 접근할 때 Room 조회 쿼리가 실행될 수 있다.

```java
String title = room.getTitle();
```

---

## 11.1 즉시 로딩

즉시 로딩은 부모 Entity를 조회할 때 연관 Entity도 함께 조회하는 방식이다.

```java
@ManyToOne(fetch = FetchType.EAGER)
private Room room;
```

즉시 로딩을 사용하면 필요하지 않은 데이터까지 항상 조회할 수 있다.

또한 예상하지 못한 JOIN이나 추가 쿼리가 발생할 수 있다.

따라서 연관관계는 기본적으로 지연 로딩을 사용하는 것이 적절하다.

```java
@ManyToOne(fetch = FetchType.LAZY)
```

특히 `@ManyToOne`과 `@OneToOne`의 기본 로딩 방식은 `EAGER`이므로 명시적으로 `LAZY`를 설정해야 한다.

# 12. 영속성 컨텍스트

영속성 컨텍스트는 JPA가 Entity를 관리하는 공간이다.

Entity는 다음과 같은 생명주기를 가진다.

```text
비영속
    ↓ persist 또는 save
영속
    ↓ detach 또는 트랜잭션 종료
준영속
    ↓ remove
삭제
```

---

## 12.1 비영속 상태

Java 객체만 생성되고 JPA가 관리하지 않는 상태이다.

```java
Room room = Room.create(
        "Qurie",
        "ABC123"
);
```

아직 데이터베이스에 저장되지 않았으며 영속성 컨텍스트에서도 관리하지 않는다.

---

## 12.2 영속 상태

Repository의 `save()`를 통해 저장하면 JPA가 Entity를 관리한다.

```java
Room room = roomRepository.save(
        Room.create("Qurie", "ABC123")
);
```

이후 `room`은 영속성 컨텍스트에서 관리된다.

---

## 12.3 1차 캐시

영속성 컨텍스트는 Entity를 1차 캐시에 보관한다.

```java
Room firstRoom = roomRepository.findById(1L)
        .orElseThrow();

Room secondRoom = roomRepository.findById(1L)
        .orElseThrow();
```

같은 트랜잭션 안에서 같은 ID를 다시 조회하면 1차 캐시의 Entity를 반환할 수 있다.

```java
firstRoom == secondRoom; // true
```

하나의 영속성 컨텍스트 안에서 동일한 ID의 Entity는 같은 객체로 관리된다.

# 13. 변경 감지

변경 감지는 영속 상태의 Entity 값이 변경되었을 때 JPA가 이를 감지하여 UPDATE SQL을 실행하는 기능이다.

```java
@Transactional
public RoomResponse updateRoom(
        Long roomId,
        UpdateRoomRequest request
) {
    Room room = roomRepository.findById(roomId)
            .orElseThrow(RoomNotFoundException::new);

    room.updateTitle(request.title());

    return RoomResponse.from(room);
}
```

명시적으로 다음 코드를 호출하지 않아도 된다.

```java
roomRepository.save(room);
```

트랜잭션이 종료되는 시점에 JPA가 최초 상태와 현재 상태를 비교한다.

```text
최초 상태
title = "Qurie"

변경 상태
title = "Qurie Backend"

트랜잭션 종료
    ↓
UPDATE 쿼리 실행
```

실행되는 SQL은 다음과 유사하다.

```sql
UPDATE rooms
SET title = ?,
    updated_at = ?
WHERE id = ?;
```

---

## 13.1 변경 감지의 조건

변경 감지가 동작하려면 다음 조건이 필요하다.

* Entity가 영속 상태여야 한다.
* 트랜잭션 안에서 변경되어야 한다.
* 트랜잭션이 정상적으로 커밋되어야 한다.

다음 코드는 트랜잭션이 없기 때문에 변경 사항이 저장되지 않을 수 있다.

```java
public void updateRoom(Long roomId, String title) {
    Room room = roomRepository.findById(roomId)
            .orElseThrow();

    room.updateTitle(title);
}
```

따라서 데이터 변경 메서드에는 `@Transactional`을 적용한다.

```java
@Transactional
public void updateRoom(Long roomId, String title) {
}
```

# 14. 트랜잭션

트랜잭션은 여러 데이터베이스 작업을 하나의 작업 단위로 처리한다.

트랜잭션은 다음 네 가지 특성을 가진다.

```text
원자성
일관성
격리성
지속성
```

이를 ACID라고 한다.

---

## 14.1 원자성

여러 작업이 모두 성공하거나 모두 실패해야 한다.

방 생성 기능에는 다음 두 작업이 포함된다.

```text
1. Room 저장
2. RoomMember OWNER 저장
```

첫 번째 작업만 성공하고 두 번째 작업이 실패하면 잘못된 데이터가 만들어진다.

```text
rooms에는 방이 존재
room_members에는 OWNER가 없음
```

따라서 하나의 트랜잭션으로 묶어야 한다.

```java
@Transactional
public RoomResponse createRoom(
        Long userId,
        CreateRoomRequest request
) {
    User user = userRepository.findById(userId)
            .orElseThrow(UserNotFoundException::new);

    Room room = roomRepository.save(
            Room.create(
                    request.title(),
                    inviteCodeGenerator.generate()
            )
    );

    roomMemberRepository.save(
            RoomMember.createOwner(room, user)
    );

    return RoomResponse.from(room);
}
```

`RoomMember` 저장 중 예외가 발생하면 앞에서 저장한 `Room`도 함께 롤백된다.

---

# 15. 트랜잭션 경계

트랜잭션 경계는 하나의 트랜잭션이 시작되고 종료되는 범위이다.

여러 Repository 작업을 하나의 비즈니스 기능으로 묶을 때는 Service 계층에서 트랜잭션 경계를 정의하는 것이 적절하다.

```text
Controller
    ↓
Service  ← 트랜잭션 시작
    ↓
UserRepository
RoomRepository
RoomMemberRepository
    ↓
Service 종료 ← 커밋 또는 롤백
```

Controller에 트랜잭션을 적용하기보다는 Service에 적용한다.

```java
@Service
@RequiredArgsConstructor
@Transactional(readOnly = true)
public class RoomService {
}
```

조회 메서드는 읽기 전용 트랜잭션을 사용한다.

```java
public RoomResponse getRoom(Long roomId) {
}
```

데이터 변경 메서드에는 별도로 `@Transactional`을 적용한다.

```java
@Transactional
public RoomResponse createRoom(...) {
}
```

메서드에 선언된 설정이 클래스에 선언된 설정보다 우선 적용된다.

---

## 15.1 `readOnly = true`

조회 전용 서비스에는 다음과 같이 설정할 수 있다.

```java
@Transactional(readOnly = true)
```

장점은 다음과 같다.

* 해당 기능이 조회 목적임을 명확하게 표현할 수 있다.
* 변경 감지와 Flush 관련 비용을 일부 줄일 수 있다.
* 잘못된 데이터 변경을 발견하기 쉬워진다.
* 데이터베이스가 읽기 전용 최적화를 지원할 수 있다.

데이터를 변경하는 메서드에서는 일반 트랜잭션을 사용해야 한다.

```java
@Transactional
public RoomResponse updateRoom(...) {
}
```

# 16. 방 생성 시 OWNER 자동 등록

방을 생성하면 `rooms` 테이블과 `room_members` 테이블에 데이터가 함께 저장되어야 한다.

예를 들어 사용자 ID가 `10`인 사용자가 방을 만들면 다음 데이터가 생성된다.

### rooms

| id | title         | status |
| -: | ------------- | ------ |
|  1 | Qurie Backend | ACTIVE |

### room_members

| id | room_id | user_id | role  |
| -: | ------: | ------: | ----- |
|  1 |       1 |      10 | OWNER |

---

## 16.1 Repository

```java
public interface UserRepository
        extends JpaRepository<User, Long> {
}
```

```java
public interface RoomRepository
        extends JpaRepository<Room, Long> {
}
```

```java
public interface RoomMemberRepository
        extends JpaRepository<RoomMember, Long> {

    Optional<RoomMember> findByRoomIdAndUserId(
            Long roomId,
            Long userId
    );

    boolean existsByRoomIdAndUserId(
            Long roomId,
            Long userId
    );
}
```

---

## 16.2 Service

```java
@Service
@RequiredArgsConstructor
@Transactional(readOnly = true)
public class RoomService {

    private final UserRepository userRepository;
    private final RoomRepository roomRepository;
    private final RoomMemberRepository roomMemberRepository;
    private final InviteCodeGenerator inviteCodeGenerator;

    @Transactional
    public RoomResponse createRoom(
            Long userId,
            CreateRoomRequest request
    ) {
        User user = userRepository.findById(userId)
                .orElseThrow(UserNotFoundException::new);

        String inviteCode =
                inviteCodeGenerator.generate();

        Room room = Room.create(
                request.title(),
                inviteCode
        );

        Room savedRoom =
                roomRepository.save(room);

        RoomMember owner =
                RoomMember.createOwner(
                        savedRoom,
                        user
                );

        roomMemberRepository.save(owner);

        return RoomResponse.from(savedRoom);
    }
}
```

---

## 16.3 방 생성 트랜잭션이 필요한 이유

다음 상황을 가정할 수 있다.

```text
Room 저장 성공
    ↓
RoomMember 저장 실패
```

트랜잭션이 없다면 OWNER가 없는 방이 데이터베이스에 남을 수 있다.

트랜잭션이 있으면 `RoomMember` 저장 실패 시 `Room` 저장도 롤백된다.

```text
Room 저장 성공
    ↓
RoomMember 저장 실패
    ↓
전체 트랜잭션 롤백
    ↓
Room 저장도 취소
```

# 17. 방 소유자 확인

방 수정이나 삭제는 `OWNER`만 수행할 수 있다.

사용자가 방의 소유자인지 확인하려면 `RoomMember`를 조회해야 한다.

```java
private RoomMember getRoomMember(
        Long roomId,
        Long userId
) {
    return roomMemberRepository
            .findByRoomIdAndUserId(
                    roomId,
                    userId
            )
            .orElseThrow(RoomAccessDeniedException::new);
}
```

OWNER 여부를 확인한다.

```java
private void validateOwner(
        Long roomId,
        Long userId
) {
    RoomMember roomMember =
            getRoomMember(roomId, userId);

    if (!roomMember.isOwner()) {
        throw new RoomOwnerRequiredException();
    }
}
```

---

## 17.1 방 수정

```java
@Transactional
public RoomResponse updateRoom(
        Long userId,
        Long roomId,
        UpdateRoomRequest request
) {
    validateOwner(roomId, userId);

    Room room = roomRepository.findById(roomId)
            .orElseThrow(RoomNotFoundException::new);

    room.updateTitle(request.title());

    return RoomResponse.from(room);
}
```

---

## 17.2 방 삭제

방 데이터를 실제로 삭제하지 않고 `CLOSED` 상태로 변경하는 소프트 삭제 방식을 사용한다.

```java
@Transactional
public void deleteRoom(
        Long userId,
        Long roomId
) {
    validateOwner(roomId, userId);

    Room room = roomRepository.findById(roomId)
            .orElseThrow(RoomNotFoundException::new);

    room.close();
}
```

처리 흐름은 다음과 같다.

```text
현재 사용자 확인
    ↓
RoomMember 조회
    ↓
OWNER 역할 확인
    ↓
Room 조회
    ↓
상태를 CLOSED로 변경
    ↓
변경 감지로 UPDATE 실행
```

---

## 17.3 방 조회와 권한 검증 순서

방이 존재하지 않는 경우와 사용자가 참여하지 않은 경우 중 어떤 오류를 먼저 반환할지도 고려해야 한다.

다음 방식은 방 존재 여부를 먼저 확인한다.

```java
Room room = roomRepository.findById(roomId)
        .orElseThrow(RoomNotFoundException::new);

RoomMember member = roomMemberRepository
        .findByRoomIdAndUserId(roomId, userId)
        .orElseThrow(RoomAccessDeniedException::new);
```

다만 보안상 방의 존재 여부를 외부에 노출하지 않으려면 참여 관계부터 조회하여 동일한 접근 거부 오류를 반환하는 방식도 사용할 수 있다.

프로젝트의 보안 정책에 따라 일관된 방식을 적용해야 한다.

# 18. JPA Auditing

JPA Auditing을 사용하면 생성 시각과 수정 시각을 자동으로 관리할 수 있다.

Entity마다 다음 코드를 반복하지 않아도 된다.

```java
this.createdAt = LocalDateTime.now();
this.updatedAt = LocalDateTime.now();
```

---

## 18.1 Auditing 활성화

메인 애플리케이션이나 설정 클래스에 `@EnableJpaAuditing`을 추가한다.

```java
@EnableJpaAuditing
@SpringBootApplication
public class QurieApplication {

    public static void main(String[] args) {
        SpringApplication.run(
                QurieApplication.class,
                args
        );
    }
}
```

별도 설정 클래스로 분리할 수도 있다.

```java
@Configuration
@EnableJpaAuditing
public class JpaConfig {
}
```

---

## 18.2 BaseTimeEntity

```java
@Getter
@MappedSuperclass
@EntityListeners(AuditingEntityListener.class)
public abstract class BaseTimeEntity {

    @CreatedDate
    @Column(
        nullable = false,
        updatable = false
    )
    private LocalDateTime createdAt;

    @LastModifiedDate
    @Column(nullable = false)
    private LocalDateTime updatedAt;
}
```

각 애너테이션의 역할은 다음과 같다.

| 애너테이션               | 역할                  |
| ------------------- | ------------------- |
| `@MappedSuperclass` | 상속받은 Entity에 필드를 매핑 |
| `@EntityListeners`  | Auditing 이벤트 감지     |
| `@CreatedDate`      | 최초 저장 시 생성 시각 기록    |
| `@LastModifiedDate` | 수정 시 수정 시각 기록       |

Room Entity는 다음과 같이 상속받는다.

```java
@Entity
public class Room extends BaseTimeEntity {
}
```

---

## 18.3 생성 시각만 필요한 Entity

`RoomMember`의 가입 시각처럼 수정 시각이 필요하지 않은 경우 별도의 공통 Entity를 사용할 수 있다.

```java
@Getter
@MappedSuperclass
@EntityListeners(AuditingEntityListener.class)
public abstract class BaseCreatedEntity {

    @CreatedDate
    @Column(
        nullable = false,
        updatable = false
    )
    private LocalDateTime createdAt;
}
```

```java
@Entity
public class RoomMember extends BaseCreatedEntity {
}
```

# 19. 생성자와 수정자 Auditing

JPA Auditing은 생성 시각과 수정 시각뿐만 아니라 생성자와 수정자도 관리할 수 있다.

```java
@CreatedBy
private Long createdBy;

@LastModifiedBy
private Long updatedBy;
```

이를 사용하려면 `AuditorAware`를 구현해야 한다.

```java
@Configuration
@EnableJpaAuditing
public class JpaConfig {

    @Bean
    public AuditorAware<Long> auditorProvider() {
        return () -> Optional.of(1L);
    }
}
```

위 코드는 테스트를 위한 임시 사용자 ID를 반환한다.

실제 인증 기능이 추가되면 SecurityContext에서 로그인 사용자 ID를 가져와야 한다.

```java
@Bean
public AuditorAware<Long> auditorProvider() {
    return () -> {
        Authentication authentication =
                SecurityContextHolder
                        .getContext()
                        .getAuthentication();

        if (
            authentication == null
            || !authentication.isAuthenticated()
        ) {
            return Optional.empty();
        }

        CustomUserPrincipal principal =
                (CustomUserPrincipal)
                        authentication.getPrincipal();

        return Optional.of(principal.getUserId());
    };
}
```

---

## 19.1 생성자를 FK로 저장할지 ID로 저장할지

생성자와 수정자를 저장하는 방식은 두 가지가 있다.

### 사용자 Entity 연관관계

```java
@CreatedBy
@ManyToOne(fetch = FetchType.LAZY)
private User createdBy;
```

### 사용자 ID만 저장

```java
@CreatedBy
private Long createdBy;
```

단순 감사 정보라면 사용자 ID만 저장하는 방식이 구조가 단순하다.

방의 OWNER 여부는 Auditing의 `createdBy`가 아니라 `RoomMember.role`을 기준으로 판단해야 한다.

방 생성자와 현재 OWNER는 달라질 수 있기 때문이다.

```text
최초 생성자: 사용자 A
현재 OWNER: 사용자 B
```

# 20. N+1 문제

N+1 문제는 Entity 목록을 한 번 조회한 후 각 Entity의 연관관계를 조회하기 위해 추가 쿼리가 반복 실행되는 문제이다.

예를 들어 방 참여자 10명을 조회한다고 가정한다.

```java
List<RoomMember> members =
        roomMemberRepository.findAll();
```

첫 번째 쿼리로 참여자 목록을 조회한다.

```sql
SELECT *
FROM room_members;
```

이후 반복문에서 사용자 닉네임을 조회한다.

```java
for (RoomMember member : members) {
    System.out.println(
            member.getUser().getNickname()
    );
}
```

`User`가 지연 로딩 상태라면 각 참여자마다 사용자 조회 쿼리가 실행될 수 있다.

```text
RoomMember 목록 조회 1회
User 조회 N회

총 1 + N회
```

이를 N+1 문제라고 한다.

---

## 20.1 N+1 문제 확인

SQL 로그를 활성화하면 실행되는 쿼리를 확인할 수 있다.

```yaml
logging:
  level:
    org.hibernate.SQL: debug
```

다음과 같이 비슷한 쿼리가 반복되면 N+1 문제를 의심할 수 있다.

```sql
SELECT * FROM room_members;

SELECT * FROM users WHERE id = 1;
SELECT * FROM users WHERE id = 2;
SELECT * FROM users WHERE id = 3;
SELECT * FROM users WHERE id = 4;
```

---

## 20.2 Fetch Join

JPQL의 Fetch Join을 사용하면 연관 Entity를 한 번에 조회할 수 있다.

```java
@Query("""
    SELECT rm
    FROM RoomMember rm
    JOIN FETCH rm.user
    WHERE rm.room.id = :roomId
""")
List<RoomMember> findAllWithUserByRoomId(
        @Param("roomId") Long roomId
);
```

실행되는 SQL은 다음과 유사하다.

```sql
SELECT rm.*, u.*
FROM room_members rm
JOIN users u
    ON rm.user_id = u.id
WHERE rm.room_id = ?;
```

---

## 20.3 EntityGraph

`@EntityGraph`를 사용할 수도 있다.

```java
@EntityGraph(attributePaths = "user")
List<RoomMember> findAllByRoomId(Long roomId);
```

---

## 20.4 DTO Projection

화면에 필요한 데이터만 직접 조회할 수도 있다.

```java
@Query("""
    SELECT new m.qurie.room.dto.response.RoomMemberResponse(
        rm.user.id,
        rm.user.nickname,
        rm.role
    )
    FROM RoomMember rm
    WHERE rm.room.id = :roomId
""")
List<RoomMemberResponse> findMemberResponses(
        @Param("roomId") Long roomId
);
```

DTO Projection을 사용하면 Entity 전체가 아니라 필요한 컬럼만 조회할 수 있다.

---

## 20.5 기본 원칙

연관관계를 모두 `EAGER`로 바꾸는 것은 N+1 문제의 올바른 해결 방법이 아니다.

기본 전략은 다음과 같다.

```text
연관관계는 LAZY로 설정
    ↓
필요한 조회 API에서만
Fetch Join, EntityGraph, DTO Projection 사용
```

# 21. 인덱스

인덱스는 데이터베이스에서 특정 데이터를 빠르게 찾기 위한 자료구조이다.

책의 목차나 색인과 비슷한 역할을 한다.

인덱스가 없으면 조건에 맞는 행을 찾기 위해 테이블 전체를 확인할 수 있다.

```sql
SELECT *
FROM room_members
WHERE room_id = 10
  AND user_id = 20;
```

`room_members` 데이터가 많아질수록 전체 탐색 비용이 증가한다.

---

## 21.1 기본 키 인덱스

기본 키에는 자동으로 인덱스가 생성된다.

```sql
PRIMARY KEY (id)
```

다음 조회는 기본 키 인덱스를 사용할 수 있다.

```sql
SELECT *
FROM rooms
WHERE id = 1;
```

---

## 21.2 유니크 인덱스

`invite_code`처럼 중복을 허용하지 않는 컬럼에는 유니크 인덱스를 사용할 수 있다.

```java
@Column(
    nullable = false,
    unique = true
)
private String inviteCode;
```

또는 테이블에 명시할 수 있다.

```java
@Table(
    name = "rooms",
    indexes = {
        @Index(
            name = "idx_rooms_invite_code",
            columnList = "invite_code",
            unique = true
        )
    }
)
```

---

## 21.3 복합 인덱스

`room_members`에서는 방과 사용자의 조합을 자주 조회한다.

```java
findByRoomIdAndUserId(
    Long roomId,
    Long userId
);
```

따라서 다음 복합 인덱스를 고려할 수 있다.

```sql
CREATE UNIQUE INDEX
uk_room_members_room_user
ON room_members(room_id, user_id);
```

JPA에서는 다음과 같이 설정할 수 있다.

```java
@Entity
@Table(
    name = "room_members",
    uniqueConstraints = {
        @UniqueConstraint(
            name = "uk_room_members_room_user",
            columnNames = {
                "room_id",
                "user_id"
            }
        )
    },
    indexes = {
        @Index(
            name = "idx_room_members_user_id",
            columnList = "user_id"
        )
    }
)
public class RoomMember {
}
```

---

## 21.4 복합 인덱스의 순서

다음 인덱스가 있다고 가정한다.

```sql
INDEX(room_id, user_id)
```

이 인덱스는 다음 조건에서 활용하기 좋다.

```sql
WHERE room_id = ?
```

```sql
WHERE room_id = ?
  AND user_id = ?
```

하지만 다음 조건에서는 인덱스 활용도가 낮아질 수 있다.

```sql
WHERE user_id = ?
```

따라서 사용자별 참여 방 목록을 자주 조회한다면 별도의 인덱스가 필요할 수 있다.

```sql
INDEX(user_id)
```

인덱스 컬럼 순서는 실제 조회 조건을 기준으로 설계해야 한다.

---

## 21.5 인덱스의 단점

인덱스는 조회 속도를 높이지만 무조건 많이 생성하면 좋은 것은 아니다.

인덱스의 단점은 다음과 같다.

* 추가 저장 공간이 필요하다.
* INSERT 시 인덱스도 갱신해야 한다.
* UPDATE 시 인덱스도 변경될 수 있다.
* DELETE 시 인덱스에서도 제거해야 한다.
* 너무 많은 인덱스는 쓰기 성능을 저하시킬 수 있다.

따라서 다음 기준으로 인덱스를 고려한다.

* `WHERE` 조건에 자주 사용되는 컬럼
* JOIN 조건에 사용되는 외래 키
* 정렬과 그룹화에 자주 사용되는 컬럼
* 중복을 방지해야 하는 컬럼
* 실제 조회 빈도가 높은 컬럼 조합

# 26. 예외와 롤백

기본적으로 `@Transactional`은 `RuntimeException`과 `Error`가 발생하면 트랜잭션을 롤백한다.

```java
public class BusinessException
        extends RuntimeException {
}
```

비즈니스 예외가 `RuntimeException`을 상속하면 자동으로 롤백된다.

```java
@Transactional
public RoomResponse createRoom(...) {
    Room room = roomRepository.save(...);

    throw new BusinessException();

    // Room 저장도 롤백됨
}
```

체크 예외까지 롤백하려면 다음과 같이 설정할 수 있다.

```java
@Transactional(rollbackFor = Exception.class)
```

하지만 일반적으로 비즈니스 예외는 `RuntimeException`을 상속하도록 설계한다.

# 27. `@Transactional` 사용 시 주의점

## 27.1 같은 클래스 내부 호출

Spring의 `@Transactional`은 프록시 기반으로 동작한다.

같은 클래스 안에서 트랜잭션 메서드를 직접 호출하면 기대한 대로 동작하지 않을 수 있다.

```java
public void outer() {
    inner();
}

@Transactional
public void inner() {
}
```

`outer()`에서 `inner()`를 호출하면 프록시를 거치지 않는 자기 호출이 된다.

트랜잭션 경계를 외부에서 호출되는 Service의 공개 메서드에 설정하는 것이 적절하다.

---

## 27.2 private 메서드

다음과 같이 `private` 메서드에 `@Transactional`을 붙이는 것은 일반적으로 적용되지 않는다.

```java
@Transactional
private void saveRoom() {
}
```

외부에서 호출되는 `public` Service 메서드에 적용한다.

---

## 27.3 예외를 삼키는 경우

예외를 `catch`한 후 다시 발생시키지 않으면 트랜잭션이 정상 처리된 것으로 판단할 수 있다.

```java
@Transactional
public void createRoom() {
    try {
        roomRepository.save(...);
        roomMemberRepository.save(...);
    } catch (Exception exception) {
        log.error("저장 실패", exception);
    }
}
```

예외를 처리하더라도 트랜잭션을 롤백해야 한다면 예외를 다시 던져야 한다.

```java
catch (Exception exception) {
    log.error("저장 실패", exception);
    throw exception;
}
```

---

## 27.4 외부 API 호출과 트랜잭션

데이터베이스 트랜잭션 안에서 시간이 오래 걸리는 AI API 호출을 수행하면 트랜잭션과 DB Connection이 오랫동안 유지될 수 있다.

```java
@Transactional
public void generateQuiz() {
    aiClient.generateQuiz();
    quizRepository.save(...);
}
```

AI 생성은 시간이 오래 걸리고 실패 가능성이 있으므로 이후에는 다음과 같이 분리하는 것이 적절하다.

```text
AI 실행 상태 저장
    ↓
트랜잭션 종료
    ↓
외부 AI API 호출
    ↓
결과 저장용 새 트랜잭션 실행
```

Day 3에서는 방 생성과 같이 짧고 원자성이 필요한 데이터베이스 작업에 트랜잭션을 적용한다.

```java
@RestController
@RequestMapping("/api/rooms")
```

## 29.2 Service

```java
@Service
@RequiredArgsConstructor
@Transactional(readOnly = true)
public class RoomService {

    private final UserRepository userRepository;
    private final RoomRepository roomRepository;
    private final RoomMemberRepository roomMemberRepository;
    private final InviteCodeGenerator inviteCodeGenerator;

    @Transactional
    public RoomResponse createRoom(
            Long userId,
            CreateRoomRequest request
    ) {
        User user = userRepository
                .findById(userId)
                .orElseThrow(
                    UserNotFoundException::new
                );

        Room room = Room.create(
                request.title(),
                inviteCodeGenerator.generate()
        );

        Room savedRoom =
                roomRepository.save(room);

        RoomMember owner =
                RoomMember.createOwner(
                        savedRoom,
                        user
                );

        roomMemberRepository.save(owner);

        return RoomResponse.from(
                savedRoom,
                RoomRole.OWNER
        );
    }

    @Transactional
    public RoomResponse updateRoom(
            Long userId,
            Long roomId,
            UpdateRoomRequest request
    ) {
        RoomMember roomMember =
                getRoomMember(roomId, userId);

        validateOwner(roomMember);

        Room room = roomMember.getRoom();

        room.updateTitle(request.title());

        return RoomResponse.from(
                room,
                roomMember.getRole()
        );
    }

    @Transactional
    public void deleteRoom(
            Long userId,
            Long roomId
    ) {
        RoomMember roomMember =
                getRoomMember(roomId, userId);

        validateOwner(roomMember);

        roomMember.getRoom().close();
    }

    private RoomMember getRoomMember(
            Long roomId,
            Long userId
    ) {
        return roomMemberRepository
                .findByRoomIdAndUserId(
                        roomId,
                        userId
                )
                .orElseThrow(
                    RoomAccessDeniedException::new
                );
    }

    private void validateOwner(
            RoomMember roomMember
    ) {
        if (!roomMember.isOwner()) {
            throw new RoomOwnerRequiredException();
        }
    }
}
```

# 30. 데이터베이스 제약조건

애플리케이션 코드에서 중복 여부를 확인하더라도 데이터베이스 제약조건이 필요하다.

같은 사용자가 같은 방에 중복 참여하지 못하도록 다음 제약조건을 설정한다.

```java
@Table(
    name = "room_members",
    uniqueConstraints = {
        @UniqueConstraint(
            name = "uk_room_members_room_user",
            columnNames = {
                "room_id",
                "user_id"
            }
        )
    }
)
```

애플리케이션에서 먼저 검사할 수도 있다.

```java
if (
    roomMemberRepository
        .existsByRoomIdAndUserId(roomId, userId)
) {
    throw new AlreadyJoinedRoomException();
}
```

하지만 동시에 두 요청이 들어오면 두 요청이 모두 중복 검사에 통과할 수 있다.

```text
요청 A: 중복 없음 확인
요청 B: 중복 없음 확인
요청 A: 저장
요청 B: 저장
```

따라서 최종 데이터 무결성은 데이터베이스의 UNIQUE 제약조건으로 보장해야 한다.

# 31. 학습하면서 중요하다고 느낀 점

## 31.1 다대다 관계는 중간 Entity로 분리해야 한다

User와 Room의 관계에는 `OWNER`, `MEMBER`와 같은 추가 정보가 필요하다.

따라서 JPA의 단순 `@ManyToMany`를 사용하기보다 `RoomMember` Entity를 만들어 관계를 명시적으로 관리하는 것이 적절하다.

---

## 31.2 연관관계는 기본적으로 지연 로딩을 사용해야 한다

모든 연관 데이터를 항상 조회하면 불필요한 쿼리와 메모리 사용이 발생할 수 있다.

연관관계는 `LAZY`로 설정하고, 필요한 조회에서 Fetch Join이나 DTO Projection을 사용해야 한다.

---

## 31.3 변경 감지를 사용하면 수정 코드가 단순해진다

영속 상태의 Entity는 트랜잭션 안에서 값을 변경하면 별도의 `save()` 없이 UPDATE 쿼리가 실행된다.

```java
room.updateTitle(title);
```

Entity의 상태 변경은 의미가 드러나는 메서드로 제한하는 것이 좋다.

---

## 31.4 트랜잭션은 비즈니스 기능 단위로 설정해야 한다

방 생성은 `Room` 저장과 `RoomMember` 저장을 함께 성공시켜야 하는 하나의 기능이다.

따라서 Repository 메서드마다 별도로 처리하는 것이 아니라 Service 메서드 전체를 하나의 트랜잭션으로 묶어야 한다.

---

## 31.5 OWNER 권한은 RoomMember를 기준으로 판단해야 한다

방의 최초 생성자와 현재 OWNER는 달라질 수 있다.

따라서 `Room.createdBy`만 확인해서는 안 되고 `RoomMember.role`을 기준으로 현재 권한을 판단해야 한다.

---

## 31.6 Auditing으로 반복 코드를 줄일 수 있다

생성일과 수정일을 각 Entity에서 직접 설정하지 않고 JPA Auditing으로 자동 관리할 수 있다.

이를 통해 시간 필드 관리 방식을 프로젝트 전체에서 일관되게 유지할 수 있다.

---

## 31.7 N+1 문제는 SQL 로그로 확인해야 한다

코드만 보고 쿼리 개수를 정확하게 판단하기 어려울 수 있다.

API 실행 시 SQL 로그를 확인하고 반복 쿼리가 발생하는지 검증해야 한다.

---

## 31.8 인덱스는 조회 패턴을 기준으로 설계해야 한다

모든 컬럼에 인덱스를 추가하는 것이 아니라 실제 API의 조회 조건을 기준으로 설계해야 한다.

Qurie의 `room_members`에서는 다음 조회가 자주 사용된다.

```text
특정 사용자가 특정 방에 참여했는가
특정 사용자가 참여한 방 목록
특정 방의 OWNER는 누구인가
```

따라서 다음 인덱스가 필요할 수 있다.

```text
UNIQUE(room_id, user_id)
INDEX(user_id)
INDEX(room_id, role)
```

# 32. 추가로 결정해야 할 사항

다음 내용은 이후 구현 과정에서 추가 논의가 필요하다.

* 방에 OWNER를 한 명만 허용할 것인가
* OWNER가 여러 명일 수 있는가

* OWNER가 방을 나갈 때 어떤 정책을 적용할 것인가
* 방 종료 시 참여자의 상태도 별도로 변경할 것인가
* 종료된 방의 조회를 허용할 것인가
* 방 참여 기록을 실제 삭제할 것인가
* 퇴장 상태를 별도 컬럼으로 관리할 것인가
* 생성자와 수정자를 모든 Entity에 저장할 것인가

* Entity 연관관계와 단순 ID 저장 중 어떤 방식을 사용할 것인가

# 33. 오늘 학습한 내용 요약

오늘은 Spring Data JPA와 MySQL을 연결하고 Entity 연관관계와 트랜잭션의 기본 원리를 학습했다.

주요 학습 내용은 다음과 같다.

1. `@Entity`는 JPA가 관리할 클래스를 나타낸다.
2. `@Id`는 Entity의 기본 키를 지정한다.
3. `@GeneratedValue`를 사용하면 데이터베이스에서 ID를 자동 생성할 수 있다.
4. `@ManyToOne`은 여러 Entity가 하나의 Entity를 참조하는 관계를 표현한다.
5. User와 Room의 다대다 관계는 `RoomMember` 중간 Entity로 분리하는 것이 적절하다.
6. RoomMember는 방 참여 관계와 `OWNER`, `MEMBER` 권한을 관리한다.
7. 연관관계는 기본적으로 `FetchType.LAZY`를 사용하는 것이 좋다.
8. 영속성 컨텍스트는 Entity를 관리하고 1차 캐시와 변경 감지 기능을 제공한다.
9. 영속 상태의 Entity는 트랜잭션 안에서 값을 변경하면 자동으로 UPDATE된다.
10. 여러 Repository 작업은 Service 계층에서 하나의 트랜잭션으로 묶어야 한다.
11. 방 생성 시 Room과 OWNER RoomMember를 하나의 트랜잭션으로 저장해야 한다.
12. 방 수정과 삭제는 RoomMember의 역할을 기준으로 OWNER 권한을 검증해야 한다.
13. JPA Auditing을 사용하면 생성일과 수정일을 자동으로 관리할 수 있다.
14. N+1 문제는 목록 조회 후 연관 Entity 쿼리가 반복 실행되는 문제이다.
15. Fetch Join, EntityGraph, DTO Projection으로 N+1 문제를 해결할 수 있다.
16. 인덱스는 실제 조회 조건과 데이터 사용 패턴을 기준으로 설계해야 한다.
17. 애플리케이션 검사와 데이터베이스 제약조건을 함께 사용해야 데이터 무결성을 보장할 수 있다.

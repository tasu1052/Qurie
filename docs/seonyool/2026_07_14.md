## 1. WebRTC 앱 구조 

WebRTC P2P를 실제로 굴러가게 하는 인프라를 알아보자.

### ① 시그널링 서버 (Signaling Server)

P2P로 통신 전에, 서로 "내 IP는 이거고, 비디오 코덱은 이거 쓸 거야" 하고 입을 맞추는 과정이 필요하다.

* **SDP (Session Description Protocol):** 어떤 화질/코덱으로 보낼지 적힌 명세서.
* **ICE Candidate:** STUN/TURN 찔러보고 알아낸 내 접속 경로 후보들.

이 두 개를 서로 교환하게 해주는 게 시그널링 서버다. 주로 WebSocket으로 핑퐁을 치는데, 바닐라 JS로 짜면 `createOffer`, `createAnswer` 하면서 이벤트 달아주느라 코드가 스파게티가 된다. (Stream SDK 같은 툴킷이 핸드셰이크 과정을 `call.join()`로 덮어버리는 것이다.)

### ② 다대다 통신의 한계와 미디어 서버 (SFU)

1:1은 그냥 P2P로 쏘면 되지만, 3명 이상 모이는 순간 문제가 터진다.

* **Mesh (완전 P2P):** 5명이 모이면, 내 컴퓨터는 나머지 4명한테 각자 비디오를 쏴야 한다 (업로드 트래픽 4배). 모바일 기기로 이러면 배터리랑 데이터에 큰 부하가 올 것이다.
* **SFU (Selective Forwarding Unit) - 현재 트렌드:** 그래서 요새는 중앙에 릴레이 서버를 둔다. 나는 내 영상을 **서버에 딱 1번만 쏘면**, 서버가 알아서 나머지 사람들한테 뿌려준다. (Zoom, 디스코드, 그리고 Stream SDK도 다 이 방식을 쓴다.)

## 2. React + TypeScript 환경에서는 이걸 어떻게 다루나?

바닐라 WebRTC의 그 토나오는 복잡성을 React 생태계로 가져오면 어떻게 구조화될까?

### ① 전역 연결 관리 (Provider 패턴)

옛날처럼 `window.RTCPeerConnection` 같은 전역 객체를 이리저리 넘기면 스파게티 코드가 되기 딱 좋다. React에서는 이걸 깔끔하게 Context API(Provider)로 덮어버린다.

* `<StreamVideo>`: 앱 최상단에서 웹소켓 연결이랑 유저 인증을 뚫어놓고 대기한다.
* `<StreamCall>`: 특정 방(통화)에 들어갈 때 이걸로 감싸서 하위 컴포넌트들에 미디어 스트림을 쭉쭉 내려준다.

### ② 비동기 컴플렉시티를 이겨내는 상태(State) 관리

WebRTC는 철저한 비동기 이벤트 덩어리다. 누가 방에 들어오고, 마이크 끄고, 튕기는 모든 게 웹소켓 이벤트로 날아온다.

* 바닐라에서는 `onaddstream = (e) => {}` 하면서 DOM을 직접 건드려야 하지만,
* React 기반 SDK들은 이걸 낚아채서 `useCallStateHooks` 같은 걸로 상태(State)화 시켜서 던져준다. 누군가 마이크 끄면 배열 값만 싹 바뀌고, React가 알아서 렌더링을 다시 해주는 편리한 구조다.

### ③ TypeScript의 강력함 (런타임 에러 방어)

네트워크 통신 짤 때 제일 어려운 부분은 "서버에서 날아온 데이터가 도대체 어떻게 구성되어 있는 건지" 확신할 수 없다는 거다.
TypeScript를 쓰면 참가자 객체(`StreamVideoParticipant`) 안에 `roles`가 있는지, `audioLevel`이 있는지 컴파일 단에서 다 잡아준다. "누가 마이크를 켰나?" 체크할 때 원인 모를 `undefined`가 터지는 걸 원천 차단해 준다.

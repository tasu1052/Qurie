# Qurie AI 설계 노트

> Qurie 프로젝트 AI 담당 관점의 설계 결정과 근거 정리.
> 배경 개념은 `agent_concepts.md` 참고.

---

## 1. 우리는 RAG가 아니다

- RAG의 R = Retrieval(검색). **우리 파이프라인엔 검색이 없음.**
- 퀴즈의 재료 = 사용자가 업로드한 코드 → 이미 손에 있고, 컨텍스트에 통째로 들어가는 크기.
- "색인 카드 만들 필요 없이 책이 한 페이지짜리인 상황."
- Agentic RAG 자료를 공부한 이유: **루프 구조(채점→재작성→재시도)의 사고방식이 같아서.**
  시스템이 RAG라서가 아님.
- Q&A 방어: "왜 RAG 안 썼어요?" →
  "검색이 필요한 문제가 아니었고, 저희 문제는 생성물의 품질 보증이라
  Evaluator-Optimizer 루프를 선택했습니다."
  (유행 기술을 안 쓴 이유를 설명할 수 있는 게 쓴 것보다 좋은 평가를 받음)

### 개념 치환표 (Agentic RAG 튜토리얼 → Qurie)

| 튜토리얼 용어 | Qurie |
|---|---|
| retrieve (검색) | generate (퀴즈 생성) |
| grade documents (문서 채점) | judge (퀴즈 채점) |
| rewrite question (질문 재작성) | refine (비판 반영 재생성) |
| generate answer (답변 생성) | store (합격 퀴즈 저장) |

## 2. 핵심 패턴: Self-Refine 퀴즈 생성 파이프라인

### 패턴의 정확한 이름

| 관점 | 이름 |
|---|---|
| 공식 패턴명 (Anthropic) | **Evaluator-Optimizer 워크플로** |
| 학계 용어 (2023 논문) | **Self-Refine** |
| 검증 부분만 | **LLM-as-a-Judge** |
| 역할 구조로 부르면 | **Generator–Solver–Judge 3-역할 멀티 에이전트** (통칭 Generator-Critic) |

기획서/발표용 표현:
> "멀티 에이전트 기반 Self-Refine 퀴즈 생성 파이프라인
> (Generator–Solver–Judge 3-역할 구조, LLM-as-a-Judge 검증 적용)"

### 구조

```
analyze_code → generate → solve_blind → judge ─┬─ pass → dedup_store → END
                  ↑                            ├─ fail → refine ──┐
                  └────────────────────────────┴──────────────────┘
                                               └─ retry 초과 → discard → END
```

- **Generator (출제)**: 코드 분석 후 퀴즈 초안 생성. 품질 중요 → 상위 모델.
- **Solver (블라인드 풀이)**: **정답을 가린 채** 독립적으로 풀이. 출제와 **다른(더 싼) 모델**.
- **Judge (판정)**: 풀이 결과 vs 출제 정답 일치 + 문항 품질(정답 유일성, 오답 매력도) 채점.

### 설계 원칙 (면접/발표 방어 포인트)

1. **왜 2가 아니라 3역할?** 같은 모델이 자기 문제를 검수하면 같은 오류를 재현.
   같은 정보를 주고 "맞는지 봐줘" 하면 LLM은 관대하게 통과시키는 경향.
   → 핵심은 **정답을 가리고 독립적으로 풀게 하는 것(블라인드).**
2. **Solver 불일치 = 강제 불합격.** Judge 점수와 무관. 독립 풀이자가 다른 답을 골랐다는
   사실 자체가 정답 모호성의 증거 → 코드 레벨 게이트.
3. **critique 누적.** 재생성 시 "이전 시도가 왜 불합격했는지"를 프롬프트에 계속 쌓아
   같은 실수 반복 방지. (Self-Refine의 핵심)
4. **discard 로그도 자산.** 어떤 유형이 계속 불합격하는지 = 프롬프트 개선 근거.
   발표 스토리: "실패 데이터로 파이프라인을 개선했다."
5. **에이전트 개수는 본질이 아님.** 본질은
   생성자/평가자 분리 + 평가가 게이트 + 피드백이 루프를 돈다.

## 3. 왜 파인튜닝이 아닌가

- 파인튜닝이 맞는 경우: 특수 도메인 지식 주입 / 출력 스타일 고정 / 대량 호출 비용 절감.
- "코드 읽고 퀴즈 만들기"는 **추론 능력** 문제 → 오픈 7B~14B 파인튜닝해도 프론티어 API를 못 따라감.
- 고품질 "코드→퀴즈" 쌍 수천 개 만드는 것 자체가 프로젝트보다 큰 일.
- **퀴즈 퀄리티 = 모델 선택 10% + 파이프라인 설계 90%.**
- 파인튜닝 카드는 "퀴즈 데이터 1만 개 쌓인 뒤 API 비용 절감" 시점용으로 보류.

## 4. GMS 모델 배치 전략

| 단계 | 모델 급 | 이유 |
|---|---|---|
| 생성 (Generator) | gpt 5.4 (45cr) | 품질 우선 |
| 풀이/판정 (Solver/Judge) | gpt 5.4 mini (14cr) | 푸는 건 더 쉬운 작업, 저비용 |
| 태깅/분류 | gpt 5.4 nano (4cr) | 단순 작업 |

- pro급(540cr)은 이 태스크에 과함. 5.4로 시작해서 부족할 때만 상향.
- 확인 필요: GMS의 OpenAI 호환(`/v1/chat/completions`) 여부,
  `response_format={"type": "json_object"}` 지원 여부 → API 상세 조회 메뉴.
  미지원 시 프롬프트로 JSON 강제 + 파싱 실패 재시도 방어 코드 필요.

## 5. 아키텍처 결정 사항

- **AI 서버는 FastAPI 마이크로서비스로 분리** (Spring Boot가 HTTP로 호출).
  근거: LangGraph/트레이싱(Langfuse) 생태계가 Python 우선 + AI 담당 작업 영역 물리적 분리.
  → 아키텍처 다이어그램에 `[AI Server: FastAPI + LangGraph]` 박스 추가,
  Spring의 "AI 연동 모듈"은 "AI 서버 HTTP 클라이언트"로 명시.
- **중복 퀴즈 방지**: 임베딩을 MySQL JSON 컬럼 저장 + numpy 코사인 유사도 (수천 개 규모라 충분).
  발표 멘트: "규모를 고려해 벡터 DB 대신 인메모리 계산을 선택" — 기술 선택 근거 어필.
  유사도 임계값 0.92에서 시작, 데이터 보며 조정.
- **비동기 생성**: self-refine 루프는 문항당 수십 초 가능 → 세션 진행 중 백그라운드 생성,
  리뷰 종료 시점에 퀴즈 타임 시작. 지연시간을 UX 설계로 숨김.
- **Quiz는 CodeSnapshot에 귀속** (`Quiz.snapshot_id` FK). 동시 편집으로 코드가 계속 바뀌므로
  "어느 시점 코드로 낸 문제인지" 명확해야 해설이 성립.
- **1차 범위**: 객관식 + 빈칸 (정답 비교가 기계적 → 블라인드 검증이 깔끔).
  주관식은 채점 자체가 또 하나의 AI 문제(의미 동등성 판단)라 2차로.
- **지원 언어 1차**: Python + Java (SSAFY 사용자 = 사실상 이 둘).
  구조 분석은 tree-sitter(다언어 파서) 또는 LLM에 위임으로 단순화.
- **`tested_concept` 태깅**: 퀴즈마다 검증 개념 태그 → 세션 리포트에
  "이 팀은 예외 처리 개념이 약함" 같은 개념별 통계가 거의 공짜로 추가됨.

## 6. 향후 확장 로드맵 (AI 관점)

- **코드 실행 샌드박스**: output_prediction 유형을 제한 환경(subprocess + timeout + 네트워크 차단)에서
  실제 실행해 정답을 기계적으로 확인. LLM이 아닌 결정론적 검증기 추가
  → "LLM 판정 + 실행 기반 검증의 하이브리드 게이트".
- **대형 코드베이스 지원**: 저장소 단위 코드를 임베딩·색인하고 에이전트가 관련 코드를
  검색해 출제 — **이때가 진짜 Agentic RAG** (온보딩 시나리오 고도화).
  기획서 "향후 확장 방향"에 한 줄로 명시해두면 RAG 관련 Q&A 방어 완료.
- **난이도 자동 보정 (Elo)**: 퀴즈와 사용자에 Elo 점수 부여, 정답/오답마다 레이팅 교환.
  LLM이 붙인 difficulty는 부정확 → 실사용 데이터로 자가 보정. IRT(문항반응이론) 언급 가능.
- **개념 지식 그래프**: tested_concept 간 선수관계 그래프 ("재귀 → 스택 → 메모이제이션").
  틀리면 그래프 따라 선수 개념으로 내려가 진단. MySQL 관계 테이블로 구현 가능(스택 추가 없음).

# 토큰 관리 방식 톺아보기

---

## 0. 들어가며

- **세션 인증** vs **토큰 인증** 비교
- 토큰 인증에서 **Access Token / Refresh Token** 관리 방식에 집중
- **쿠키는 인증 방식이 아님** — 데이터 전달 매개체
  - 세션 ID를 쿠키에 담으면 → 세션 인증
  - 토큰을 쿠키에 담으면 → 토큰 인증

---

## 1. 세션 인증 방식 (Stateful)

### 흐름

1. 로그인 요청 → 서버가 DB와 대조 후 **세션 생성**
2. **세션 ID** 발급 → 서버 저장소(메모리/DB)에 저장
3. 후속 요청마다 쿠키에 세션 ID 담아 전송
4. 서버가 저장소에서 세션 ID 존재 여부로 검증

### 장단점

| 장점 | 단점 |
|------|------|
| 서버에서 인증 관리 → 클라이언트 정보 노출 위험 적음 | 요청마다 DB 접근 → **응답 속도 저하** |
| | 요청 증가 시 **서버 부하** |
| | MSA 환경에서 세션 일관성 유지 위해 **중앙 저장소** 필요 → **확장성 한계** |

---

## 2. 토큰 인증 방식 (Stateless)

### 핵심

- 서버에 **상태를 저장하지 않음**
- DB 조회 없이 토큰만으로 인증 → **응답 속도·확장성** 우수

### 단점

- **토큰 탈취 위험**
  - 클라이언트 자체에서 탈취
  - XSS 등으로 탈취
  - 클라이언트 → 서버 전송 과정에서 탈취

---

## 3. Access Token

### 3-1. Access Token과 JWT

- Access Token = **만료 기한이 있는 문자열**
- **JWT(JSON Web Token)** = 주로 사용되는 형식

#### JWT 구조

| 구성 | 내용 |
|------|------|
| **Header** | 토큰 유형, 서명 알고리즘 |
| **Payload** | 사용자 ID, 권한, 만료 시간 등 → **Self-contained** (DB 조회 없이 정보 파악) |
| **Signature** | Header + Payload + 비밀키로 생성 → **변조 방지** |

→ 서버에서 **별도 세션 저장소 불필요** (Stateless)

### 3-2. Access Token 저장 위치

| 저장소 | 특징 | 권장 |
|--------|------|------|
| **Local Storage** | 브라우저 닫아도 유지, XSS에 취약 | ❌ |
| **Session Storage** | 탭 단위, 브라우저 닫으면 삭제, XSS 취약 | ❌ |
| **Cookies** | 모든 요청에 자동 포함, 보안 플래그로 방어 가능 | ✅ (플래그 설정 시) |
| **Memory** | XSS 접근 어려움, CSRF 노출 없음, 새로고침 시 소멸 | ✅ (단기 AT에 적합) |

#### 쿠키 보안 플래그

| 플래그 | 방어 대상 |
|--------|-----------|
| `HttpOnly` | XSS (JS로 쿠키 접근 차단) |
| `Secure` | MITM (HTTPS에서만 전송) |
| `SameSite` | CSRF (교차 사이트 요청 위조) |

### 3-3. Access Token 인증 흐름

1. 로그인 → 서버가 DB 대조 후 **JWT 발급**
2. 후속 요청 → 헤더(또는 쿠키)에 AT 포함
3. 서버가 AT로 인증 확인 — **DB 접근은 로그인 시에만**

### 3-4. Access Token 로그아웃

| 방식 | 방법 |
|------|------|
| **Memory** | 클라이언트에서 AT null 처리 |
| **HttpOnly Cookie** | 서버에 로그아웃 요청 → `Set-Cookie`로 Expires/Max-Age 만료 |
| **BlackList** | 서버가 무효화된 JWT를 블랙리스트에 등록 → **Stateless 상실 + 오버헤드** |

### 3-5. Access Token 탈취 문제

- AT 탈취 시 → 해커/사용자 요청 **구분 불가**
- 만료까지 **무방비** 상태
- 만료 시간을 길게 → 보안 취약 / 짧게 → UX 나쁨
- → **Refresh Token 도입**

---

## 4. Refresh Token

### 4-1. Refresh Token과 JWT

- RT도 JWT 형식으로 만드는 경우가 많음
- AT와 달리 RT는 **반드시 DB 조회** 권장
  - Self-contained로 쓰면 → 불필요한 정보 노출 + **강제 무효화 불가**

### 4-2. Refresh Token 저장 위치

| 저장소 | 적합성 |
|--------|--------|
| **DB (Redis)** | ✅ 주로 사용 — 무효화 가능 + 빠른 조회 |
| Local/Session Storage | ❌ XSS 취약 |
| Memory | ❌ 새로고침 시 소멸 |
| Cookie | △ — 서버보다 Stateless, 서버보다 보안 약함 |

---

## 5. AT + RT 작동 방식

### 쿠키 방식

- 로그인 시 AT, RT **모두 쿠키**에 저장
- API 요청마다 두 토큰 함께 전달
- AT 만료 → RT ID로 사용자 정보 조회 → AT 재발급

### 서버 방식

- 로그인 시 **AT만 클라이언트**, **RT는 서버** 저장
- API는 AT만 사용, 만료 시 클라이언트가 RT 재발급 요청
- 서버가 저장된 RT와 대조 후 AT 재발급

---

## 6. Refresh Token 탈취 — RTR

### RTR (Refresh Token Rotation)

- RT로 AT 갱신할 때마다 **기존 RT 폐기 + 새 RT 발급**

#### Replay Attack 감지 시나리오

**사용자가 먼저 RT1 사용:**
1. AT2, RT2 재발급 + RT1 블랙리스트 등록
2. 해커가 RT1으로 재발급 시도 → 블랙리스트 감지
3. **모든 RT(RT1, RT2) 무효화**

**해커가 먼저 RT1 사용:**
1. AT2, RT2 재발급 + RT1 블랙리스트 등록
2. 사용자가 RT1으로 재발급 시도 → 블랙리스트 감지
3. **모든 RT(RT1, RT2) 무효화**

→ 누가 먼저든 Replay Attack 감지 시 **전체 토큰 무효화**

---

## 7. 권장 저장 위치 조합

**AT → Memory / RT → HttpOnly Cookie + RTR**

### 전체 흐름

```
1. 로그인
   └── HTTPS(TLS)로 자격 증명 전송 → DB에서 해시 비교

2. 토큰 발급
   ├── AT → 클라이언트 메모리 (짧은 만료)
   └── RT → HttpOnly 쿠키 + DB에 해시/폐기 여부 저장

3. API 요청 (Stateless)
   └── Authorization 헤더에 AT → DB 조회 없이 검증

4. AT 만료 → RT로 재발급
   ├── RT 쿠키 → /auth/refresh (Path=/auth/refresh)
   ├── SameSite=Strict/Lax → CSRF 차단
   └── DB에서 RT 폐기 여부 확인

5. RTR
   ├── 새 AT + RT 발급, 기존 RT 즉시 폐기
   ├── 새 RT → DB 저장 + HttpOnly 쿠키 교체
   └── 새 AT → 메모리 저장

6. Reuse Detection
   ├── 폐기된 RT로 재발급 요청 → 탈취로 판단
   ├── 해당 사용자 모든 RT 일괄 폐기
   └── 클라이언트 강제 로그아웃
```

### 보안 포인트 요약

| 요소 | 역할 |
|------|------|
| AT in Memory | XSS 시에도 RT 미노출, 짧은 만료로 피해 최소화 |
| RT in HttpOnly Cookie | JS 접근 불가 → XSS 방어 |
| Path=/auth/refresh | 일반 API에 RT 미포함 |
| SameSite | CSRF 방어 |
| RTR + Reuse Detection | RT 탈취·Replay Attack 대응 |

---

## 8. 핵심 비교 정리

| 구분 | 세션 | 토큰 (JWT) |
|------|------|------------|
| 상태 | Stateful (서버 저장) | Stateless (서버 미저장) |
| 속도 | DB 매 요청 | 로그인 시에만 DB |
| 확장성 | 낮음 (중앙 저장소 필요) | 높음 |
| 보안 | 클라이언트 노출 적음 | 토큰 탈취 위험 |
| 로그아웃 | 세션 삭제 | BlackList or 쿠키 만료 |

| 토큰 | 역할 | 저장 | 만료 |
|------|------|------|------|
| Access Token | API 인증 | Memory / Cookie | 짧게 |
| Refresh Token | AT 재발급 | DB(Redis) + HttpOnly Cookie | 길게 + RTR |

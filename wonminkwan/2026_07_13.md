# Amazon VPC Architecture 이해하기

---

## 1. 들어가며

서비스 설계 시 고려해야 할 계층:

| 계층 | 역할 |
|------|------|
| 프론트엔드 | 유저 경험, 화면 흐름 |
| 백엔드 | API 구조, 비즈니스 로직 |
| **인프라** | 서비스 안정성·확장성의 기반 |

인프라 없이 애플리케이션만 올리면, 평탄화되지 않은 땅 위에 건물을 세우는 것과 같다. **VPC는 그 땅을 고르고 지형을 파악하는 첫 단계**다.

---

## 2. AWS 글로벌 인프라

### 2-1. 리전 (Region)

- AWS는 전 세계 **34개 리전** 운영 (2026년 2월 기준)
- 리전 = **물리적으로 완전히 분리된** 인프라 단위
- 서울 리전 장애 → 도쿄·오하이오·프랑크푸르트 등 **다른 리전에 영향 없음**
- 리전 선택 = 서비스가 **물리적으로 어디에 위치할지** 결정하는 것

### 2-2. 가용 영역 (Availability Zone, AZ)

- AZ = **1개 이상의 데이터 센터**로 구성된 독립 공간
- 전력·네트워크·물리 인프라가 **서로 영향을 최소화**하도록 설계
- 하나의 AZ가 장애 나도 **다른 AZ에서 서비스 지속** → 고가용성의 출발점
- 서울 리전: **4개 AZ** (2026년 2월 기준)

### 2-3. 글로벌 인프라와 VPC의 관계

서비스마다 **위치 경계**가 다름:

| 서비스 | 동작 범위 | 특징 |
|--------|-----------|------|
| S3, DynamoDB | 리전 내 여러 AZ | 자동 분산 |
| EC2, RDS | 특정 AZ | **배치 위치를 직접 선택** |
| 일부 서비스 | 글로벌 | 리전에 묶이지 않음 |

**VPC = 특정 리전 안에서 만드는 나만의 가상 네트워크 공간**

## 3. VPC 기본 구성요소

### 3-1. VPC (Virtual Private Cloud)

- AWS 클라우드 안에 **직접 설계·통제 가능한 가상 네트워크**
- EC2, RDS, 로드밸런서 등 모든 리소스는 VPC 위에 배치
- VPC 구조 → 서비스 **안정성·확장성** 결정

### 3-2. IP 범위 (CIDR)

- VPC 생성 시 **CIDR 블록** 설정 (예: `10.0.0.0/16`)
- 한 번 정한 CIDR은 **변경이 매우 어려움**
- 이후 서브넷 분할·서비스 확장에 직접 영향 → **초기 설계가 중요**

### 3-3. 고가용성을 위한 AZ 설정

- AZ가 여러 개 있어도 **한 AZ에 몰아두면 의미 없음**
- 고가용성 = **최소 2개 이상 AZ에 리소스 분산**
- 한 AZ 장애 시에도 다른 AZ에서 서비스 유지 → **기본 전제**

### 3-4. 인터넷 게이트웨이 (IGW)

- VPC는 기본적으로 **외부와 단절**된 공간
- IGW = VPC와 인터넷을 연결하는 **항구**
- IGW 생성 + **라우팅 경로 설정**이 함께 되어야 인터넷 통신 가능
- **생성만으로는 동작하지 않음**

### 3-5. 서브넷 (Subnet)

VPC를 성격별 구역으로 분할:

| 종류 | 용도 | 특징 |
|------|------|------|
| **퍼블릭 서브넷** | 외부와 직접 통신 필요한 리소스 | 인터넷 접근 가능 |
| **프라이빗 서브넷** | 내부 자원 (DB, 앱 서버 등) | 외부 노출 불필요 |

→ 보안과 직결, 인프라 설계의 **방향성을 결정**

### 3-6. 라우팅 테이블 (Route Table)

- 서브넷별 **트래픽 방향**을 결정하는 길 안내판
- 연결된 라우팅 테이블에 따라:
  - 인터넷으로 나갈 수 있음 (퍼블릭)
  - 내부 통신만 가능 (프라이빗)
- **퍼블릭 vs 프라이빗의 본질적 차이 = 라우팅 설정**

#### NAT Gateway

- **문제**: 프라이빗 서브넷 서버는 외부 인바운드는 차단하되, 패키지 업데이트·외부 API 호출 등 **아웃바운드는 필요**
- **해결**: NAT Gateway
  - **퍼블릭 서브넷**에 배치
  - 프라이빗 리소스의 아웃바운드를 **자신의 공인 IP로 변환**해보냄
  - 외부에서 직접 들어오는 **인바운드 연결은 차단** (일방통행 출구)

### 3-7. Elastic IP (EIP)

- EC2 재시작 시 **공인 IP가 변경**되는 문제 해결
- **고정 공인 IP** — 직접 반납하기 전까지 변하지 않음
- 서버에 붙였다 떼는 것도 가능
- 운영 환경에서 **서버 주소 고정**에 필수

## 4. VPC 액세스 제어

### 4-1. NACL (Network ACL)

- **서브넷 단위** 접근 제어
- 서브넷 입구의 **문지기** — 인·아웃바운드 트래픽을 **규칙 번호 순**으로 검사
- 특정 IP 대역 차단 등 **거친 수준**의 통제에 적합
- 걸러진 트래픽은 **내부로 진입 불가**

### 4-2. Security Group (SG)

- **인스턴스 단위** 방어선
- NACL이 마을 입구라면, SG는 **개별 건물 현관문**
- 포트·프로토콜 단위 **세밀한 제어**
- 실무에서 **가장 자주** 다루는 보안 설정

### 4-3. NACL vs Security Group 비교

| 구분 | NACL | Security Group |
|------|------|----------------|
| 적용 단위 | 서브넷 | 인스턴스 |
| 제어 수준 | 거친 필터링 | 정교한 제어 |
| 비유 | 마을 입구 문지기 | 건물 현관문 |
| 동작 | 규칙 번호 순 평가 | 허용 규칙 기반 |

→ **두 장치가 함께 동작**할 때 VPC 보안이 완성 (다층 방어)

## 5. 핵심 정리

```
리전 (Region)
 └── 가용 영역 (AZ) × N
      └── VPC (CIDR: 10.0.0.0/16)
           ├── IGW (인터넷 연결)
           ├── 퍼블릭 서브넷 → IGW 경로
           │    └── NAT Gateway
           ├── 프라이빗 서브넷 → NAT 경유 아웃바운드만
           ├── Route Table (서브넷별 트래픽 방향)
           ├── NACL (서브넷 단위)
           └── Security Group (인스턴스 단위)
```

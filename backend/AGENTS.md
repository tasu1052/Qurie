# AGENTS.md

## 적용 범위

- 이 파일의 지침은 저장소 전체에 적용한다.
- 하위 디렉터리에 별도의 `AGENTS.md`가 있으면 해당 디렉터리에서는 더 구체적인 지침을 우선한다.
- 코드 수정 전 `.editorconfig`, 빌드 파일, 기존 소스 구조를 먼저 확인한다.
- 기존 프로젝트 규칙과 이 문서가 충돌하면 프로젝트에 명시된 설정을 우선하고, 충돌 사실을 작업 결과에 알린다.
- 요청과 무관한 코드 정리, 대규모 이름 변경, 전체 파일 재포맷을 하지 않는다.

## 기준 컨벤션

Java 코드는 **네이버 캠퍼스 핵데이 Java 코딩 컨벤션**을 따른다.

자동 포맷터, Checkstyle, Spotless 또는 `.editorconfig`가 설정되어 있다면 해당 설정을 실제 기준으로 사용한다.  
문서 설명과 자동화된 설정이 충돌하면 저장소에 커밋된 자동화 설정을 우선한다.

## 파일 형식

- 모든 소스와 텍스트 파일은 UTF-8을 사용한다.
- 줄바꿈은 LF를 사용한다.
- 파일 마지막에는 빈 줄이 아니라 하나의 최종 줄바꿈 문자를 둔다.
- 줄 끝의 불필요한 공백을 제거한다.
- Java 코드의 최대 줄 길이는 120자로 제한한다.
- `package`와 `import` 선언은 120자를 넘더라도 한 줄로 작성한다.

## 들여쓰기

- Java 코드의 들여쓰기는 스페이스가 아닌 **하드 탭 문자**를 사용한다.
- 탭 너비는 스페이스 4칸으로 표시한다.
- 코드 블록이 한 단계 깊어질 때마다 탭 한 개를 추가한다.
- 줄바꿈 후 이어지는 줄은 원래 줄보다 최소 한 단계 더 들여쓴다.
- 기존 파일에서 탭과 스페이스가 혼용되어 있더라도 요청과 무관한 전체 파일 재포맷은 하지 않는다.

## 중괄호

- K&R 스타일을 사용한다.
- 여는 중괄호는 선언 또는 제어문의 마지막에 둔다.
- `else`, `catch`, `finally`, `do-while`의 `while`은 닫는 중괄호와 같은 줄에 둔다.
- `if`, `else`, `for`, 향상된 `for`, `while`, `do-while`에는 본문이 한 줄이어도 중괄호를 반드시 사용한다.
- 비어 있는 블록은 필요한 경우 `{}`로 한 줄에 작성할 수 있다.

## 이름 규칙

- 식별자에는 영문, 숫자, 언더스코어만 사용한다.
- 한국어 단어를 발음대로 로마자로 옮긴 이름을 사용하지 않는다.
- 패키지 이름은 모두 소문자로 작성한다.
- 클래스, 인터페이스, enum, record 이름은 UpperCamelCase를 사용한다.
- 클래스 이름은 명사를 사용한다.
- 인터페이스 이름은 명사 또는 형용사를 사용한다.
- 메서드 이름은 lowerCamelCase를 사용하고 동사 또는 전치사로 시작한다.
- 변수와 매개변수 이름은 lowerCamelCase를 사용한다.
- 상수는 UPPER_SNAKE_CASE를 사용한다.
- 테스트 클래스 이름은 `Test`로 끝낸다.
- 반복문 인덱스나 매우 짧은 지역 범위의 임시 변수를 제외하고 한 글자 이름을 사용하지 않는다.
- 약어 표기는 프로젝트의 기존 방식과 일관되게 유지한다.

## 선언 규칙

- 하나의 Java 소스 파일에는 하나의 최상위 클래스만 둔다.
- 일반 import에는 와일드카드(`*`)를 사용하지 않는다.
- 네이버 컨벤션상 static import에는 와일드카드가 허용되지만, 기존 프로젝트가 금지한다면 프로젝트 규칙을 따른다.
- 제한자는 다음 순서로 작성한다.

  `public protected private abstract static final transient volatile synchronized native strictfp`

- 클래스, 인터페이스, 메서드, 생성자에 붙는 애너테이션은 원칙적으로 각각 별도 줄에 작성한다.
- 한 줄에는 하나의 문장만 작성한다.
- 하나의 변수 선언문에는 하나의 변수만 선언한다.
- 배열 대괄호는 변수명이 아니라 타입 뒤에 작성한다.
- `long` 리터럴의 접미사는 소문자 `l`이 아니라 대문자 `L`을 사용한다.
- 특수 문자는 유니코드 숫자 표현보다 `\n`, `\t`, `\\` 같은 전용 이스케이프를 사용한다.

## 줄바꿈과 공백

- 쉼표 뒤에는 공백을 둔다.
- 이항 연산자와 대입 연산자 앞뒤에는 공백을 둔다.
- 단항 연산자와 피연산자 사이에는 공백을 두지 않는다.
- 제어문 키워드와 여는 소괄호 사이에는 공백을 둔다.
- 메서드 이름과 호출 소괄호 사이에는 공백을 두지 않는다.
- 여는 중괄호 앞에는 공백을 둔다.
- 줄바꿈이 필요하면 쉼표 뒤, 점(`.`) 앞, 연산자 앞 등 네이버 컨벤션에서 허용한 위치에서 나눈다.
- 연관된 코드는 붙여 두고, 서로 다른 논리 단위는 빈 줄로 구분한다.
- 과도한 빈 줄을 추가하지 않는다.

## import 정리

- 사용하지 않는 import를 제거한다.
- 일반 import와 static import를 구분한다.
- 저장소에 IntelliJ Formatter, import order 또는 Checkstyle 설정이 있으면 그 순서를 따른다.
- import 순서를 맞추기 위해 와일드카드 import로 변환하지 않는다.

## 코드 변경 원칙

- 기존 패키지 구조와 계층 구조를 유지한다.
- 요청되지 않은 공개 API, DTO 형식, 데이터베이스 스키마 또는 설정값을 변경하지 않는다.
- 기능 변경과 단순 포맷 변경을 가능한 한 같은 커밋 또는 diff에 섞지 않는다.
- 새 코드는 주변 코드의 설계 패턴과 예외 처리 방식을 따른다.
- 설명을 위한 주석보다 명확한 이름과 작은 메서드를 우선한다.
- 주석은 코드가 무엇을 하는지가 아니라 왜 필요한지를 설명할 때 작성한다.
- 기존 테스트를 임의로 삭제하거나 통과시키기 위해 약화하지 않는다.
- 동작을 변경하면 정상 흐름과 주요 실패 흐름에 대한 테스트를 추가하거나 수정한다.

## 작업 완료 전 검증

저장소에 존재하는 빌드 도구와 wrapper를 사용한다.

- Gradle 프로젝트: 가능한 경우 `./gradlew test`를 실행한다.
- Maven 프로젝트: 가능한 경우 `./mvnw test`를 실행한다.
- Checkstyle, Spotless 또는 별도의 검증 task가 설정되어 있으면 관련 task도 실행한다.
- 자동 포맷 명령은 수정한 파일에만 영향을 주는지 확인한 후 실행한다.
- 테스트나 검증 명령을 실행하지 못했으면 실행하지 못한 이유를 명확히 알린다.
- 실행하지 않은 테스트를 통과했다고 말하지 않는다.

## 작업 결과 보고

작업이 끝나면 다음을 간단히 보고한다.

- 변경한 파일과 핵심 변경 내용
- 실행한 테스트 및 검사 명령
- 검증 결과
- 남아 있는 위험, 가정 또는 실행하지 못한 항목

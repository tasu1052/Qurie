## 1. MVP (Minimum Viable Product)

- **핵심 가치를 검증할 수 있는 최소한의 기능만 담은 첫 버전.** 완성품이 아니라 "이 아이디어가 먹히는지"를 최소 비용으로 확인하는 물건.
- Qurie의 MVP: 코드 업로드 → AI 퀴즈(객관식·빈칸) → 같이 풀기 + 동시 편집 에디터
- MVP가 아닌 것: 화상, 주관식 채점, 공식문서 근거 링크, Elo 보정
- 기획서 "개발 우선순위"의 "가장 먼저 구현하여 서비스 가치를 검증" = MVP 사고방식
- 왜: 6주 프로젝트에서 전부 만들려다 핵심도 못 끝내는 게 최대 실패 패턴
- 유래: 린 스타트업. 실무에선 "1차 개발 범위"와 거의 동의어

## 2. RAG 도입 판단 (오늘의 가장 중요한 설계 논의)

### 문제 제기 (내 질문)

코드 안에서만 출제하면 범용성이 떨어진다. 깊은 이해를 시키려면 공식문서 지식도 필요하지 않나?

### 결론: 2단계로 분리

**① 개념 확장 문제 → RAG 불필요 (프롬프트만으로 해결)**
- Python/Java 기초·중급 개념(공식문서 수준)은 LLM 파라미터에 이미 들어있음
- 검색해서 넣어주는 건 모델이 아는 걸 다시 보여주는 셈 → 품질 향상 거의 없음
- 해법: `concept_extension` 문제 유형 추가
  - 코드 내 출제: "이 어노테이션이 없으면 생기는 문제는?"
  - 개념 확장 출제: "트랜잭션 격리 수준 중 이 상황에 적합한 것은?"
- 기존 파이프라인 변경 없이 프롬프트 수정만으로 범용성 확보 (비용 ≈ 0)

**② 낯선/최신 라이브러리 → 조건부 검색 필요 (진짜 Agentic RAG)**
- 라이브러리를 쓰는 코드의 의미는 코드 자체에 안 적혀 있음 (문서에 있음)
  예: `vectorstore.as_retriever(search_kwargs={"k": 3})` — k의 의미는 LangChain 문서에
- 모델이 아는 라이브러리(표준 라이브러리, Spring 핵심)는 검색 없이 깊은 문제 가능
- 모델 지식이 낡은 것(LangChain처럼 빠르게 변하는 것, 마이너 라이브러리)은
  검색 없이 출제하면 **깊은 문제가 아니라 틀린 문제**가 나옴
- ⚠ 블라인드 검증의 맹점: Generator와 Solver가 **같은 낡은 지식을 공유**하면
  둘 다 속아서 할루시네이션 퀴즈가 통과할 수 있음

**조건부 검색 구조:**
```
analyze_code에서 import 목록 추출
  → 표준/유명 라이브러리만 → 검색 없이 출제 (기존 파이프라인)
  → 낯선 라이브러리 감지 → API 문서 검색 → 결과를 Generator·Judge 프롬프트에 첨부 → 출제
```
- "항상 검색"이 아니라 "필요할 때만 검색", 그 판단을 시스템이 함
  = Agentic RAG의 정의("검색이 고정 단계가 아니라 결정되는 도구") 그대로

### 우선순위 확정

1. **MVP**: 기존 파이프라인 + concept_extension. 1차 범위를 "표준 라이브러리 중심 코드"로 명시
2. **2차**: import 기반 조건부 문서 검색
3. 기획서 확장 로드맵 문구: "라이브러리 API 문서 조건부 검색 — 코드가 사용하는 외부
   라이브러리를 감지해 공식문서를 검색·참조하여 출제하는 Agentic RAG 구조"

### Q&A 방어 멘트 (최종 버전)

> "표준 라이브러리 범위에선 불필요해서 안 썼고, 필요해지는 조건(낯선 라이브러리)을
> 정의해서 조건부 도입을 설계했습니다."
> — 무조건 쓴 것보다 훨씬 잘 이해한 답변

## 3. 학습 로드맵 확정 (4주 코스)

| 단계 | 내용 | 기간 |
|---|---|---|
| 0주차 준비 | HTTP 감각 (Spring 경험과 매핑) | 반나절 |
| 1단계 | FastAPI 기본기 (공식 튜토리얼 + 실습) | 3~4일 |
| 2단계 | LLM API 직접 다루기 (프레임워크 없이 GMS 호출) | 2~3일 |
| 3단계 | LangGraph (toy 재구현 → 공식 튜토리얼) | 3~4일 |
| 4단계 | 통합 — 진짜 파이프라인 + FastAPI 연결 | 1주 |
| 5단계 | 조건부 검색 구현 | 1주 |

**공부 방법 원칙:**
- AI 사용 규칙 변경: "코드 생성기" → "코드 리뷰어". 내가 먼저 짜고 리뷰만 시킴
- 파인만 테크닉: 단계 끝날 때마다 팀원에게 5분 설명. 막히는 지점 = 이해 안 된 지점
- 역순 학습: 문서 정독 말고, 만들다 막히면 문서 찾기

## 4. DevOps

- **Development + Operations.** 개발↔운영의 벽을 허물고 코드 작성부터 배포·운영까지
  하나의 자동화된 흐름으로 만들자는 문화 → 실무에선 그 일/직무의 통칭
- 배경: 예전엔 개발팀이 코드를 "던지고" 운영팀이 배포·복구 → "내 컴에선 되는데" vs "서버 터졌는데" 책임 미루기
- 핵심 도구:
  - **Docker** — 앱+실행환경을 컨테이너로 포장, 어디서든 똑같이 실행
  - **CI/CD** — push하면 자동 테스트 → 통과 시 자동 배포 (수동 배포 제거)
  - **모니터링** — 서비스 생존/에러율/응답속도 감시
- Qurie의 "인프라·통합" 담당 역할이 정확히 이것
- 나(AI 담당)와의 접점: FastAPI 서버의 Dockerfile, API 키 환경변수 주입, `GET /health` 엔드포인트
- 커리어 연결: **AI 엔지니어링(배포/서빙) ≈ DevOps 기술의 AI 적용**
  → 이번 프로젝트에서 인프라 담당 어깨너머로 Docker/CI 봐둘 것

## 5. Jira 업무 유형 4가지

| 유형 | 크기/목적 | Qurie 예시 |
|---|---|---|
| **에픽** | 몇 주짜리 기능 묶음 | "AI 퀴즈 생성 파이프라인" |
| **스토리** | 사용자 가치 한 조각 ("누가 ~할 수 있다") | "사용자는 코드 업로드로 퀴즈 5개를 받을 수 있다" |
| **작업** | 개발자가 할 일 한 조각 | "Generator 프롬프트 v1 작성" |
| **버그** | 되던 게 안 됨 (고장 신고) | "정답 인덱스가 보기 순서와 어긋남" |

- **판별법**: 데모로 보여줄 수 있으면 스토리 / 개발자끼리만 의미 있으면 작업 / 고장이면 버그 / 몇 주 묶음이면 에픽
- 실용 팁: 에픽 = 기획서 핵심 기능 4~5개, 스토리 = 주차별 데모 단위, 작업 = 하루~이틀 크기
- 내 AI 에픽의 작업 목록 = 학습 로드맵 단계가 거의 그대로

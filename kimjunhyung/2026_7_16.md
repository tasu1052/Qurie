## 한 문장 요약

**애자일**(변화 대응 철학)을 **스크럼**(1주 스프린트 반복)으로 구현하고, 그 실행을 **Jira**(Epic–Story–Task 계층 + 보드)로 기록하되, **일관되게 · 실시간으로 · 균형 있게** 하라.

## 1. 개념 계층: 애자일 → 스크럼 → Jira

| 층위 | 정의 | 비유 (Java 기준) |
|---|---|---|
| 애자일 (Agile) | 변화에 적극적으로 대응하는 개발 방법론 (철학) | 패러다임 (OOP) |
| 스크럼 (Scrum) | 짧은 스프린트 단위로 사이클을 반복하는 애자일 구현체 | 언어 스펙 (Java) |
| Jira | 스크럼을 실제로 운영하는 프로젝트 관리·협업 도구 | 실행 환경 (JVM + IDE) |

### 워터폴 vs 애자일

- **워터폴**: 요구사항 → 디자인 → 개발 → 테스트 → 배포. 한 방향, 되돌아가기 어려움
  - 문제: 후반에 결함 발견 시 수정 비용 폭발, 끝까지 동작하는 제품 없음, 요구사항 변경 대응 불가
- **애자일**: 디자인 → 개발 → 테스트를 짧은 사이클로 반복. 매 사이클마다 동작하는 결과물 + 피드백 반영
- 수학적 직관: 워터폴 = 한 번에 해를 구하는 직접법, 애자일 = 해에 수렴해가는 iterative method. 문제(요구사항)가 계속 변하는 환경에서는 반복법이 강건함

### 스크럼 핵심 규칙

- **스프린트 = 반복의 단위** (1~4주, SSAFY는 1주)
- 기간 고정(timebox): 시간이 상수, 작업량이 조정 대상
- 매 스프린트마다 동작하는 결과물이 나와야 함
- 짧게 쪼개면 추정이 정확해지고, 매주 실측값으로 다음 추정을 보정하는 피드백 루프

### Jira를 쓰는 이유

- 화이트보드+포스트잇으로는 안 되는 것: 실시간 현황 공유, 계층 구조 관리, 스프린트 기록(velocity), Git 연동
- GitLab 이슈와의 차이: GitLab은 코드 중심 경량 트래커, Jira는 스프린트·스토리 포인트 등 스크럼 운영 기능이 깊음
- 채용 우대사항의 "Jira 능숙"의 진짜 의미 = 스크럼 프로세스 안에서 일해본 경험, 작업을 이슈 단위로 쪼개고 추정하는 능력, 투명한 진행 공유 습관

## 2. 위클리 루틴 (1주 스프린트)

| 시점 | 활동 | 내용 |
|---|---|---|
| 월요일 오전 | **계획** | Product Backlog → Sprint Planning Meeting → Sprint Backlog |
| 월~금 | **수행** | 스프린트 실행 + 매일 Daily Scrum (24H) |
| 금요일 종료 전 | **회고** | Sprint Review + Sprint Retrospective |

### 역할

- **Product Owner(PO)**: 뭘 만들지 결정, 요구사항의 주인
- **Scrum Master**: 프로세스 진행자 (팀장 ≠ 상사)
- **Team**: 개발자들
- SSAFY 6인 팀에서는 팀장이 PO + 스크럼 마스터 겸하는 경우가 많음

### 핵심 개념

- **Sprint Backlog ⊂ Product Backlog**: 우선순위와 팀 수용량(velocity) 기준으로 부분집합을 뽑는 게 계획
- **Daily Scrum**: 매일 15분 이내. "어제 한 것 / 오늘 할 것 / 막힌 것(blocker)" 3가지. 목적은 보고가 아니라 **장애물 조기 발견**
- **Review vs Retrospective**:
  - Review = 결과물 검토 (대상: 제품) → 제품을 개선
  - Retrospective = 과정 회고 (대상: 팀) → 팀을 개선
  - 회고 결과가 다음 주 계획에 반영되며 루프가 닫힘

## 3. 데일리 루틴

1. Jira 켜기
2. 오늘 할 이슈를 **할 일 → 진행 중**으로 이동
3. 이슈 수행 (코딩)
4. **Git Push 후** 이슈를 **진행 중 → 완료**로 이동
5. Jira 끄기

### 포인트

- 핵심은 **보드 상태와 실제 상태의 동기화**. 이슈 이동 = 팀에게 보내는 실시간 방송
- 완료 기준이 Push인 이유: "코드 다 짰다"는 주관적, "Push했다"는 객관적. Definition of Done을 검증 가능한 이벤트에 걸어둠. 로컬에만 있는 코드는 팀 입장에선 존재하지 않음
- **동시에 여러 개 병행보다 하나의 작업 수행 권장** (WIP 제한)
  - 컨텍스트 스위칭 비용 (재몰입에 20분+)
  - 3개를 60%씩 = 팀에 전달된 가치 0. "Stop starting, start finishing"
  - 보드 가독성

## 4. Jira 용어: Epic · Story · Task · Sub Task

```
Epic
├── Story ── Sub Task
└── Task ── Sub Task
```

| 단위 | 정의 | 아이콘 |
|---|---|---|
| Epic | 큰 단위의 작업 | 보라색 번개 |
| Story | 사용자 관점의 기능·요구사항 | 초록색 책갈피 |
| Task | 개발자의 단위 작업 (기술적 작업) | 파란색 체크 |
| Sub Task | Story/Task 하위 세부 작업 | 하늘색 겹친 사각형 |

### Story vs Task — 크기가 아니라 관점의 차이

- 판별 질문: **"이 작업이 끝나면 사용자가 뭔가 달라진 걸 체감하나?"** → Yes = Story, No = Task
- Story와 Task는 같은 층위. Task가 Story에 종속되는 게 아니라 둘 다 Epic 바로 아래 독립 이슈로 존재 가능
- Story를 사용자 언어로 강제하는 이유: 백로그가 "전달할 가치 목록"이 되어 우선순위 판단이 쉬워짐
- 관용 문형: "As a [사용자], I want [기능], so that [목적]" — SSAFY에선 "~할 수 있다" 꼴 유지만 해도 충분
- "사용자 관점"은 최종 사용자만이 아니라 **작업 결과물을 소비하는 사람** 관점으로 넓게 이해 (예: 발표 자료 조사도 Story 가능)

### 예시 (퀴즈 생성 프로젝트)

- Epic: `퀴즈 생성 파이프라인`
- Story: `사용자가 코드 파일을 업로드하면 퀴즈를 받아볼 수 있다`
- Task: `FastAPI 마이크로서비스 초기 세팅`, `GMS API 클라이언트 모듈 작성`
- Sub Task: `업로드 API 엔드포인트 구현`, `파일 파싱 로직 작성`

## 5. Epic 분할 전략

| 전략 | 기준 | 예시 | 장점 | 단점 |
|---|---|---|---|---|
| **기능 중심** | 주요 기능 단위 | 회원 관리, 게시글 관리 | 기능별 진척이 보임, 애자일 철학에 부합 | 담당 구분이 흐려짐 |
| **역할 중심** | 역할/기술 스택 단위 | Backend 세팅, Frontend 개발 | 담당자 관리 깔끔 | 기능이 여러 Epic에 흩어짐 |

- 같은 작업 집합을 (기능, 역할) 중 어느 축으로 파티셔닝하느냐의 문제 — 한 축으로 묶으면 다른 축은 흩어짐
- **실전 권장: 혼합** — 기능 중심 기본 + 초반 세팅 작업만 역할 중심 Epic (세팅은 어떤 기능에도 속하지 않으므로)
- 우리 프로젝트 Epic 설계:
  - `BE 프로젝트 세팅` (역할)
  - `AI 서비스 세팅` (역할)
  - `퀴즈 생성` (기능)
  - `퀴즈 풀이/채점` (기능)
  - `검수 파이프라인` (기능)
- **평가는 전략 선택이 아니라 "일관성"을 봄** — 뒤죽박죽이 최악

## 6. Jira 실제 조작 워크플로우

```
① 타임라인에서 Epic 생성
② 백로그에서 스프린트 컨테이너 생성
③ 백로그에서 이슈(Story/Task) 생성
④ 이슈 속성 채우기 (Epic 연결 · StoryPoint · 담당자)
⑤ 이슈를 스프린트로 Drag & Drop
⑥ 스프린트 시작
⑦ (1주간 데일리 루틴)
⑧ 스프린트 완료 → Review/회고 → ①로 반복
```

### ① Epic 생성

- 경로: **타임라인 → + 만들기 에픽 → 내용 입력**
- 타임라인에서 만드는 이유: Epic은 기간을 가지므로 간트 차트 뷰(타임라인)가 관리 화면

### ③ 이슈 생성

- 경로: **백로그 → + 이슈 만들기 → 유형 선택(작업/스토리/버그) → 제목 입력**
- 제목 컨벤션: `역할 / 내용` (예: `FE / 사용자 로그인 기능 개발`) — 우리 팀은 `BE /`, `FE /`, `AI /`
- 유형을 정확히: 전부 Task로 만들면 컨벤션 평가 감점 요인

### ④ 이슈 관리 (속성 채우기)

- **Epic 연결**: `+ Epic` 버튼 → 선택. 연결해야 계층 구조가 실제로 생김
- **StoryPoint**: 포인트 입력란에 숫자
- **팀원 할당**: 사람 아이콘 → 선택. 스프린트에 들어가는 모든 이슈는 담당자 필수 (유령 이슈 금지)
- 우선순위는 스프린트 시작 후 이슈 세부 창에서 설정 가능
- 완성 상태: 한 줄에 `유형 | 키 | 제목 | Epic 라벨 | 상태 | 포인트 | 담당자`가 다 보임

### ⑤⑥ 스프린트 등록 & 시작

- 등록: 백로그 영역 이슈를 스프린트 영역으로 **Drag & Drop** = 계획 회의의 물리적 실체
- 판단 기준: 우선순위 + 수용량 (포인트 합이 velocity를 넘지 않게)
- 시작: **스프린트 시작** 버튼 → 이름 / 기간 / 시작·종료 날짜 / **스프린트 목표** 입력
- 목표는 "이슈 6개 처리"가 아니라 "코드 업로드부터 퀴즈 생성까지 E2E로 돌아간다" 같은 한 문장 — 주중 우선순위 판단 기준이 됨
- 시작 = 상태 전이: 보드 활성화, 데일리 루틴 개시, timebox 고정

### ⑧ 스프린트 완료

- **스프린트 완료** 버튼 → 미완료 이슈를 다음 스프린트로 이월 선택
- **이월은 실패가 아니라 데이터**: "30 계획, 27 소화" = 실측 velocity → 다음 계획에 보정
- 매주 100% 완료가 계속되면 오히려 의심 (추정이 보수적일 가능성)
- 주의: 하위 Sub Task가 미완료면 스프린트를 닫을 수 없음 (계층 정합성 강제)

## 7. 스토리 포인트 (Story Point)

**정의**: 작업 구현을 위한 전반적인 노력의 추정치 측정 단위

### 왜 시간이 아니라 포인트인가

- 절대 시간 추정은 "누가 하느냐"에 종속됨 (같은 작업이 사람에 따라 2시간 vs 8시간)
- 포인트 = **상대적 복잡도**. "저 작업의 2배쯤"이라는 비율 관계는 누가 하든 대체로 일정
- 기준 작업을 1포인트로 잡고 비교로 추정 (절대 척도 → 비율 척도)
- 따라서 팀마다 기준이 다름 → **팀내 합의가 가장 중요** (A팀의 5 ≠ B팀의 5)

### 척도: 선형 vs 피보나치

- 선형: 1, 2, 3, 4, 5, …
- **피보나치: 1, 1, 2, 3, 5, 8, 13, …** ← 실무 표준
- 피보나치인 이유: **추정 불확실성은 작업 크기에 비례** → 큰 작업에 1단위 눈금은 가짜 정밀도(false precision)
  - 인접 항 비율이 황금비 φ ≈ 1.618로 수렴 → 사실상 **로그 스케일 눈금**
  - Weber–Fechner 법칙과 같은 구조 (감각은 자극의 로그에 비례)
- 부수 효과: 13을 넘으면 "추정 불가능할 만큼 크다 → 쪼개라"는 신호

### 플래닝 포커

1. 이슈 하나에 대해 각자 **동시에** 카드 제시 (anchoring 방지)
2. 비슷하면 확정
3. 크게 갈리면(2 vs 8) → 숫자 차이가 아니라 **이해 차이**가 드러난 것 → 논의 후 재투표
- 진짜 가치: 숫자보다 **숨은 요구사항과 리스크가 드러나는 과정**

### 우리 팀 시작 기준 (1주 스프린트)

| 포인트 | 감각 |
|---|---|
| 1 | 반나절 이하 (설정 수정, 간단 UI) |
| 2 | 하루 (CRUD API 하나) |
| 3 | 1~2일 (연동 포함 기능) |
| 5 | 2~3일 (Self-Refine 루프 같은 복잡 로직) |
| 8+ | 쪼개라는 신호 |

- 팀 수용량 30포인트(6명 × 1주)로 시작 → 첫 스프린트 실측 후 보정

## 8. SSAFY 평가기준 3가지

### ① 컨벤션과 가독성

> Epic, Story, Task 등 이슈에 대한 컨벤션을 정하고 일관성 있게 준수했는지? 작업의 정보를 한 눈에 알아볼 수 있는가?

- 백로그를 열었을 때 모든 이슈가 같은 규칙으로 읽히는가
- 대응: 첫 계획 회의에서 컨벤션 문서화 (Epic 전략, 제목 접두어, Story 문형)

### ② 실시간성

> 실시간으로 이슈 관리를 제대로 진행하고 있는가?

- 전형적 실패: "금요일 몰아서 옮기기" — 상태 변경 이력이 타임스탬프로 남아서 들킴
- 대응: 데일리 스크럼에서 각자 보드 열어놓고 말하기 → 회의가 보드 갱신을 강제

### ③ 분배의 균형

> 이슈의 담당자를 적절히 지정했는지? 스토리 포인트 분배, 업무를 팀 내 균형있게 분배했는가?

- 담당자 없는 유령 이슈 금지 + 포인트 쏠림 체크
- 스토리 포인트의 이중 용도: 추정 도구 + **업무량의 정량 지표**
- AI 파트처럼 무거운 작업은 포인트를 정직하게 크게 → 이슈 개수가 적어도 업무량이 기록으로 증명됨

## 9. 실습 중 배운 것 (화면 관련)

- **팀 설정** (Atlassian Teams): 이슈 소스를 프로젝트에 연결, 계획 스타일 Scrum, 스프린트 길이 1주(SSAFY 기준), 수용량 30으로 시작 후 실측 보정. 단, 팀 기능은 편의 기능 — 평가 핵심은 프로젝트 보드의 Epic/Story/Task 관리
